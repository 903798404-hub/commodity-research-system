# Routine Release 工具实现说明

本文从顶层[标准发布规范](../../07_docs/03_标准开发与生产发布规范.md)下沉命令、请求字段和生命周期细节，不增加发布分类、授权或证据层。风险 Gate 以当前 `release_reversibility.py`、`pre_release_runtime.py` 和顶层规范为准。ADDITIVE_REVERSIBLE 不调用 Routine 专用入口，但按同镜像 Candidate/Production 验收，且不要求真实 targeted recovery PASS。

## Routine Stateless 工具入口

只有现有 `classify_release` 对精确 production → target 直接输出 `ROUTINE_STATELESS`，或机器
`NEEDS_MAINTAINER_RISK_REVIEW` 且无 destructive evidence、由绑定 exact diff/main/完整 state/infra
事实的 Maintainer review 正式解析 `FINAL_RELEASE_TREATMENT=ROUTINE_STATELESS`，才能使用
`04_scripts/runtime/routine_release.py`。无 caller risk override。DB/schema、storage、数据写入、
Compose/mount、runtime authorization 或不可逆变化仍进入原 high-risk 流程；本入口不改分类核心。

流程为 `MAIN CI PASS → BUILD ONCE → VALIDATE EXACT IMAGE → APPLICATION SMOKE →
DEPLOY SAME IMAGE → POST-DEPLOY SMOKE → DEPLOYMENT RESULT`。本节取代 routine 对第10–12节
多级签名/Manifest 和 seal-before-cleanup 的强制要求；高风险保持原要求。源码、现有数据
Manifest、Approved Commit/Tree/Image、受保护 host policy、fresh execution grant 和独立生产批准不变。

命令均在已批准、root-owned 的独立 Linux 工具检出执行，不在正式业务仓库运行：

```text
python -B 04_scripts/runtime/routine_release.py build --request <approved-request.json> --output <build.json>
python -B 04_scripts/runtime/routine_release.py validate --request <approved-request.json> --output <acceptance.json>
python -B 04_scripts/runtime/routine_release.py deploy --request <approved-request.json> --output <deployment.json>
```

请求是管理员准备的部署输入，root-owned 0600；不可由业务容器写入。共有字段：
`source_root`（独立 clean detached target）、`project_id`、`base_commit`、`target_commit`、
`target_tree`、`ci_record`（正式 hosted Admission JSON）、`production_data_mutation=false`、
`rebuild=false`。需要人工风险解析时还必须携带同一受保护 `maintainer_risk_review`；缺失、超过24小时、
base/target/tree/main/diff/findings 不一致或 state/infra 事实不完整均阻断。工具源码和 target 源码
可以是不同的已批准 Commit，分别核验。

- build：`build_authorized=true`、全新 `build_directory`；独占创建 attempt 目录，只 build 一次。
  失败后不在同一 attempt 自动重建。记录 Commit/Tree/Image ID、RepoDigests（可为空）、release ID、
  OCI/source revision、CI run。production/validation 阶段没有 build 调用。
- validate：`candidate_authorized=true`、不可变 `image_id`、`candidate` 实例输入；使用 existing exact
  image，以 `compose up --no-deps --no-start --no-build --pull never --force-recreate <service>` 创建未启动实例（Compose 2.27.1 支持），
  由现有 issuer 签发 fresh candidate grant 后才 start。candidate namespace 必须为空且以
  `routine-candidate-` 开头，只开放 localhost 测试端口，restart=no；禁止 lifecycle/data hooks。
- deploy：`production_authorized=true`、同一 `image_id`、`acceptance_record`、`production`、
  `previous_release`、`rollback`。重新核验 current container/namespace 和上一镜像源码身份，
  创建 fresh production 实例、签发 fresh production grant、启动、health/HTTP 和所选 UI acceptance。
  禁止 rebuild、数据 refresh、provider/FULL DAILY。失败记录 release FAIL 并恢复上一 image。

每个实例输入包含 `project_directory`、`compose`、`environment`、`policy_template`、全新
`policy_output`、`grant_directory`、`key_path`、`writable_root`、`container_port`。这些是部署方
按现有 host policy/Runtime Manifest 准备的实际文件和路径，不是任意 shell command。
Compose 只允许目标服务、精确 Image ID、正式 entrypoint、只读 rootfs 和显式 bind mounts，
不得含 build、command、post_start、pre_stop。Candidate may use writable runtime paths only when their host sources are isolated candidate-owned storage. Production-backed mounts remain readonly unless executing the actual production instance.
Manifest 的 target/mode/required mounts 不变；candidate 使用现有 create_candidate_scope 的受保护目录和设备号/inode 绑定，不以 caller 的 writable_root 声明授权。可选 production_readonly 输入仅引用既有受保护 production policy 的 policy_path/source/target；scope 保存 policy 哈希及 source 设备号/inode，fresh grant 重新核验。已批准生产只读输入不冒充 CI fixture，其余 seed 字节校验保留。
candidate scope、marker、seed/只读业务视图按现有宿主工具准备；
Routine HTTP Candidate Compose 使用 `routine_release.candidate_compose_document` 生成：独立 project 的普通 bridge（internal=false），仅发布 `127.0.0.1:<host_port>`，禁止 external/production network；生成后再绑定现有 host policy 的 Compose hash，create 不改写已绑定配置。容器端口仍由实例合同指定。Production 与 high-risk validator 网络合同不变。
本入口不抓数据、不复制正式 secret、不创建 snapshot。实例创建后工具只填入实测 config digest，
并保留现有 issuer 对源码、Compose、mount、nonce、角色、grant 签名/期限的完整验证。

`application_smoke` 配置 `kind`、相对 `path`；通用 `kind=dom` 还配置非空 `selectors`
（CSS selector → 必须出现的正整数数量）。URL 必须落在实际容器 inspect 确定的端口，不能替换
为其他服务。第一 consumer 使用 `kind=soybean-fixed-months`、`path=?workspace_page=import_profit`。
`empty_sessions` 列出已通过只读数据盘点确认无结果的 AM/PM；不得凭空声明 store 状态。
AUTOMATED 模式第一 consumer 为 `?workspace_page=import_profit`，用宿主 Playwright Chromium 读取实际绑定容器
端口的 `.profit-card` DOM：AM/PM 各12行，完整船期 YYYY-MM 的月份序列各为01..12。
声明空的 session 的行情/CNF/榨利必须为空；税率等配置参数可以存在。CNF=0 是真实数值，
不当作 null。部分数据不影响12行判断。仅 AUTOMATED 的 Playwright 和 Chromium 须在环境预检中已可用；
本工具不在发布时安装依赖。HTTP 200 或 Python unit test 不能替代所选 UI 验收；MANUAL 由用户查看实际页面完成同一业务检查。

`routine-candidate-acceptance/1` 是工具生成的普通 JSON，含 Commit/Tree/Image/Release ID、
project/base/CI run、validation timestamp、runtime preflight/health/application smoke 及 cleanup
结果。AUTOMATED 候选在 finally 清理；MANUAL 机器通过时保留等待，完成/拒绝/取消后清理；清理失败则验收 FAIL。无需大型 Evidence Bundle、截图签名、DOM
hash tree 或把完整 grant 嵌入 signed record。结果写到受保护的新文件，不能手填 PASS。
host issuer 读取 hash-bound 普通 record 时重新计算风险；high-risk 不能借普通 record 降级。

`routine-deployment-result/1` 记录 deployed identity、CI run、candidate acceptance、时间、
production health/smoke、previous release、最终 result 和 rollback result。无需再套多级签名。
普通发布仍保留可诊断日志、已有数据 Manifest、上一 release/Compose/env/data/schema 恢复资产。

`previous_release` 至少含 commit/tree/image_id/container_id/release_id；`rollback` 除实例字段外
还包含上一 `source_root` 与全新 `assets_output`。切换前实测旧镜像和健康，生成普通
`routine-rollback-assets/1`；恢复时仅允许同一 routine forward delta 的旧 identity，使用新实例与
新 grant，旧 historical grant 不读取、不续期。AUTOMATED 回滚的上一版本 DOM 只验证其原页面可加载，不要求它
已经包含本次12月修复。没有发布前 rehearsal 要求；恢复失败必须如实记录，不宣称 release PASS。
本合同不承诺 host loss recovery：只有 local Image ID 时仍记录 LOCAL_IMAGE_ONLY。

## Routine MANUAL / AUTOMATED

请求 `ui_acceptance_mode` 可为 `MANUAL` 或 `AUTOMATED`，省略保持 AUTOMATED 兼容。
MANUAL 无 Playwright/Chromium 依赖，不能覆盖机器失败，不能降级 STATEFUL_OR_INFRA。
两种模式均保留 exact source/CI/risk/image/OCI、隔离/readonly data、fresh candidate/production grant、runtime preflight 和 health。
MANUAL 额外执行实际应用 HTTP 检查；AUTOMATED 保持浏览器页面验证。

MANUAL validate 机器 PASS 后输出 `WAITING_FOR_MAINTAINER_UI_ACCEPTANCE`（退出码2，不是失败或最终PASS），
普通 checkpoint 保存精确 Commit/Tree/Image/Release、CI、container ID/start time、URL、实例输入和机器结果。
候选继续运行，提供实际 URL（localhost 通过既有安全访问方式查看），不得扩大端口暴露。
Maintainer 查看 AM/PM 各1–12月、空月份无假值、CNF None/0、部分数据、日期/origin/跨年身份，同时确认布局、历史 PM 图、历史 CNF 和其他 import-profit 页面无明显回归，再明确回复验收结果。
操作者把该回复记录为普通请求 `manual_ui={"decision":"PASS|FAIL|CANCEL","operator":"实际操作者"}`，
并设置 `checkpoint_record` 指向工具产生的等待记录。禁止推测用户同意或手改机器字段。

```text
python -B 04_scripts/runtime/routine_release.py candidate-ui --request <manual-request.json> --output <accepted-or-failed.json>
python -B 04_scripts/runtime/routine_release.py production-ui --request <manual-request.json> --output <final-result.json>
```

candidate-ui 仍需 candidate_authorized；production-ui 仍需 production_authorized。记录和输出受现有 host 文件保护，
每次输出使用新文件；不是加密审批、token、签名 UI evidence 或 approval server。
恢复必须对应同一连续运行 container/start/restart/namespace/URL 和精确 image，重新检查 readonly mounts、health/HTTP。
原 runtime preflight 只证明当时 fresh grant 启动；连续实例等待不续期旧 grant；实例重启或替换立即停止，不能沿用人工决定。
人工 PASS 不覆盖新机器失败。Candidate PASS 后清理其容器，正式 deploy 的 acceptance_record 使用该 accepted 输出；
FAIL/CANCEL 安全清理候选并保留失败记录，不切换。未确认不得 deploy；不会重新 build。

MANUAL deploy 机器通过后保存 production checkpoint 并再次返回 WAITING_FOR_MAINTAINER_UI_ACCEPTANCE。
用户验收实际生产页面后 production-ui PASS 才输出最终 release PASS；FAIL/CANCEL 或新机器失败输出 FAIL 并 rollback。
回滚仍用上一 exact image/Compose/env/source、fresh instance/grant、runtime preflight、health/HTTP/readonly 检查；
MANUAL 回滚不依赖浏览器，恢复后向用户提供旧页面作人工确认。回滚结果不把失败的新 release 改为 PASS。
不可确认原实例身份时停止操作并报告 drift，不删除或替换未知容器。高风险发布原严格合同不变。

代码/模拟测试完成不等于真实容器验收，也不授予 production deployment 权限。

## HIGH_RISK 执行路径闭包修订草稿

状态：`DRAFT_PENDING_PRODUCTION`。这不是生产启用或维护窗口授权。

现有 `deployment_plan.json` 增加严格的 1.8.0 HIGH_RISK 分支；1.7.0
legacy 分支保留原规则。unknown field 继续拒绝。新计划绑定独立工具
Commit/Tree、旧/目标/primary rollback 应用 Commit/Tree/Image ID、受保护的
release request（含 Review、签名 CandidateValidationRecord、配置/挂载合同、
恢复证据）、当前实例和其 policy、目标与回滚实例构造输入、发布锁及数值策略。
`formal_containers={}` 表示新实例尚不存在，不填写未来 Container ID。
实例 policy template 是构造输入，不是已经签发的实例 grant；真实配置在
create 后由现有 host observation 与 source/render bridge 核验，并形成新的
protected policy/output。计划封存只表示意图固定，绝不是执行授权。

发布锁固定在既有受保护宿主存储父目录下的
`/var/lib/market-data/production-runtime/spread-release.lock`；父目录必须已存在且
通过既有 root ownership/permission 验证。锁用 O_NOFOLLOW、0600 和非阻塞 flock，
不假定共享 `/run/lock` 是 root-only 目录，不改变它的系统权限。

正式 producer/verifier 与实际入口：

```text
python3 09_deploy/spread_release/create_deployment_plan.py --high-risk-input /protected/draft.json --output /protected/deployment_plan.json
python3 09_deploy/spread_release/verify_release_contract.py --high-risk-plan /protected/deployment_plan.json
python3 09_deploy/spread_release/high_risk_execution.py --plan /protected/deployment_plan.json --output /protected/new-execution-evidence
```

宿主执行入口消费相同封存计划，在发布锁下先做现有 assessment、Review/main
freshness、签名验收、当前实例/配置和真正回滚 issuer/资产可用性检查。
然后仅停止本次服务、create 未启动目标、观察实际实例、正式 pre-release
revalidation、适用的 service credential、fresh production grant、精确
`docker start <created-id>`、post-start comparator、非 root Runtime Readability、
ApplicationServiceContext（仅支持它的新应用）、health/HTTP/DOM 和观察。
不会签发后再通过 compose up 重建实例。执行器不接受 CLI 自定义 transport
或 PASS override；Hosted 只通过内部测试 seam 注入实际 Docker 故障。

停服前失败保持源服务；停服后 create/授权/启动/验收失败，停止失败目标，
以 primary rollback 精确旧镜像创建新实例，再由旧应用适用的现有 production
issuer 签发 fresh grant 并完成 Readability/health/页面验收。禁止拿
`routine-rollback-assets/1` 代替 HIGH_RISK 恢复批准，禁止复用 rehearsal grant。
旧应用没有 Application Service Identity 时不强行加入新 credential 模型。

readiness 复用既有默认：总等待 90 秒、轮询 2 秒、请求 3 秒、连续成功 2 次。
观察时长、轮询、连续失败数、stop/start/rollback 超时及固定失败分类均必须
显式封存，缺失在停服前拒绝。建议生产草稿观察 120 秒、轮询 2 秒、连续失败
2 次、stop 10 秒、start 60 秒、rollback 180 秒；这些不是原系统既有规定，
需未来生产计划明确确认。Hosted 用显式 2 秒观察来验证状态衔接，不当作生产
策略。runtime/image/mount/grant 漂移、退出/重启立即失败；health 连续失败或
观察结束仍不健康进入回滚。普通 warning 不触发回滚。grant 仍有既有有效期，
观察过程中继续检查；不能因保留证据复用过期 grant。

恢复 verifier 不仅依赖 sandbox 文件，还要求原实例仍运行。最后必要消费在
停服前完成；证据与其 live 资源保留到部署成功或成功回滚，才清理准确绑定的
临时 rehearsal 实例、sandbox 与 grant。回滚失败保留待人工恢复资源。
历史 evidence 不删不改，当前运行实例的 grant/service credential 不作为临时
演练凭据清理；失败目标 credential 在成功恢复后按精确实例范围销毁。
不削弱 verifier，不在停服后把旧的 live predicate 冒充仍然成立。

legacy `deploy_spread_release.sh` / `rollback_spread_release.sh` 的 compose-up
路径不是这次 HIGH_RISK 的完整入口；严格 legacy plan verifier 会拒绝 1.8.0
计划。旧脚本仅用于其原合同，不得列入本次 HIGH_RISK 完整可用切换方案。
工具版本与应用目标分别记录；新工具可加载精确应用源码中的现有 issuer，
不把工具 SHA 写入旧镜像 RELEASE，不自动改变 0d7b86d 应用目标或重建 8046a28
镜像。生产批准、镜像验收有效性、Review freshness 仍需分别正式核验。

本节仍为草稿；身份与大豆真实生产闭环完成后再独立完成权威手册闭包。

### Hosted executor compatibility / 输入准备修订

状态仍为 `DRAFT_PENDING_PRODUCTION`。独立宿主工具负责 transport 与共享
`runtime_observation.py.compose_mounts` 解释；精确应用源码的
`host_authorization.py` 仍负责既有 policy、record、mount/source 与 grant/consumer
合同，旧应用不要求提供新工具私有 `_observe` wrapper。不得 monkeypatch 旧 issuer，
不得把新版 grant 强加给旧 consumer。HIGH_RISK `_prepare_session` 在任何 stop 前
检查实际加载文件和必需调用签名；旧/新 issuer 的源文件、模块名及 Commit/Tree
记录于新 attempt 的 `issuer-loading-*` 和 execution result。缺少所需接口明确拒绝。
Compose 预检包括 volumes 与经过既有严格 declaration 解析的 RO 文件 secrets；
真实 inspect 的全部 mounts 再由同一 manifest/policy validator 核验，无 secret 通配。

HTTP 可见性不是 signing role：显式已批准 Compose loopback binding 必须与
Docker 实际 loopback publication 精确匹配；production 未指定/通配 binding 仍
只接受既有 wildcard/dual-stack 形式。candidate 仍只允许 loopback；额外端口、
地址或 publication 不匹配都拒绝。不得为了 synthetic production-role E2E
而把隔离端口暴露为 public，或跳过正式 health/HTTP 检查。

readiness 解释 Docker public inspect 的 `State.Status`（含 `removing`），
不要求 engine-internal `RemovalInProgress` 必须出现。Running/Dead/Restarting
必须为显式布尔值，Status 必须为已知状态；若显式提供 removal flag，其类型及
移除状态一致性仍校验。未知、malformed 和 terminal/removing 状态不接受为就绪；
原始 inspect、签名和 raw hashes 不规范化回写。

正式应用 preflight 的完整 stdout/stderr（脱敏）、原始流 SHA256、argv、CID/Image
与退出码保存后再处理失败。旧 CLI 只输出 error_type 时，失败分支可通过同一
镜像内未修改的 parser/readonly_preflight 函数保存新诊断 traceback；该诊断不
替代 CLI 验收，原 CLI 非零结果仍拒绝，诊断返回零也不能转为 PASS。

Linux 同入口 E2E 必须完成 sealed plan → create → fresh credential/grant → start →
Readability/health/HTTP/DOM → observation；另外实际 start 后故障必须经同入口
fresh old instance / 新 grant 回滚。基线或 rehearsal 的 grant 不能用于恢复实例。
恢复 evidence 的 live 依赖保留至最后消费者验证，成功部署/回滚后才按精确范围
清理；失败收据及 raw hashes 不改写。Hosted synthetic trust 不是生产批准。

CI required/full 两条 lane 使用同一个 `required_lane_fixtures.py` setup，
在各自 disposable checkout 建立 `01_data`、`06_outputs`、`10_logs` 空目录。
这些是 Registry forbidden-path 的存在性合同，不是数据库/Parquet 输入；不补造
业务文件。外部输入继续来自既有确定性 synthetic builder 和精确 checkout 的
tracked config，输出到各 job 独立 RUNNER_TEMP，读取后封为只读。fixture manifest
记录相对清单、大小、内容 SHA256、实际 checkout/装配路径；测试前验证可读性和
字节身份，缺输入明确 INPUT_PREPARATION_FAILED。两侧通过既有 full artifacts
传递 preparation receipt，在完整 paired comparison 前比较同一 input identity，
不互相覆盖源码、不共享 RW runtime、不访问生产数据。原 67 个失败保留原状态，
只能由新精确 SHA 的完整成对结果证明消除；相同历史债务仍单列。

## 宿主 Docker 时间兼容与发布手册修订草稿

状态：`DRAFT_PENDING_PRODUCTION`。本节是实现说明及发布手册修订草稿，
不是新的生产操作标准；身份与大豆真实生产闭环完成后另行 documentation closure。

宿主发布工具本次兼容目标为实际 Ubuntu `/usr/bin/python3`（Python 3.10.12）；
应用镜像仍使用 `Dockerfile.spread-runtime` 中锁定的 Python 3.12 基础镜像
（既有生产构建证据为 3.12.13）。两者不是同一个解释器合同。正式命令中的
`python`/`python3` 由调用方 PATH 选择，源码不会自动升级或替换系统 Python；
运维执行前记录明确的 executable 和 `--version`，例如使用现有

### RELEASE-REFRESH：固定镜像重验与准备入口（修订草稿）
