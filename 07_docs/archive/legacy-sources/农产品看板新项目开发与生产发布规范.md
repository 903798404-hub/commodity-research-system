# 农产品看板标准开发与生产发布手册

## 1. 文档定位

本手册是 `market-data` 单仓库的标准开发、测试、Git、GitHub、服务器构建、候选验收、正式部署、基线、回滚与清理规则。它适用于主工作台、USDA、Oil World 及后续农产品研究模块，可直接作为 Codex 的执行约束。

唯一正式链路是：

> 本地唯一开发源 → 本地测试与 Git 提交 → GitHub `main` → 服务器只读可信检出 → 候选镜像与候选容器 → 密封部署计划 → 用户批准 → 正式部署 → 密封部署结果 → 部署后生产基线

生产服务器只运行经过确认的完整 Git SHA，不作为日常开发环境，不从服务器向 GitHub 推送代码。

## 2. 变更范围驱动原则

发布验收范围必须由本次代码变更范围决定。每次开发开始前必须明确：

- 本次修改什么；
- 直接影响哪些文件、页面、数据和运行链；
- 明确不修改什么；
- 需要哪些专项测试；
- 需要哪些回归检查；
- 服务器候选阶段需要验证什么。

如果验收过程中出现与本次变更无关的品种、Parquet、业务模块或历史测试依赖，必须停止并重新判断验收范围。不得为了追求表面上的“更严格”而无边界扩大服务器测试。

本地完整仓库测试可以作为全局回归门槛。服务器候选阶段重点验证：

- Git、Tree、镜像 ID、OCI revision 等不可变身份；
- 候选冷启动、健康接口和 RestartCount；
- 本次受影响页面、路由、外部入口和降级逻辑；
- 正式数据只读、生产服务与其他容器不变；
- 本次变更直接涉及的部署契约。

任何范围扩张都要先形成新的书面依据和停止点，不得在发布过程中临时探索。

## 3. 系统边界与目录

`market-data` 是唯一 Git 根目录。核心职责位置如下：

| 位置 | 职责 |
|---|---|
| `01_data/` | 动态业务数据；部署不得覆盖或清空 |
| `02_configs/` | 非敏感配置 |
| `03_src/` | 可复用业务代码 |
| `04_scripts/` | 本地与服务器执行入口 |
| `05_apps/` | Streamlit 页面与应用 |
| `06_outputs/` | 输出与报告 |
| `07_docs/` | 契约、手册和审计说明 |
| `08_tests/` | 测试 |
| `09_deploy/` | Docker、Compose、发布与回滚定义 |
| `10_logs/` | 运行日志 |
| `11_独立应用/` | USDA、Oil World 等独立前端源码 |

动态数据、日志、输出和 `.env` 与镜像分离。部署不得覆盖 `/home/ubuntu/market-data/01_data`、`06_outputs`、`10_logs` 或生产环境文件。任何凭据只记录变量名、路径、所有者和权限，绝不记录值。

## 4. 开发前契约

开发前至少固定以下信息：

### 4.1 项目和页面

- 项目名称、业务目标、用户和场景；
- 本期范围与非目标；
- 放入现有应用还是新增应用；
- 页面入口、路由、默认筛选、失败降级和响应式要求；
- 不得影响的现有页面和服务。

只有依赖隔离、独立扩缩容或安全边界确有必要时才新增容器。进入主工作台的功能归属于 `spread-dashboard` Release。

### 4.2 数据

- 权威来源、认证变量名、更新频率与时区；
- 自然年、市场年或作物年度；
- raw、processed、stable 路径；
- Schema、类型、单位、空值和唯一主键；
- 修订、幂等、异常停止和质量验收规则；
- 宿主机路径、容器路径、写入主体和只读边界。

### 4.3 运行

- 更新命令、cron、锁、日志和状态文件；
- 成功、无变化和失败行为；
- 敏感变量文件的路径与权限；
- 容器重建后的数据持久性检查；
- 候选与生产的端口、挂载和网络。

## 5. 本地开发标准

1. 从本地干净 `main` 开始，先记录完整 HEAD。
2. 读取根 `AGENTS.md`、项目契约和本手册。
3. 运行 `git status --short`，识别用户原有修改和未跟踪文件。
4. 只修改书面范围内文件，不夹带日志、缓存、截图、数据或临时产物。
5. 先运行变更模块专项测试，再运行约定的完整回归。
6. 运行 Python 语法检查、`git diff --check` 和必要的页面实测。
7. 审查 `git diff`、`git diff --stat`、`git diff --name-status`。
8. 在提交前确认业务数据、Docker、Compose、cron 和生产文件没有越界修改。

Windows 本地不要求 Docker Desktop、Podman 或 WSL。本地负责代码、Python、前端、Streamlit、静态构建契约和 Git 检查；生产镜像在服务器隔离目录构建。

## 6. Git 本地提交标准

必须使用显式文件路径暂存：

```powershell
git add -- 05_apps/example.py 08_tests/test_example.py
```

禁止：

```text
git add .
git add -A
git commit -a
```

标准提交闸门：

1. `git status --short`
2. `git diff --check`
3. `git diff --stat`
4. `git diff --name-status`
5. 显式 `git add -- <允许文件>`
6. `git diff --cached --check`
7. `git diff --cached --stat`
8. `git diff --cached --name-status`
9. 运行提交前完整测试和语法检查
10. 创建含义明确的业务提交
11. `git show --check --stat --oneline HEAD`
12. 确认提交只含允许文件

本地 `main` 只允许按预期领先 `origin/main`。提交标题应清楚说明业务目标，不能只写“update”“fix”或日期。

## 7. GitHub 推送标准

推送前：

```bash
git status --branch --short
git remote -v
git branch -vv
git rev-parse HEAD
git fetch origin
git rev-parse origin/main
git log --oneline origin/main..HEAD
git diff --name-status origin/main..HEAD
```

必须确认远程没有意外变化、本地只领先预期提交、差异文件完全匹配审查结果。使用普通 fast-forward：

```bash
git push origin main
```

禁止 `--force` 和 `--force-with-lease`；只有单独的特殊恢复任务明确批准后才可讨论后者。

推送后核对：

```bash
git fetch origin
git rev-parse HEAD
git rev-parse origin/main
git ls-remote origin refs/heads/main
```

三者必须指向同一完整 SHA。GitHub 更新不会自动改变生产服务器。

| 包装脚本 SHA-256 | `4eef86b5129ef6be39229cc5ae5f262b200d97f9a4fe880e05f865f056d239de` |

公钥：

```text
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIOgaJ5D9QaMywWpc9mNB4I7mb086O+vQwuiGpKz8ne/T commodity-research-system production read-only deploy key
```

规则：

- 轮换密钥时同步更新 GitHub Deploy Key、公钥、指纹和包装脚本审计。

## 9. 可信构建源标准

固定流程：

1. 使用包装脚本执行 `git ls-remote`，确认远程 `main` 完整 SHA。
2. 浅克隆 `main` 到新的唯一临时目录。
3. 不直接复用失败目录，不优先使用裸 SHA fetch。
4. 克隆后核对 `HEAD` 完整 SHA，并记录 Tree SHA。
5. 执行 `git fsck --connectivity-only`。
6. 确认工作区干净。
7. 切换为 detached HEAD。
8. 验证通过后原子 rename 为：

   `/home/ubuntu/market-data-builds/<FULL_GIT_SHA>`

9. 生成 `checkout_result`、审计文件和 Manifest。
10. 只有 `checkout_passed=true` 才允许构建镜像。

失败检出不得删除或复用，完整归档到 `failed-checkouts`，记录大小、文件数、inode、ctime、mtime 和失败原因。

## 10. 超时、Shell 与 UTF-8 安全

### 10.1 超时

本次浅 Git 操作曾约 124 秒后被外层工具终止。`git ls-remote` 数据量小，不代表 `clone` 或 `fetch` 也会同样快。

- Git 内部克隆 timeout 可为 900 秒；
- 自动化外层 timeout 必须更大，例如至少 1000 秒；
- 不得让外层工具先于 Git 内部 timeout 终止；
- 不得使用 `nohup`、后台运行或忽略退出码绕开验收。

### 10.2 远程 Shell

- 复杂 SSH 参数必须固化在包装脚本中；
- 自动化只传包装脚本路径和少量稳定参数；
- 禁止在复杂远程单行命令中嵌套 `GIT_SSH_COMMAND='ssh ...'`；
- 禁止 `eval`；
- 禁止不断增加反斜杠修复多层引号；
- 多行远程脚本必须使用 quoted heredoc；
- 包含反引号、美元符号或中文正文时，禁止未引用 here-doc；
- JSON、Markdown、Dockerfile 和审计文件优先由服务器 Python 以 UTF-8 生成。

### 10.3 UTF-8 与中文路径

本次发生过 PowerShell 到远程 Shell 的中文路径问号替换，以及首次追溯部署结果中文内容损坏。

- 中文路径不得通过 PowerShell 文本管道、`echo`、Shell 数组或远程命令参数传递；
- 路径枚举和复制由服务器内部 Python `pathlib` 完成；
- 脚本通过 SCP 等字节安全方式传输；
- 生成后执行严格 UTF-8 往返读取；
- 检查 ASCII 问号替代和 `U+FFFD`；
- 发现损坏立即停止，不得覆盖；
- 损坏产物整体移入唯一失败归档目录；
- 重新生成后重新计算并验证 Manifest。

### 10.4 Shell 变量

Shell 变量区分大小写。本次 `command_file` 与 `COMMAND_FILE` 不一致曾导致构建前退出。

```bash
set -euo pipefail
: "${VARIABLE:?VARIABLE is required}"
```

所有关键变量在首次使用前显式赋值。不得关闭 `set -u` 掩盖错误。空发布目录不得直接删除，应归档并记录 inode、ctime、mtime 和失败原因。

## 11. 候选镜像标准

- 标签绑定短 SHA，禁止 `latest`、`new` 或无标签作为候选/正式身份；
- `org.opencontainers.image.revision` 必须为完整 Git SHA；
- 记录 `source`、`created`、`title`、`version`；
- 新镜像 ID 必须与旧正式镜像不同；
- 不覆盖旧镜像标签；
- 构建产物包括 `image_build_result`、完整 inspect、原始命令、原始输出和 Manifest；
- 缓存统计解析失败不得事后猜测；
- Docker build 成功但审计失败时，可独立核验镜像身份，但必须保留 warning；
- 正式部署直接使用已验收的同一 Image ID，不得重新构建或重新打标签。

## 12. 候选容器标准

- 端口只绑定 `127.0.0.1`；
- 正式数据优先只读挂载；
- 日志、缓存和临时文件写入候选独立目录；
- restart policy 为 `no`；
- 核验容器 ID、镜像 ID、OCI revision、`MARKET_DATA_GIT_HEAD`；
- 检查根页面、健康接口、RestartCount 和日志；
- 禁止临时向公网公开候选端口；
- 候选截图必须来自候选容器，不得用效果图、本地旧图或生产截图代替；
- 发布结束后候选容器是否停止和删除必须进入独立清理任务。

## 13. 测试与验收标准

必须区分：

| 层级 | 目标 |
|---|---|
| 变更模块专项测试 | 验证直接变更语义 |
| 本地完整仓库回归 | 验证全局代码回归 |
| 候选镜像运行验证 | 验证打包身份、启动和健康 |
| 真实浏览器验收 | 验证受影响页面、路由、响应式和外部入口 |
| 部署契约测试 | 验证部署文件、身份和回滚边界 |

本次经验：

- 精简生产镜像可以不包含 `08_tests`、`09_deploy` 和完整文档；
- 不要求生产镜像承载完整仓库测试；
- `PYTHONPATH` 必须保留原始值并追加真实闭包，不能整体覆盖；
- `collect-only` 原始日志与 JUnit 是权威；
- 禁止宽松正则猜测测试数量；
- 构建测试环境前先审计静态文件依赖闭包；
- 与本次变更无关的测试数据不得阻断发布；
- 如需拆分测试矩阵，在开发阶段设计并审查，不在发布阶段临时探索。

## 14. 部署前生产基线

部署前必须有密封生产基线，至少记录：

- 生产 Git HEAD、Tree、detached/clean 状态；
- 容器、镜像、OCI revision、端口、挂载、网络、命令和 RestartCount；
- 仅限白名单的非敏感环境变量；
- 六项或本项目定义的关键数据 size、mtime、SHA-256；
- USDA、Oil World 等未变服务；
- HTTP 与健康状态；
- 自动任务的身份与状态（任务在本次范围内时）。

基线在正式目录外的同文件系统临时目录生成。Manifest 全部通过后原子 rename。正式目录 `0555`、文件 `0444`、所有者 `root:root`。不建立会变化的 `latest/current` 链接，旧基线永久保留。

## 15. 部署计划

候选验收通过后先生成密封 `deployment_plan`：

- 初始 `execution_permitted=false`；
- 需要用户明确批准；
- 部署计划和回滚脚本必须通过 `bash -n`；
- 锁定新旧提交、Tree、镜像 ID、容器 ID、挂载、端口、环境白名单和回滚对象；
- 记录预计中断、健康轮询、强制停止和回滚条件；
- 不得直接执行未审核命令；
- 不得在生产执行 `git pull`；
- 生产 Git 对象从可信构建源受控传入，最终保持 detached HEAD。

## 16. 正式部署

标准切换：

1. 再次验证部署前基线、部署计划、候选结果和所有 Manifest。
2. 预创建新容器并核对配置，不占用正式端口。
3. 停止旧容器，将其改为唯一、明确的回滚名称并保留。
4. 将新容器切换为正式名称并启动正式端口。
5. HTTP 和健康通过后切换生产 Git 到固定提交。
6. 核验 Git HEAD、OCI revision、`MARKET_DATA_GIT_HEAD` 三重一致。
7. 验证受影响页面、内部路由、外部入口、数据和其他容器。
8. 任一强制项失败立即按密封计划回滚。
9. 不自动删除旧容器、旧镜像、候选容器或失败对象。

## 17. 部署结果是强制阶段

部署脚本成功结束前必须生成并密封：

- `approval_record.json`
- `deployment_result.json`
- `deployment_audit.md`
- `pre_deployment_runtime.json`
- `post_deployment_runtime.json`
- `production_browser_checks.json`
- `deployment_result_manifest.sha256`

生成、JSON 校验、Manifest 校验、权限密封和原子发布必须是正式部署脚本的强制最后阶段，而不是部署后的可选补充。

如果 `deployment_result` 缺失：

- 不得宣称发布事实链完成；
- 不得直接生成部署后生产基线；
- 必须先执行受控追溯重建；
- 标明 `result_capture_mode=retrospective_reconstruction`；
- 无法恢复的原始时间或测量值写为 `null`；
- 操作方报告值单独标记 `operator_reported`，不得伪装为服务器测量值。

## 18. 回滚标准

不同阶段的回滚必须明确：

- 新容器尚未接管端口：删除与否留待审计，旧服务保持不变；
- 旧容器已停止、新容器未健康：恢复旧容器名称、端口和运行状态；
- 新容器已健康、Git 切换失败：恢复旧容器和旧 Git；
- 页面或数据验收失败：恢复旧容器、旧镜像、旧提交和正式端口；
- 任何阶段都要核验数据不变性和其他服务不变。

不得用 `latest` 临时替代回滚镜像。回滚失败时保留旧容器、失败新容器和日志，停止自动操作并升级为人工恢复。

## 19. 部署后生产基线

部署结果密封后必须生成 `post_deployment` 生产基线，记录：

- 新生产 Git、Tree、正式容器和正式镜像；
- Git、OCI revision、`MARKET_DATA_GIT_HEAD` 三重身份；
- 端口、挂载、网络、RestartCount 和环境白名单；
- 数据哈希；
- USDA、Oil World 等不变服务；
- 回滚容器和候选容器；
- 部署结果引用、前一基线引用和 `known_warnings`。

只有部署结果和部署后基线均密封，发布才正式闭环。

## 20. 清理标准

清理是独立任务。默认禁止：

```text
docker system prune
docker image prune
docker volume prune
docker compose down
```

清理前只读盘点当前正式容器和镜像、候选容器、回滚容器、测试与矩阵镜像、构建源、生产基线、部署计划、部署结果、失败归档和磁盘使用。

分类只能使用：

- `must_keep`
- `keep_until_next_update_cycle`
- `keep_until_manual_review`
- `safe_to_stop_after_approval`
- `safe_to_delete_after_approval`
- `unknown_do_not_touch`

保留原则：

- 当前正式镜像长期保留；
- 最新旧正式镜像和回滚容器至少保留一个正常自动更新周期及用户确认期；
- 生产基线、部署计划、部署结果和 Manifest 长期保留；
- 失败审计至少保留到经验写入手册并再完成一次后续成功发布；
- 候选容器可在正式稳定确认后，经单独授权先停止，再决定是否删除；
- 测试镜像与中间测试目录仅在无容器引用、无生产事实链依赖且复盘完成后，经批准清理；
- 可信构建源至少保留到本 Release 清理评审完成；
