# 执行环境与跨环境传输规范

## 1. 目的与适用范围

本规范用于防止任务因环境识别错误、附件路径猜测、跨环境文件不可达、超时处理不当或编码损坏而中断或重复执行。它适用于 `market-data` 单仓库内的开发、测试、诊断、发布准备和生产操作。

根目录 `AGENTS.md` 中的“执行环境预检”是强制闸门。本规范提供详细执行方法，不降低仓库现有的数据、部署和生产保护要求。

除简单文本修改外，任何任务在正式执行前都必须完成预检。部署、生产诊断、数据替换、跨环境传输和长时间命令始终必须预检。

## 2. 四个环境及其边界

四个环境相互隔离。禁止默认认为一个环境中的路径、附件、进程、凭据或工具可以被另一个环境直接访问。

### 2.1 Windows 本地开发环境

正式仓库：

```text
C:\Users\xx202\Desktop\codex自动更新\codex-projects\market-data
```

该环境主要负责代码和文档修改、本地测试、Git 提交及 GitHub 推送。应先确认实际仓库根目录，不能仅凭当前目录名称判断已经位于正式仓库。

### 2.2 Codex 执行与附件环境

Codex 通常可以访问当前打开的工作区，以及用户明确附加到 Codex 任务且已进入当前可访问文件系统的附件。

Codex 不得假设：

- 能够访问 ChatGPT 会话中的 `/mnt/data`；
- 附件一定保存在 `Downloads`、桌面、当前工作区或 Git 仓库；
- 用户提到的文件名与本地发现的同名文件是同一文件。

使用附件前必须先定位实际绝对路径，并验证存在性、可读性、大小和必要的 SHA-256。

### 2.3 ChatGPT 会话沙箱

常见路径：

```text
/mnt/data/<filename>
```

该路径只属于生成文件的 ChatGPT 当前会话环境。Windows、Codex 和 Ubuntu 生产服务器不能自动访问该路径。

ChatGPT 提供下载链接后，只有用户将文件下载到本地，或把文件重新附加到 Codex 任务，文件才进入 Codex 可访问环境。Codex 不得把 ChatGPT 回复中的 `/mnt/data/...` 当作 Windows 或 Codex 本地路径执行命令。

### 2.4 Ubuntu 生产服务器

正式仓库通常位于：

```text
/home/ubuntu/market-data
```

服务器只运行经过确认的 Git SHA 和正式镜像。Windows 文件、Codex 附件及 ChatGPT 沙箱文件不会自动出现在服务器上；文件必须通过明确、可审计的传输方式进入服务器。

服务器路径只是参考值时，必须先在服务器只读确认实际路径。不得因为本地存在同名文件就认为服务器也存在，反之亦然。

## 3. 强制执行环境预检

开始正式执行前，Codex 必须确认并向用户输出以下信息：

1. 当前操作系统和版本。
2. 当前 Shell 及版本。
3. 当前工作目录。
4. Git 仓库根目录。
5. 当前 HEAD、分支和 `git status --short`。
6. 每个任务输入文件的实际绝对路径。
7. 输入文件是否存在、是否可读；需要身份保证时计算 SHA-256。
8. 每条关键命令应在 Windows 本地、Codex 执行与附件环境、ChatGPT 会话沙箱还是 Ubuntu 服务器执行。
9. 目标执行环境是否能够直接访问输入文件。
10. 是否需要跨环境传输，以及计划采用的传输方式。
11. Python、Node、Git、Docker、SSH 等本任务实际依赖是否可用；不相关工具可标记为“不需要”，不得把非依赖工具缺失误报为任务失败。
12. 当前文件、仓库、Docker、SSH 或服务器权限是否满足任务要求。

预检必须先于业务修改、测试、诊断、传输或部署命令。只读的路径、仓库、工具和权限检查属于预检本身。

预检失败时必须停止正式执行，只报告缺失条件及其影响。不得：

- 自行安装软件；
- 创建内容相似的替代输入文件；
- 从未知目录复制同名或相似文件；
- 修改 `PATH`；
- 扩大本地或服务器权限；
- 关闭 SSH 主机密钥校验或替换既有 SSH 身份；
- 降低哈希、签名、分支、提交或生产身份校验标准。

如果用户重新上传附件、提供明确路径或补充权限即可解除阻塞，应准确说明所需的单一条件，不进行猜测式修复。

## 4. 路径与文件身份

路径只在其所属环境中有效。同名文件不代表同一文件，路径相似也不代表来源可信。

文件从一个环境进入另一个环境后，必须重新确认：

- 实际绝对路径；
- 文件大小；
- SHA-256；
- 修改时间；
- 文件所有者和权限；
- 预期用途；
- 是否允许覆盖目标。

涉及发布、部署、生产诊断、数据替换或其他高风险任务时，源端与目标端 SHA-256 不一致必须停止。不得把“内容看起来相同”作为哈希不一致时继续执行的依据。

路径必须使用明确的绝对路径。跨环境操作不得使用模糊路径、未展开变量、通配符或“找到的第一个同名文件”作为正式输入。

## 5. 跨环境文件传输

### 5.1 ChatGPT 到 Codex

正确流程：

1. 用户下载 ChatGPT 生成的文件，或把文件直接附加到 Codex 任务。
2. Codex 在当前可访问文件系统中定位附件实际路径。
3. Codex 验证文件存在、可读、大小合理，并按任务要求计算 SHA-256。
4. 通过后才把该文件作为任务输入。

不得使用 ChatGPT 回复中的 `/mnt/data/...` 作为 Codex 本地路径，也不得猜测附件位于 `Downloads`、桌面或仓库。

### 5.2 Windows 到 Ubuntu：一次性临时执行

一次性只读脚本优先通过既有 SSH 连接的标准输入执行：

```bash
ssh <existing-host> 'bash -s' < "<local-script>"
```

执行前必须在 Windows 本地完成：

- 确认脚本实际绝对路径和可读性；
- 语法检查；
- SHA-256 校验；
- 危险命令和生产写入审查；
- SSH 主机别名、既有身份及目标环境确认；
- 内外层超时预算确认。

脚本必须以前台方式执行并保留退出码、stdout 和 stderr。除非任务明确要求服务器保留文件，不得把临时脚本永久写入服务器。

PowerShell 不能支持某种输入重定向语法时，不得改用后台任务或把大量脚本正文嵌入复杂单行命令。应使用已审查的本地脚本或能够逐字节传递文件的前台包装入口，并验证实际传输字节；不得用可能改变编码的文本管道代替文件字节传输。

### 5.3 Windows 到 Ubuntu：持久文件

服务器需要长期保留的文件可以使用 SCP，但执行前必须明确：

- 本地源文件绝对路径；
- 远程目标绝对路径；
- 目标文件所有者和权限；
- 传输前源文件 SHA-256；
- 传输后目标文件 SHA-256；
- 是否明确允许覆盖现有文件；
- 目标已存在、哈希不符、权限不符或传输失败时如何停止。

不得使用模糊路径、通配符或未确认的目标目录；不得覆盖未知正式文件。默认不允许覆盖，除非任务明确授权且已确认恢复来源。

### 5.4 正式开发与发布文件

正式业务代码、部署脚本和可复用诊断工具优先采用以下可信链路：

```text
本地 Git 提交
→ GitHub main
→ 服务器只读可信检出
```

服务器必须核验完整 Git SHA，并按现有部署规则核验镜像和容器身份。不得长期依赖聊天附件、临时 SCP 文件或来源不明的压缩包作为正式生产构建输入。

## 6. 长任务、超时与完成判定

所有长命令必须保持前台运行，并最终返回明确退出码。禁止通过以下方式绕开自动化工具或外层 Shell 的超时：

```text
nohup
后台执行
Start-Job
不等待的 Start-Process
忽略退出码
仅凭输出文件暂时为空判断任务失败
```

如果命令具有内部 timeout，自动化工具或外层 Shell 的 timeout 必须更长并保留合理缓冲。例如内部 timeout 为 900 秒时，外层 timeout 至少应大于 1000 秒；还应考虑 SSH 建连、输出刷新和退出清理所需时间。

任务完成必须综合确认：

- 进程已经退出；
- 退出码明确；
- 预期完成标记存在；
- stdout 和 stderr 已完整保留；
- 必要时输出文件大小稳定且 SHA-256 已记录。

不得只凭任务刚启动时某个输出文件仍为 0 字节，就判断启动失败或重复启动同一任务。状态不明确时，应先确认原进程是否仍存在、退出码是否已生成及输出是否只是尚未刷新。

超时必须被报告为“执行时间或工具边界问题”，不能自动归类为代码失败。超时后不得未经确认就重复执行可能产生副作用的任务。

## 7. Shell、编码与中文路径

Windows、PowerShell、SSH 和 Linux 之间不得通过复杂单行命令传递大量脚本正文。复杂操作优先使用：

- 已审查的脚本文件；
- SSH 标准输入；
- SCP；
- Git 可信检出；
- 目标环境内部 Python 生成 JSON 或 Markdown。

命令使用哪一种引号、重定向和路径语法，必须以实际执行 Shell 为准。不得把 Bash 语法直接当作 PowerShell 语法，也不得把 Windows 路径直接当作 Linux 路径。

涉及中文路径、中文正文、JSON 或 Markdown 时，必须：

1. 以 UTF-8 严格模式读取，遇到非法字节即失败。
2. 避免经过会隐式采用系统代码页的文本管道。
3. 传输后重新检查大小和 SHA-256。
4. 必要时进行 UTF-8 解码、重新编码的往返校验。
5. 检查中文文件名和目录层级是否完整。
6. 检查换行、引号、JSON 结构和 Markdown 代码围栏是否完整。

必须检查以下编码损坏标志：

- 原中文位置出现 ASCII 问号替代；
- 出现 Unicode replacement character `U+FFFD`；
- 中文路径缺失、截断或变为乱码；
- 换行、引号或转义符异常；
- JSON 无法严格解析；
- Markdown 正文或代码块结构被破坏。

发现编码损坏必须立即停止，不得覆盖正式文件、Manifest、部署结果、数据或治理文档。

## 8. 环境问题的分类与停止原则

诊断结论必须明确区分：

- **环境问题**：路径、Shell、运行时、文件可见性或环境边界不满足；
- **代码问题**：在正确且完整的执行环境中，代码行为仍不符合预期；
- **数据问题**：输入缺失、格式错误、版本不符或校验失败；
- **权限问题**：现有身份没有完成任务所需的最小权限；
- **网络问题**：SSH、GitHub、依赖源或服务端点不可达或不稳定；
- **工具能力问题**：当前工具不能提供任务要求的操作或证据。

不得把环境缺失描述为代码失败，也不得为了让测试通过而降低安全标准、扩大权限、改变生产配置或绕过身份校验。

停止时应报告：失败类别、已经确认的事实、唯一缺失条件、该条件由谁提供，以及条件满足后应从哪个安全步骤继续。

## 9. 建议建立的固定工具

未来建议独立开发以下三个受 Git 管理的入口：

```text
本地开发环境预检工具
服务器只读性能与状态诊断工具
发布前 Git、镜像和容器身份核验工具
```

这些工具在正式加入仓库前必须分别完成需求定义、独立开发、测试、危险命令审查、编码验证和代码评审。工具必须有稳定的完成标记、明确退出码、超时预算和版本或 SHA-256 身份。

聊天附件中的一次性脚本不因成功执行一次就自动成为正式工具。本规范不授权移动、提交或部署现有 `server_readonly_diagnostic.sh`。
