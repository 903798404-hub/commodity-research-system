# 系统架构与项目边界

> 文档状态：当前权威文档。本文定义当前系统架构和项目边界，不定义具体发布命令。

## 1. 单仓库基线

`market-data` 是农产品研究系统唯一开发源、唯一 Git 根目录和唯一代码基线。GitHub 仓库 `commodity-research-system` 是正式版本记录中心。

本地 `main` checkout 是 clean `origin/main` 镜像，只用于只读审计和同步，不承担开发、
临时 merge、集成验收或 release。所有 feature、integration 和 release 工作使用属于同一
Git common dir 的独立 Git Worktree，避免共享可写源码工作区。Feature Worktree
不是新的仓库或代码基线，也不因独立 branch 自动获得部署或正式数据写入权限。

服务器只运行经过核验的 Git SHA 和镜像，不作为日常开发环境。服务器正式目录 `/home/ubuntu/market-data` 不得用于新版本 checkout、依赖安装、测试或镜像构建。

USDA 和 Oil World 保持独立应用结构，但属于同一 Git 仓库：

```text
11_独立应用/
├─ USDA平衡表/
└─ OilWorld平衡表/
```

不得建立嵌套 `.git`，不得重新建立与 `market-data` 同级的独立开发副本。

## 2. 顶层目录职责

| 目录 | 职责 | 主要生命周期 |
|---|---|---|
| `00_项目入口/` | 人工查看入口 | 随项目文档维护 |
| `01_data/` | 原始、人工、处理中、稳定和数据库数据 | 运行时持续变化 |
| `02_configs/` | 非敏感配置和应用登记 | Git 管理 |
| `03_src/` | 可复用核心业务代码 | Git 管理 |
| `04_scripts/` | 本地、数据和服务器执行入口 | Git 管理 |
| `05_apps/` | Streamlit 页面和应用入口 | Git 管理 |
| `06_outputs/` | 报告、图表、审计和推送结果 | 运行时持续变化 |
| `07_docs/` | 规范、契约、手册和历史归档 | Git 管理 |
| `08_tests/` | 自动测试和固定测试样例 | Git 管理 |
| `09_deploy/` | Docker、Compose、发布、回滚和服务器入口 | Git 管理 |
| `10_logs/` | 应用和更新任务日志 | 运行时持续变化 |
| `11_独立应用/` | 独立技术栈应用 | Git 管理；授权原始资料除外 |

不得重新创建 `data`、`scripts`、`output`、`logs`、`docs`、`deploy` 等旧版顶层目录。

## 3. 业务分层

系统采用四层业务结构：

1. 数据层：接入、校验、清洗和存储行情、基差、报告和研究数据。
2. Skill 层：实现 USDA、MPOB、报告解读、基差月差、持仓变化等可复用研究能力。
3. Agent/Pipeline 层：组合数据和 Skill，执行日报、事件分析、更新与预警。
4. 输出与应用层：提供 Streamlit、独立前端、Markdown、Excel、图表和推送结果。

核心位置：

- 通用包：`03_src/agri_research_agent/`
- 正式 Pipeline：`03_src/agri_research_agent/pipelines/`
- 执行入口：`04_scripts/`
- 页面：`05_apps/`
- Agent 结果：`06_outputs/`

### 3.1 公共架构模块边界

`03_src/agri_research_agent/` 当前已增加两个可供后续项目逐步采用的长期边界：

| 模块 | 当前职责 | 禁止承载 |
|---|---|---|
| `market_data/` | `Exchange`、`ContractId`、`ContinuousInstrumentId`、`MarketQuote`、Trading Calendar 协议、标准只读 loader 和 provider adapter 等市场数据语义 | 具体价差、榨利、持仓或页面业务公式 |
| `shared/` | `RuntimeContext`、`FileIdentity`、Atomic Storage 等跨业务技术 primitive | 价差公式、榨利公式、USDA/Oil World 规则、天气规则和其他业务判断 |

新增或迁移业务的目标依赖方向是：

```text
External / Manual Source
→ Provider
→ Pipeline
→ Standardized Data
→ Domain
→ App
```

这是后续项目采用 Architecture Foundation 时的目标方向，不表示当前所有旧模块、
历史数据链或页面已经完成迁移。价差、品种榨利、外盘持仓等后续项目可以优先复用
`market_data` 和 `shared`，但必须通过各自 Change Boundary 单独实施和验收。
USDA、Oil World 等已有稳定 bounded context 可以继续保留自身合理模式，不得为追求
形式统一而改写其已验证边界。

## 4. 运行链路

典型运行顺序为：

```text
01_data 输入
→ 02_configs 配置
→ 03_src 核心能力
→ 04_scripts 执行入口
→ 05_apps 页面或 11_独立应用
→ 06_outputs 结果
→ 10_logs 日志
```

该顺序说明职责关系，不意味着所有任务都必须写入每一层。

## 5. 正式应用和容器边界

正式应用登记以 `02_configs/app_catalog.yaml` 为事实来源。当前架构包含：

| 应用 | 代码归属 | 正式 Compose / project | 正式容器与端口 |
|---|---|---|---|
| 主工作台 | 仓库根、`05_apps/` | 根 `docker-compose.yml` / `market-data` | `spread-dashboard` / 8501 |
| USDA 平衡表 | `11_独立应用/USDA平衡表/` | `09_deploy/usda_release/compose.production.yml` / `market-data-usda` | `usda-dashboard` / 8080 |
| Oil World 平衡表 | `11_独立应用/OilWorld平衡表/` | `09_deploy/oil_world_release/compose.production.yml` / `market-data-oil-world` | `oil-world-dashboard` / 8081 |

默认只保留这三个正式运行容器。候选容器是一次性验收对象，证据密封后必须在生成 `deployment_plan` 前删除。一个服务的操作不得解析、启动、构建、重建或停止另外两个服务；不得在共享 Compose project 上使用 `--remove-orphans`，不得以 `docker compose down` 作为普通发布操作。

只有在依赖隔离、独立扩缩容或安全边界确有必要时才新增容器。进入主工作台的普通功能归属于 `spread-dashboard`，不得因单一页面或数据文件随意新增服务。

## 6. 应用独立性

- 只修改一个应用时，只测试、构建候选和部署该应用。
- 不得无必要重建或重启其他应用。
- USDA 和 Oil World 由主工作台提供入口，但运行时不互相启动。
- 外部应用地址通过环境变量提供；页面代码不得硬编码生产 IP。
- 应用缺少外部地址时必须降级显示，不能影响主工作台其他模块。

## 7. 代码、发布资产和运行内容

由 Git 管理：

- 源码、非敏感配置、测试、部署文件和长期文档；
- USDA 正式 `public/data/` 等经确认属于静态构建输入的发布资产；
- Oil World 源码、配置、发布代码和受控正式发布快照。

不由普通 Git 发布、部署时必须保护：

- `01_data/`
- `06_outputs/`
- `10_logs/`
- `.env` 和服务器环境文件
- Oil World 授权原始 Excel、HTML、PDF 和附属资料
- USDA 未获准提交的原始 CSV

“服务器只读部署”限制服务器对 GitHub 的写权限和代码来源，不代表运行数据目录不可写。

## 8. 中文与英文边界

采用“外层中文，底层英文”：

- 面向研究人员的页面标题、说明、报告名和人工查看文件可使用中文；
- Python 包、模块、类、函数、变量、import 路径和配置键保持英文；
- 标准数据字段名保持英文；
- 部署引用的工程路径保持稳定，不因展示需求随意改名；
- 中文路径进入跨环境流程时必须执行 UTF-8 和文件身份校验。

## 9. 架构变更原则

机器可读项目边界见 [Project Registry](../02_configs/project_registry.json)，不在本文维护第二份路径清单。
Soybean PM 的业务层包含 PM、AM/PM snapshot、CNF、profit materialization、history、UI 和专项tests，
但不拥有 Tankan/Weather/FULL DAILY/Wrapper/Preflight/Async/Public/shared。soybean-pm 当前为 ready，按可信 Registry 的 business ownership 开发；旧 PM worktree 仅作只读恢复来源。
Weather / Basis Push 是 Consumer / Notification 项目，仅负责 formatting、consumer、send adapter 和tests；
只读正式 Public/Consumer/Daily Summary，不自行 refresh 数据库。其专属路径证据未齐，登记为待补边界。
International Spread、Weather、Domestic Basis、USDA、Oil World 已按现有专属路径登记；
Palm 仅确认六核心配置，Canola 未确认独占代码，因此先登记并阻断未经审查的扩权。
Registry 的 owned 不是业务/生产操作授权；protected 与 shared dependencies 的修改另行分类。

涉及以下事项时，必须先形成项目契约并评审：

- 新应用或新容器；
- 顶层目录职责变化；
- 跨应用接口；
- 数据持久化位置变化；
- 正式端口、挂载、网络或环境变量变化；
- Git 管理边界变化；
- 数据更新和代码部署职责合并。

项目契约可以补充架构，但不得绕过 `AGENTS.md` 和标准开发发布规范。
