# 农产品研究系统更新手册 V1

> 本手册用于日常数据更新、定向部署、状态检查和故障止损。开发与部署原则见[《开发与部署工作流》](开发与部署工作流.md)，三个正式应用的唯一登记信息见[`02_configs/app_catalog.yaml`](../02_configs/app_catalog.yaml)。

## 1. 系统总览

正式链路只有一条：本地 `market-data` 是唯一开发源，GitHub 保存可追溯的正式版本，服务器只运行已核验的完整 Git revision。数据更新只改变业务数据；代码部署只改变已提交的代码和镜像，两者不得混为一次操作。

| 应用 | 用途 | 正式入口 | 容器 | 端口 |
|---|---|---|---|---:|
| 主工作台 | 价差、基差和一口价页面 | `http://124.222.106.25:8501/` | `spread-dashboard` | 8501 |
| USDA平衡表 | USDA PS&D 月度平衡表 | `http://124.222.106.25:8080/`，自动转到 `/usda/` | `usda-dashboard` | 8080 |
| Oil World平衡表 | Oil World季度看板和演示页 | `http://124.222.106.25:8081/oil-world/` | `oil-world-dashboard` | 8081 |

Oil World演示页：`http://124.222.106.25:8081/oil-world/presentation`。

遇到任何更新，先判断属于哪一类：

- 只追加基差Excel：执行“基差手动更新”，不部署代码。
- 价差当日数据缺失：执行“价差数据更新”，不部署代码。
- USDA或Oil World新报告期：先在本地生成和验证发布数据，再决定是否需要目标应用部署。
- 修改源码、配置、测试或前端：执行“代码修改与部署”。

## 2. 基差手动更新

### 2.1 本地追加并自检

- 在哪里：本地正式仓库。
- 文件：`01_data/manual/basis/国内现货基差.xlsx`。
- 操作：在现有工作表末尾追加数据并保存，不另建日期版母版。
- 生产影响：此时没有影响生产。

在仓库根目录记录本地文件哈希：

```powershell
Get-FileHash -Algorithm SHA256 -LiteralPath '01_data\manual\basis\国内现货基差.xlsx'
```

继续条件：Excel可正常打开，新行日期、品种、基差和一口价均正确。发现历史行被删除、历史值被修改、未知品种或关键空值时立即停止，不上传。

### 2.2 上传并核对

使用当前已配置的文件传输工具，把本地母版上传到：

```text
/home/ubuntu/market-data/01_data/incoming/basis/国内现货基差.xlsx
```

服务器项目目录：`/home/ubuntu/market-data`。上传后在服务器执行：

```bash
sha256sum '/home/ubuntu/market-data/01_data/incoming/basis/国内现货基差.xlsx'
```

继续条件：服务器哈希与本地 `Get-FileHash` 完全一致。哈希不同、文件不存在或大小异常时停止，不执行更新脚本。上传本身尚未改变正式Excel和Parquet。

### 2.3 执行更新

在服务器执行：

```bash
cd /home/ubuntu/market-data
docker exec spread-dashboard python /app/04_scripts/update_basis_data.py
```

成功时会看到：

```text
[OK] 基差 Excel、Parquet 和更新状态已完成一致性切换
当前总行数：...
本次新增：...
最新业务日期：YYYY-MM-DD
```

核对规则：总行数不得减少；本次新增数应等于本次Excel实际新增业务记录数；最新业务日期应等于Excel中的最新日期。重复上传同一Excel时新增数应为0。当前已验证基线为16481行、最新业务日期2026-07-03，后续正常追加后总行数和日期应向前变化。

出现 `[ERROR] 基差更新被拒绝` 时立即停止。脚本会保持旧正式文件不变并清理临时文件；不得手工修改或复制Parquet绕过校验。

### 2.4 页面验收

打开主工作台，分别进入“基差”和“一口价”页面。成功标准：页面非空、最新业务日期正确、新增记录可查询。再读取状态文件：

```bash
cat /home/ubuntu/market-data/01_data/update_status.json
test ! -e '/home/ubuntu/market-data/01_data/incoming/basis/国内现货基差.xlsx'
```

状态中的 `basis_update.status` 应为 `success`，上传入口应已清理。服务器不长期保存按日期命名的Excel或Parquet；用户自己的仓库外备份承担历史恢复。

## 3. 价差数据更新

### 3.1 当前自动任务

生产任务已确认在北京时间工作日周一至周五16:30运行：

```text
docker exec spread-dashboard python /app/04_scripts/server_update_spreads.py --update-from-akshare
```

它从AkShare更新 `historical_price_long.xlsx`，再生成价差Excel和Parquet，并更新 `01_data/update_status.json`。它不修改基差人工Excel或 `basis_quotes.parquet`。外资席位更新目前没有活动定时任务，不要按旧文档示例自行启用。

查看最近状态和日志：

```bash
cat /home/ubuntu/market-data/01_data/update_status.json
tail -n 100 /home/ubuntu/market-data/10_logs/cron_update_spreads.log
ls -lt /home/ubuntu/market-data/10_logs/server_update_spreads_*.log | head
```

成功标准：状态为 `success`，`latest_date` 是预期交易日，必需合约全部成功且失败数为0。若当天不是交易日，不要仅凭日期未变化判定失败，应先看状态和日志。

### 3.2 手动补跑

只在自动任务缺失且确认没有另一更新进程运行时，在服务器执行：

```bash
cd /home/ubuntu/market-data
docker exec spread-dashboard python /app/04_scripts/server_update_spreads.py --update-from-akshare
```

命令返回0并打印 `server_update_spreads completed` 后，再检查状态文件和日志。失败时脚本会尝试恢复更新前文件；看到合约失败、价格为空、锁冲突或校验错误时停止，不连续反复补跑，也不手工覆盖价差数据库。

## 4. USDA更新

### 4.1 准备数据

在本地进入：

```powershell
cd '11_独立应用\USDA平衡表'
```

在 `configs/usda_report_version.json` 设置 `currentReportMonth` 和 `previousReportMonth`。把当前月份唯一CSV放入 `data/raw/usda_psd/YYYY-MM/`；构建脚本在该目录不存在时才回退读取 `raw/`。原始CSV只读，不在Git提交中保存。

USDA API抓取脚本存在，但生产自动获取流程尚未确认。除非另行完成凭据、网络和数据范围验收，不要把 `pnpm run fetch:usda` 当作正式更新命令。

### 4.2 生成、检查和比较

在USDA目录执行：

```powershell
pnpm run build:data
pnpm run check:data
pnpm run compare:data
pnpm run test
```

成功标准：数据构建打印生成的matrix、商品和国家数量；`check:data`无fatal；比较命令生成或确认本月与上月差异；测试全部通过。任一步失败都停止，不修改正式服务器。

生成位置包括 `public/data/`、`data/snapshots/usda_psd/YYYY-MM/` 和前端快照。核对 `public/data/report_version.json` 的月份后再预览：

```powershell
pnpm run dev -- --host 127.0.0.1 --port 5173
```

打开 `http://127.0.0.1:5173/`。成功标准：默认页面和目标商品/国家可以打开，月份、单位、同比和月度修正符合本次报告。

### 4.3 数据更新还是代码更新

- 只替换原始数据并重新生成 `public/data/`、快照和月份配置，属于数据发布；只提交正式 `public/data/` 和必要配置，不提交原始CSV或本地 `data/raw`、`data/snapshots`。
- 修改 `src/`、`scripts/`、依赖、Dockerfile或Nginx配置，属于代码更新；同时运行对应测试和构建。
- USDA数据被打入静态镜像，因此即使只更新正式生成数据，生产也需要按新revision只重建 `usda-dashboard`。

本地提交后，在服务器按第6节检出明确revision，并只执行：

```bash
cd /home/ubuntu/market-data
docker compose build usda-dashboard
docker compose up -d --no-deps usda-dashboard
curl -f http://127.0.0.1:8080/usda/
```

成功标准：只替换USDA容器，curl成功，`http://124.222.106.25:8080/`可打开。失败时停止，不重建主工作台或Oil World。主工作台/USDA的标准化旧镜像标签和一条式回滚命令尚待确认；回滚前必须从本次部署记录取得上一可用镜像。

## 5. Oil World更新

### 5.1 放置季度原始资料

Oil World授权原始资料位于Git仓库外，按 `{raw_root}/YYYY-MM/` 保留原目录结构。路径只通过环境变量 `OILWORLD_RAW_DATA_ROOT` 或不进入Git的 `02_configs/local_paths.json` 设置；不得把本机绝对路径写入Git文件。

在本地进入：

```powershell
cd '11_独立应用\OilWorld平衡表'
$env:OILWORLD_RAW_DATA_ROOT = 'D:\OilWorld'
```

把新季度唯一主Excel及配套原始资料放入 `$env:OILWORLD_RAW_DATA_ROOT\YYYY-MM\`。主Excel文件名必须包含英文月份和年份，例如 `Oil World-September 2026.xlsx`。目录内有0个或多个主Excel时停止。

### 5.2 预演和正式生成

以2026年9月为例，在Oil World目录执行：

```powershell
..\..\.venv\Scripts\python.exe 04_scripts\update_oil_world.py --release 2026-09 --validate-only
..\..\.venv\Scripts\python.exe 04_scripts\update_oil_world.py --release 2026-09
```

第一条只验证，不写正式目录或指针。只有预演通过后才执行第二条。成功标准：报告中的 `validate_only`、release、source hash、mapping和comparison检查符合预期；正式执行后新release不可变安装，`latest.json`最后更新。

检查发布和相邻比较：

```powershell
Get-Content public\data\oil_world\latest.json
Get-Content public\data\oil_world\releases.json
Get-ChildItem public\data\oil_world\comparisons
```

`latest.json`应指向新季度，`releases.json`应包含新release，`comparisons/{previous}_to_{current}/`应存在。发布期已存在、普通发布不晚于latest、映射冲突或引用缺失时停止，不覆盖旧release。

### 5.3 定向测试和本地预览


特别门禁：Brazil / Soybeans 与 Argentina / Sunflowerseed 是Jan–Dec自然年口径，不能与作物年度序列交叉比较；遇到审计冲突应保持不展示，不能为了填满表格改用另一时间轴数值。

## 6. 代码修改与部署

### 6.1 本地开发和提交

在本地仓库根目录执行：

```powershell
git status --short
git branch --show-current
git diff
```

只修改本次任务文件，运行与变更直接相关的定向测试，然后执行：

```powershell
git diff --check
git add -- path/to/file1 path/to/file2
git diff --cached --name-only
git commit -m '准确描述本次修改'
git push origin main
git rev-parse HEAD
```

禁止使用 `git add .` 或 `git add -A`。暂存区出现运行数据、原始资料、日志、缓存、凭据或无关文件时停止提交。

### 6.2 服务器按revision部署

部署前记录完整提交SHA和目标应用。在服务器执行：

```bash
cd /home/ubuntu/market-data
git status --short
git fetch origin main
REVISION='填写完整提交SHA'
git cat-file -e "${REVISION}^{commit}"
```

`git status --short`有无法解释的输出时停止。确认提交存在后，按现有正式部署流程检出并核验：

```bash
git checkout --detach "$REVISION"
test "$(git rev-parse HEAD)" = "$REVISION"
```

然后只构建目标服务：

```bash
# 主工作台
docker compose build spread-dashboard
docker compose up -d --no-deps spread-dashboard

# USDA
docker compose build usda-dashboard
docker compose up -d --no-deps usda-dashboard
```

Oil World使用第5节的独立Compose命令。成功标准：只有目标容器的镜像和启动时间变化，目标URL、数据和日志正常；其他两个容器不变。失败时按第9节回滚并停止。

## 8. 常见故障的最短处理

| 故障 | 最短排查路径 | 停止条件 |
|---|---|---|
| 网页打不开 | 查 `docker ps`、端口、目标容器最近100行日志，再用服务器本机curl | 容器退出、端口未监听或日志有启动错误时停止部署 |
| 容器不断重启 | 查 `docker inspect` 的状态与重启次数、查日志 | 不反复手工restart，直接准备回滚 |
| 基差更新被拒绝 | 读取终端错误，检查Excel是否删历史、改历史值、损坏或有未知品种 | 不手工修改Parquet，不绕过校验 |
| 上传文件没有生效 | 比较本地和incoming SHA-256，确认运行的是固定命令 | 哈希不同或incoming不存在时重新上传，不执行脚本 |
| 数据为空 | 检查状态JSON、正式数据文件是否存在且非0字节、页面日志 | 不用样例或旧文件覆盖正式数据 |
| 服务器磁盘不足 | 运行 `df -h` 和 `docker system df`，只记录占用 | 不执行prune；进入单独清理任务 |
| Git工作区不干净 | 运行 `git status --short` 和 `git diff`，识别来源 | 不reset、restore或clean；无法解释就停止部署 |
| 新镜像启动失败 | 保留失败日志和镜像，确认旧镜像仍在 | 不继续更新其他容器，立即回滚目标应用 |

## 9. 回滚

代码回滚与数据回滚是两件事：

- 基差更新失败：脚本在原子切换前拒绝，旧Excel、Parquet和状态保持不变；用户不需要手工恢复。
- 价差更新失败：脚本会尝试恢复本次运行前的数据；先看状态和日志，不立即手工复制备份。
- 代码部署失败：使用本次部署前记录的上一可用revision镜像，只恢复目标容器；不要重建其他应用。
- Oil World数据失败：先恢复匹配的 `releases.json`，最后恢复 `latest.json`；不删除新release和comparison目录。

主工作台和USDA当前Compose尚未统一可直接填写的旧镜像变量，精确回滚命令待下一次部署基线标准化确认。没有上一镜像ID、完整revision和网页恢复验证计划时，不执行临时猜测命令。

## 10. 文件保留与清理

- Git只保留源码、配置、测试和必要文档；经确认属于静态应用构建输入的正式发布JSON作为受控发布资产管理。Git不保存运行日志、缓存、凭据或授权原始资料。
- Oil World原始资料位于仓库外；不得删除唯一原始资料或用户外部备份。
- 服务器保留当前生产数据、当前镜像和一个已验证回滚镜像；Oil World还必须保留 `releases.json` 引用的release和comparison。
- 可重新生成的缓存、临时文件和已确认无运行引用的中间文件可以在单独清理任务中删除。
- 删除前必须确认容器挂载、页面引用、定时任务、恢复来源和目标路径。
- 日志以后采用固定保留期限；具体天数待确认，在确认前不批量删除。
- 外部审计目录在基线稳定、结论已进入正式文档且确认无恢复用途后可以清理。
- 不使用 `docker system prune`、`docker image prune -a` 或未经清单确认的递归删除命令。
