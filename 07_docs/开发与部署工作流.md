# 开发与部署工作流

> 本文只定义开发、版本和部署原则。日常更新与故障处理命令见[《农产品研究系统更新手册》](农产品研究系统更新手册.md)。

## 1. 一句话原则

农产品研究系统只有一条正式代码链路：在本地 `market-data` 单仓库开发，通过 GitHub 保存正式版本，再由服务器使用只读权限取得指定版本并运行。

```text
本地修改
→ 本地测试
→ Git commit
→ Git push
→ 服务器只读获取精确提交
→ 候选镜像构建与验证
→ 正式容器切换
→ 保留回滚版本
```

## 2. 当前项目结构

```text
market-data/
├─ 01_data/                  运行数据
├─ 02_configs/               农产品看板配置
├─ 03_src/                   核心代码
├─ 04_scripts/               维护和数据处理脚本
├─ 05_apps/                  Streamlit 应用入口
├─ 06_outputs/               正式生成结果
├─ 07_docs/                  长期文档
├─ 08_tests/                 测试
├─ 09_deploy/                部署文件
├─ 10_logs/                  运行日志
└─ 11_独立应用/
   ├─ USDA平衡表/            USDA Vite/React 前端及其正式 public/data
   └─ OilWorld平衡表/        Oil World 独立前端、发布脚本及正式快照
```

整个 `market-data` 是唯一 Git 根仓库。USDA 和 Oil World 保留独立应用结构，但都属于同一个仓库，不建立嵌套 Git 仓库，也不维护同级的独立开发副本。

## 3. 什么是本地开发基线

“本地开发基线”是指：本地 `market-data` 中的代码、配置、测试和部署文件是所有修改的起点，也是判断哪个版本正确的第一依据。

新功能和一般修复必须先在本地完成，并通过对应测试。服务器不是日常编辑代码的地方，不能因为线上目录看起来更新，就把服务器目录当作新的开发源。

这样做可以避免本地、GitHub 和服务器各自出现一套不同代码，最终无法判断应该保留哪一份。

## 4. 什么是 GitHub 单仓库

GitHub 的 `commodity-research-system` 仓库是唯一正式版本记录中心。一次可部署修改必须对应一个明确的 Git 提交哈希。

GitHub 负责保存：

- 源代码、配置、测试和维护脚本；
- Dockerfile、Compose 和其他部署文件；
- 长期项目文档；
- USDA 前端源码及其正式 `public/data/`。

GitHub 不负责保存服务器持续变化的运行数据、日志、环境密钥和自动生成输出。

## 5. 什么是服务器只读部署

服务器通过受控的只读方式取得正式代码，不得从服务器向 GitHub push。无论使用只读 Git 凭据还是经验证的提交包，都必须对应并核验一个完整提交 SHA。

部署时必须指定并核验一个完整提交哈希，例如 `<提交哈希>`。不能以“某个 latest 文件夹”或来源不明的压缩包作为正式版本，也不能直接用整文件夹覆盖正在运行的项目。

“只读”限制的是服务器对 GitHub 仓库的权限，不是限制服务器磁盘上的所有文件。应用运行时仍然需要写入数据、输出和日志。

## 6. 代码与运行数据的区别

代码回答“系统如何运行”，运行数据回答“系统当前处理了什么”。两者的生命周期不同。

### 由 Git 管理

- `02_configs/`、`03_src/`、`04_scripts/`、`05_apps/`；
- `07_docs/`、`08_tests/`、`09_deploy/`；
- 根目录依赖、测试、Docker 和 Compose 配置；
- `11_独立应用/USDA平衡表/` 中的源码、配置、测试、部署文件和 `public/data/`。
- `11_独立应用/OilWorld平衡表/` 中的源码、配置、测试、部署文件和正式发布快照。

### 不由 Git 发布、部署时必须保护

- `01_data/`：服务器正式运行数据和人工维护数据；
- `06_outputs/`：应用生成的正式结果；
- `10_logs/`：更新任务和应用运行日志；
- `.env`：服务器地址、环境参数和可能的敏感配置。
- Oil World 授权原始 Excel、HTML、PDF 和附属介质：保存在 Git 仓库外，由 `OILWORLD_RAW_DATA_ROOT` 或本机忽略配置定位。

这些运行内容可以持续写入。服务器取得新代码时，应复制、挂载或原样保留它们，不能因 Git 中没有这些文件就认为它们可以删除。

本地可以存在用于开发和验证的数据，但这些目录内容仍不应被普通 Git 提交带入正式版本。

## 7. 新增功能的完整流程

1. 在本地正式 `market-data` 仓库修改代码或配置。
2. 日常修改运行与变更直接相关的定向测试；部署、清理、固定基线和跨应用接口等关键节点再运行对应完整回归。
3. 查看 Git diff，确认没有 `.env`、运行数据、日志、缓存或密钥进入提交。
4. 创建 Git commit，并 push 到 GitHub 正式分支。
5. 部署前备份服务器当前代码目录，记录当前容器、镜像和 Compose 状态，并给当前镜像添加回滚标签。
6. 在新的服务器暂存目录中，以受控只读方式取得代码并检出、核验精确提交。
7. 将受保护的 `01_data/`、`06_outputs/`、`10_logs/` 和 `.env` 复制或挂载到暂存版本，核对文件数、大小和路径。
8. 顺序构建新镜像。先在临时端口启动候选容器，验证 HTTP、页面、数据接口、日志和环境变量。
9. 候选验证全部通过后，再短暂停止正式容器，以原子目录切换方式启用新版本。
10. 验证正式容器、端口、页面、Git 提交、数据挂载和定时任务。
11. 短期保留旧项目目录、旧镜像、回滚标签和部署记录，稳定观察后再决定是否清理。

只修改一个服务时，只构建和替换该服务，不无必要地重建或重启另一个服务。

## 8. 线上紧急修复后的回流流程

原则上不直接修改服务器正式源码。只有明确的紧急线上故障允许临时修复，且修复完成不代表流程结束。

紧急修复后必须立即：

1. 记录服务器实际修改的文件和原因；
2. 将同样的修改同步回本地正式仓库，而不是把整个服务器目录下载覆盖本地；
3. 比较文件内容、Git diff 和必要的哈希，处理可能的版本分叉；
4. 在本地运行故障相关定向测试，并在重新部署前运行对应完整回归；
5. commit 并 push 到 GitHub；
6. 服务器重新以受控只读方式取得这个正式提交；
7. 按候选验证和正式切换流程重新部署。

在紧急修改尚未回流为正式 Git 提交前，不应继续开发下一项功能，否则服务器修复很容易在下一次部署中丢失。

## 9. 数据更新与独立应用边界

数据更新和代码部署分别执行。基差数据由用户在本地当前《国内现货基差.xlsx》中追加，上传到服务器 `/home/ubuntu/market-data/01_data/incoming/basis/国内现货基差.xlsx` 后运行 `docker exec spread-dashboard python /app/04_scripts/update_basis_data.py`。脚本校验历史记录、生成当前 Parquet 并原子替换数据文件；这一流程不替换代码。代码部署也不得顺带覆盖基差 Excel、Parquet 或状态文件。

USDA 和 Oil World 是独立应用：只修改其中一个应用时，只运行该应用的定向测试并只部署对应服务。Oil World 原始资料通过统一外部根目录读取，不进入普通 Git 提交；正式发布快照仍按既有项目规则受控。

## 10. 如何确认线上运行版本

首先在服务器正式项目目录读取 Git 提交：

```bash
git -C /home/ubuntu/market-data rev-parse HEAD
git -C /home/ubuntu/market-data status --short
```

第一条给出线上目录对应的完整提交哈希；第二条正常情况下应没有输出。部署报告还应记录正式容器使用的镜像 ID，并将它与本次构建记录对应起来。

仅看到容器名称或文件修改时间，不能证明线上运行的是哪个版本。应同时核对 Git 提交、镜像 ID、Compose 配置和容器状态。

## 11. 为什么不再整文件夹覆盖

整文件夹覆盖无法可靠区分代码与运行数据，容易造成以下问题：

- 把服务器最新数据覆盖成旧数据；
- 覆盖服务器 `.env`，导致地址或密钥失效；
- 把本地缓存、虚拟环境或构建产物带到服务器；
- 丢失服务器紧急修复，或把服务器临时文件带回本地；
- 无法确认最终内容对应哪个 Git 提交。

因此部署只以正式 Git 提交为代码来源，并单独保护运行目录。发生版本分叉时，必须逐文件比较和合并，禁止双向整目录覆盖。

## 12. 失败时如何回滚

正式切换前必须保留三类回滚资源：旧项目目录、旧镜像或回滚标签、部署前的容器和 Compose 检查记录。

如果新版本正式验证失败：

1. 停止失败的新容器，但保留失败版本目录和日志用于排查；
2. 把旧项目目录恢复为正式路径；
3. 将旧镜像或 `rollback-<时间戳>` 标签恢复为正式镜像；
4. 使用旧 Compose 配置启动服务，不重新构建；
5. 验证关键 HTTP 地址、数据挂载、环境变量和定时任务；
6. 确认旧服务恢复后，再在本地修复问题并重新走正式流程。

回滚过程中禁止删除 `01_data/`、`06_outputs/`、`10_logs/`、`.env`、唯一有效备份或故障日志。

## 13. 权限与职责总结

| 位置 | 主要职责 | 是否可直接开发 | 是否可持续写入运行内容 |
|---|---|---:|---:|
| 本地 `market-data` | 唯一开发基线 | 是 | 可使用本地测试数据 |
| GitHub 单仓库 | 唯一正式版本记录中心 | 通过本地 push 更新 | 否 |
| 服务器正式目录 | 运行已确认的 Git 提交 | 原则上否 | 是，限运行数据、输出、日志和环境配置 |

服务器只读取代码、按精确提交部署和运行目录可写三者并不冲突：代码来源可追溯，生产运行状态则被单独保护并允许正常更新。
