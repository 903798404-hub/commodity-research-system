# 文档索引与适用范围

> 文档状态：当前权威文档。本文件是 `07_docs/` 的唯一当前入口；旧原文已归入 `archive/legacy-sources/`，不得作为当前执行依据。

## 1. 目的

本文件是 `07_docs/` 的统一入口，用于回答：

- 当前任务最少需要读取哪些文档；
- 各文档负责定义什么，不负责定义什么；
- 多份文档出现冲突时采用什么优先级；
- 项目契约、检查清单和历史归档能否覆盖通用规则；
- 旧文件在兼容期内应如何理解。

`07_docs/` 只保存长期规则、项目契约、操作说明和历史事实，不保存业务数据、密钥或可执行代码。

## 2. 规则优先级

当前规则优先级固定为：

1. 根目录 `AGENTS.md`。
2. 用户明确批准的当前任务范围或当前项目专项契约。
3. `03_标准开发与生产发布规范.md`。
执行辅助：`04_开发与发布检查清单.md`、`06_日常运行与数据更新手册.md` 与模板。
历史归档不参与规则优先级：ARCHIVED / NOT AUTHORITATIVE / DO NOT EXECUTE。

`01_系统架构与项目边界.md`、`02_数据与输出规范.md` 和
`05_执行环境与跨环境传输规范.md` 分别是其主题的当前权威文件；适用任务必须
读取并遵守。它们不改变上述发布规则优先级，也不得被项目契约放宽。

适用原则：

- 下级文件不得放宽上级文件的数据、凭据、生产、回滚或破坏性操作保护。
- 项目契约可以增加更严格要求，或在通用规范明确允许时定义应用差异；不得隐式修改通用发布标准。
- 检查清单只负责逐项执行，不能创造、删除或覆盖规范正文中的规则。
- 检查清单与规范不一致时必须停止，由用户或文档维护者修正规则，不得自行选择较宽松版本。
- `archive/` 中的文件只用于事实追溯、事故复盘和恢复证据，不得作为当前操作命令来源。

## 4. 新项目文档闸门

执行时先使用 `04` 第 1 节选择流程，再按 8 个阶段检查适用项。普通开发截止于第 3 节；数据更新转 `02` / `06`；已授权的生产任务才进入第 4–7 节。任务单和治理审查卡引用 `03`，无需复制治理全文。CI 触发与镜像/生命周期分流的统一规则见 `03` 的“CI 触发与验证深度”。

开始任何新项目、新模块、现有模块重大扩展或新的自动更新链开发前，必须先完成
以下文档判断，再决定新增或修改文档的位置：

1. 读取根目录 `AGENTS.md` 和本文件。
2. 在 `projects/` 中查找并读取与任务对应的项目契约。
3. 已有相关契约时优先更新原契约，不得另建同义的“说明”“手册”“流程”、
   “指南”“新版规范”或“最终规范”。
4. 尚无对应契约时，只允许在 `projects/` 新增一份名称明确的项目契约，并在
   下节项目专项契约表中同步登记。

文档内容按性质落位：

| 内容类型 | 唯一落位 | 修改门槛 |
|---|---|---|
| 影响整个仓库且预计长期有效的最高级强制规则 | 根目录 `AGENTS.md` | 普通业务项目不得修改 |
| 影响全部项目的长期通用制度 | 对应的 01–06 权威文档 | 单个项目的特殊需要不得修改通用制度 |
| 具体项目长期有效的业务、数据、页面和运行规则 | `projects/<项目契约>.md` | 优先更新已有契约；不得创建同义文件 |
| 单次发布事实、事故、历史实例、具体 SHA、镜像、容器、IP、日期和复盘 | `archive/` | 必须标明历史状态；不得作为当前执行依据，使用前重新核验 |

不得在 `07_docs/` 根目录新增 00–06 以外的 Markdown 文档。

## 6. 历史归档

[`archive/`](archive/) 保存：

- 单次项目说明；
- 事故、失败过程和修复经验；
- 已被替代但仍有复盘价值的规则；
- Git SHA、Tree SHA、容器 ID、镜像 ID、部署时间和生产基线路径；
- 旧版目录、输出和操作约定。

历史事实保留；无运行引用、无独立历史价值的重复治理说明允许经引用审计删除，通过 Git 历史恢复。历史文件应明确标注适用时间、替代文档和“不得作为当前执行依据”。

- `archive/2026-07-历史运行实例与业务基线.md`：2026 年 7 月公网入口、端口、
  数据日期、行数、任务时间、cron 状态和 `partial_failure` 记录；所有实例值
  均须重新只读核验，不得直接复用。

## 9. 开发治理最小入口

根 AGENTS 是最高规则，本文只导航；项目路径和状态读取
[Project Registry](../02_configs/project_registry.json)，启动/Scope 命令以 `03` 为准，
执行勾选用 `04`，只复制新功能模板。`01` 解释边界；`02/05/06` 按任务读取，不复制一套项目规则。
Registry 的 shared_dependencies 和状态只提供维护与影响范围信息；修改相关源码需明确任务 Scope 和测试，不由 metadata 授权。
普通 business 默认 `--project`，缺失 Registry 不阻止项目启动；历史聊天 SHA 不覆盖 fresh remote。

当前生产 FULL DAILY 已采用 Approved control-plane/tool-repo 和 Provider UTF-8 machine evidence，
详见 [正式入口](../04_scripts/automation/说明.md)，不要求开发 caller 是 clean main。
Prewarm Separation 尚未正式闭包；soybean-pm 已解除 Registry 冻结、状态 ready；旧 FULL DAILY 仍冻结，不将其设计当作已上线功能。

仅需复盘时读取：`archive/2026-09-04-AsyncContractRollout候选记录.md`、
`archive/2026-09-04-Missing非阻断候选记录.md`；它们记录历史候选阶段，不是当前执行模板。
