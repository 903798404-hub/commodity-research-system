## Mainstream Development Governance

统一流程：`main → feature/fix branch → implementation → automated tests → required CI → main`。
Repository Maintainer/Admin 审查并接纳 Governance / CI candidate；review 是 integration decision，不是 CI failure。Worktree 仅用于并行开发；可用 START / RESUME 自动 fetch 并建立工作区，也可直接建立 feature/fix branch，不存在项目存在审批。

Registry 是 project/module metadata、ownership documentation、test mapping、impact analysis、runtime target 和维护责任登记，不是普通源码修改的 hard authorization。无 owner 不阻止合法项目启动；同一个明确的 Governance / CI candidate 可以原子修改 Registry、owner、test mapping、Admission、workflow、相关实现、测试和文档。不得借 metadata 偷偷扩大无关模块 Scope、减少 required tests 或取得生产权限。

Business 运行 scoped required tests；Shared / Infra 增加 impact/consumer tests，未映射 shared source 使用更广回归；Governance / CI 运行 governance regression 和相关平台 CI，并记录 `CHANGE_CLASS = GOVERNANCE_OR_CI`、`MAINTAINER_REVIEW_REQUIRED = YES`。技术验证 PASS 时 `trusted-main-admission-v1` PASS；failing tests、Scope violation、required test deletion、Registry 减测和未授权 production mutation 始终 FAIL，review 不能覆盖失败。

required plan 保留 base required/future/impact obligations，并 UNION candidate 新增/修改测试及 candidate 新增 mapping。candidate tree 中的测试版本必须真正执行，collection 非空，失败和 skip 均不得记为 PASS。Windows-specific required tests 使用 `windows-2022`；跨平台测试使用 Linux。最终 required check 聚合同一 base / candidate Commit/Tree、plan 和 workflow run/attempt 的实际平台 job；缺少必需平台结果即 FAIL。没有 Windows dependency 的 Business 不启动 Windows suite。

候选 workflow 是 Maintainer review 的信任对象；不承诺防御恶意 Maintainer 修改自己的 CI。一个 candidate 完成相关实现和 CI，无须先安装 owner 或 executor、无须分阶段 main transition。没有 candidate approval server、审批 token 或额外 GitHub App。

main Ruleset 保持 Active、required check `trusted-main-admission-v1`、non-fast-forward/deletion protection；不使用 bypass 作为正常开发路径，不修改 GitHub settings。提交前检查 diff/scope/tests；只显式 git add 文件。任何新 commit 都重新取得 exact hosted evidence。取得测试 PASS 后，main 接纳仍按任务授权，由 Maintainer 决定；本地 main 保持 clean 镜像，接纳只用普通 fast-forward，不 force、rebase、squash 或额外 merge commit。

`PROJECT_EXISTENCE_APPROVAL_REQUIRED = NO`；`ORDINARY_BUSINESS_NEEDS_HUMAN_APPROVAL = NO`；`REGISTRY_IS_HARD_AUTHORIZATION = NO`；`STAGED_GOVERNANCE_MIGRATION_REQUIRED = NO`。

`main != production`。生产单独授权；Approved identity、Commit/Tree/Image、Manifest、release gate、rollback、candidate 不写 production 均保留。Registry ownership、CI PASS 和进入 main 不授予 server deployment、production data mutation、FULL DAILY 或 runtime grant 权限。Production Release 合同独立执行。

## 1. 手册用途与阅读顺序

- **目标**：把任务分类为本地开发、数据更新、候选、正式发布、回滚或只读审计。
- **输入**：用户授权、任务范围、当前项目契约和文档索引。
- **入口与关键检查**：确认本手册适用；数据任务同时读 `02`、`06`，生产操作读 `03`、目标发布工具和密封产物。
- **输出**：记录所读文档、阶段和授权边界。
- **停止**：任务类型、授权或项目契约不明确。
- **禁止**：把 archive、旧报告或聊天摘要当作当前操作依据。

## 2. 系统与服务架构

- **目标**：确认只操作目标应用。Spread 使用根 `docker-compose.yml`、容器 `spread-dashboard`、端口 8501；USDA 使用 `09_deploy/usda_release/compose.production.yml`、project `market-data-usda`、容器 `usda-dashboard`、端口 8080；Oil World 使用 `09_deploy/oil_world_release/compose.production.yml`、独立 project、容器 `oil-world-dashboard`、端口 8081。

## 10. 服务器发布前基线

Routine 分流：先按规范14.4执行现有 risk classifier。只有 `ROUTINE_STATELESS` 使用
`routine_release.py build → validate → deploy`；本手册14–17章的多级 Manifest/签名密封链
仅用于 high-risk/原发布工具，不作为 routine 的额外 Gate。Routine 核对：exact main CI、
build once、同一 Image ID、fresh candidate/production grants、readonly data、真实浏览器
DOM smoke、plain acceptance/deployment JSON、失败恢复 previous image。cleanup 不依赖
复杂 seal transaction；无 rollback rehearsal、无旧 grant 续期。准备具体实例 Compose/env/
policy/template 和 rollback source，校验 Playwright Chromium 可用，生产仍独立批准。

- **目标**：在任何候选前封存正式服务、数据和空间的只读事实。
- **输入**：用户批准的服务器访问、目标服务、正式 Compose/env 路径和当前部署结果。
- **入口与关键检查**：记录容器/Image ID/RestartCount/端口/挂载、HTTP、数据 Manifest、磁盘、Build Cache、当前与回滚镜像和正式仓库状态。
- **输出**：带时间戳的基线或审计证据，不复制业务数据或密钥。
- **停止**：正式服务异常、容器身份不明、数据哈希异常、Cron 风险窗口或工作区不干净。
- **禁止**：在基线阶段构建、重启、删除、修改 Compose/env/Cron 或运行数据。

正式 release preflight 必须执行规范 14.1–14.3 的风险分类与资产评估：分别记录
ROLLBACK_ASSETS_READY、EXECUTION_AUTHORIZATION、ROLLBACK_REHEARSAL_REQUIRED 和
IRREVERSIBLE_STATE_CHANGE。保留当前及上一正式版本资产；历史 grant 过期不单独阻止
ROUTINE_STATELESS；STATEFUL_OR_INFRA 必须有真实恢复验证。分类输出不等于发布批准。

## 11. 可信源码获取

- **目标**：从 GitHub 取得唯一、完整、可验证的候选构建上下文。
- **输入**：完整目标 SHA、Deploy Key、固定 SSH 包装脚本和唯一隔离目录。
- **入口与关键检查**：`ls-remote` 核验远程 SHA；全新只读浅克隆后 detached checkout，核对 HEAD、Tree、clean 和 `git fsck --connectivity-only`。
- **输出**：带命令、退出码、Commit/Tree 的可信检出记录。
- **停止**：浅克隆失败、对象错误重复出现、Tree 不一致、目录不干净或来源混合。
- **禁止**：在 `/home/ubuntu/market-data` checkout/安装/测试/构建；使用 worktree、旧迁移目录或不完整 clone 构建。

## 12. 候选镜像构建

- **目标**：从可信检出构建带完整身份的不可变候选镜像。
- **输入**：可信 Git/Tree、目标 Dockerfile、版本化 release ID、回滚对象和构建上下文。
- **入口与关键检查**：使用目标应用正式发布工具；候选标签不使用 `latest`/`new`，OCI revision=完整 Git SHA，记录完整 Image ID、Tree、构建输出和 inspect。
- **输出**：已构建镜像、release bundle/Manifest 或明确失败证据。
- **停止**：镜像身份、构建上下文、OCI、Release 或回滚对象缺失/不一致。
- **禁止**：覆盖正式/回滚标签、在正式仓库构建、把数据或 env 烘焙进镜像。

## 13. 候选容器验证

- **目标**：隔离验证目标服务而不影响正式三个容器。
- **输入**：候选 Image ID、release bundle、独立 Compose、正式数据只读视图和本机空闲端口。
- **入口与关键检查**：候选必须独立 project/容器名、只绑定 `127.0.0.1`、`restart=no`；用正式 readiness/validate 工具轮询 HTTP、日志、页面、inspect Git/Tree/Image 和数据不变性。
- **输出**：有限脱敏日志摘要、HTTP/页面/身份/旁路容器零变化证据。
- **停止**：端口公网暴露、重启、身份不一致、挂载可写、正式容器或数据改变。
- **禁止**：固定 sleep 代替就绪轮询、启动/重建 USDA 或 Oil World、候选占用正式端口。

## 14. candidate_result

- **目标**：只在候选仍存在且所有验收通过后密封候选事实。
- **输入**：已验证 release、readiness 结果、候选 inspect、候选启动前正式容器快照和 checks 文件。
- **入口与关键检查**：使用 `create_candidate_result.py`；Schema 和 Manifest 必须通过，运行时 Git SHA 必须由 inspect 实测，非人工输入。
- **输出**：不可覆盖的 `candidate_result.json` 与 `candidate_result.manifest.json`。
- **停止**：快照晚于候选启动、候选不存在、Schema/Manifest/身份失败或证据不完整。
- **禁止**：手写 JSON、补造快照、把计划值或正式仓库 HEAD 冒充运行身份。

## 15. deployment_plan

- **目标**：在候选容器已真实删除后密封唯一、非敏感的正式切换和回滚计划。
- **输入**：已验证 release、candidate_result、当前生产 Compose/env/容器/数据基线和候选 Image ID。
- **入口与关键检查**：确认候选容器不存在但候选镜像仍存在；用 `create_deployment_plan.py` 只读生成并验证 Manifest，锁定服务、project、绝对 Compose、项目目录、`current_production`、`target_release`、`deployment_tool_revision`、目标/回滚 Image ID 和 argv。A 与 B 不同是正常升级状态。
- **输出**：`deployment_plan.json`、Manifest、预演和基线对比。
- **停止**：候选容器未删、计划要求预先改生产 env/Compose、身份链不一致或回滚不明确。
- **禁止**：手写 plan、密封后 amendment 改核心 argv、用相对路径或当前目录猜测生产路径。

## 16. 正式部署

- **目标**：在用户批准后只切换计划目标服务，并复用候选的同一 Image ID。
- **输入**：用户批准、已验证 release/candidate_result/plan 及其 Manifest、可信工具检出。
- **入口与关键检查**：发布工具先确认实际 env、Compose 和容器仍等于密封基线，再原子切换 env 并从计划读取执行参数；实际 Compose argv 必须包含 `--no-build --pull never --no-deps --force-recreate`，且只针对目标服务。
- **输出**：目标服务切换记录和部署后事实。
- **停止**：未获批准、候选 Image ID 不同、旁路服务变化、就绪失败或回滚条件触发。
- **禁止**：重新构建正式镜像、`up --build`、`compose down`、prune、切换未在计划中的服务。

## 17. deployment_result

- **目标**：把正式部署完成事实密封为不可覆盖结果。
- **输入**：计划、正式容器 inspect、HTTP/页面/数据/旁路服务回归和实际运行时 Git SHA。
- **入口与关键检查**：由正式生成器写入 `deployment_result.json`、Manifest 和 bundle Manifest；计划目标、实际 Image ID、OCI、Git、Tree、数据和 HTTP 必须一致。
- **输出**：完整部署结果链。
- **停止**：任一结果/Manifest 缺失、运行时身份空或冲突、数据/其他服务变化。
- **禁止**：以容器名、标签、GitHub main 或人工描述代替结果链；缺少结果仍宣称发布完成。

## 18. 正式回归

- **目标**：证明目标服务已恢复、其他服务和运行数据未变化。
- **输入**：部署前基线、正式容器、端口、HTTP、数据 Manifest 和部署结果。
- **入口与关键检查**：核验实际 Image ID、RestartCount、健康/HTTP、页面、挂载、数据和三服务身份；无 healthcheck 的服务必须结合 HTTP 和日志。
- **输出**：部署结果中的回归结论和差异摘要。
- **停止**：目标不可用、非目标服务变化、数据哈希变更或观察到回归。
- **禁止**：用一次容器状态检查替代完整身份与业务回归。

## 19. 回滚

- **目标**：使用计划中已验证的上一 Git、Image、Compose/env 基线恢复目标服务。
- **输入**：密封计划、回滚 Image ID、前基线、回滚入口和用户批准。
- **入口与关键检查**：按密封步骤用既有精确回滚镜像创建 fresh instance，完成创建态验证、签发新 grant 后启动；重新核验 Image/Git/Tree/consumer/HTTP/数据。不得复用已停止实例的历史 grant。
- **输出**：回滚结果与新的部署结果事实。
- **停止**：唯一回滚对象不存在、数据恢复边界不明、计划未密封或旁路服务异常。
- **禁止**：重新构建、用 `latest` 猜旧版、删除失败证据或把代码回滚误作数据回滚。

## 20. 候选与失败资产清理

- **目标**：在证据链完成后仅清理明确、可恢复、已获批准的候选运行实体。
- **输入**：结果链、生产稳定证据、候选容器/镜像/data 清单和单独清理授权。
- **入口与关键检查**：候选容器必须在 plan 前删除；之后逐项核验当前正式、唯一回滚、数据、Manifest、失败证据和引用。
- **输出**：清理计划、完整 ID/路径、前后空间和零变化验证。
- **停止**：对象仍被容器/计划/结果引用、证据未密封或恢复能力不清楚。
- **禁止**：通配符删除、删除唯一回滚、自动删除 `candidate-data`、删除父目录。

## 21. 镜像与 Build Cache 治理

- **目标**：每服务仅保留当前正式镜像与一个已验证回滚镜像，并控制缓存预算。
- **输入**：Docker 镜像/容器清单、发布结果、空间审计和用户批准。
- **入口与关键检查**：分别记录逻辑 SIZE、共享层、Docker Root 实际占用和根盘；Build Cache 软目标 2GB、超过 4GB 告警，根盘 70% 提示、80% 阻断新发布。
- **输出**：对象级保留/清理清单与空间对账。
- **停止**：镜像身份/引用不明、正式或回滚对象缺失、活动构建或空间口径混淆。
- **禁止**：`docker system prune`、`docker image prune -a`、`docker volume prune`、`docker compose down`，以及把共享层重复计入释放空间。

## 22. 三服务干净生产基线

- **目标**：记录而非备份三服务的 Git、Compose、容器、镜像、数据、HTTP 和空间身份。
- **输入**：只读服务快照、六个保留镜像、数据 Manifest、磁盘与 Build Cache 数据。
- **入口与关键检查**：创建新的带时间戳 baseline，不改写旧基线；2026-07-26 的 `/home/ubuntu/production-baselines/20260726T095054Z_three-service-clean-baseline/` 仅是当日参考实例，非永久常量。
- **输出**：`baseline_manifest.json`、`baseline_result.json`、`baseline_summary.md` 及 SHA-256。
- **停止**：三服务异常、身份/数据不一致、基线目录不可写或需要复制业务数据。
- **禁止**：把基线当作业务数据备份、覆盖旧 baseline、将 env 值或密钥写入基线。

## 23. Cron 与自动更新验证

- **目标**：验证自动任务的执行用户、时区、锁、日志、权限、运行身份和稳定数据链。
- **输入**：项目契约、Cron 条目、包装脚本、日志目录、密钥路径（只查元数据）和状态/Manifest。
- **入口与关键检查**：只读确认时区、排程、flock、重定向、运行用户可写日志、容器运行身份与控制仓库身份的区分；真实执行另需用户授权。
- **输出**：无密钥内容的审计结果、权限和数据完整性结论。
- **停止**：无法确认运行用户、锁、密钥权限、日志写入或数据原子性。
- **禁止**：为诊断而运行真实更新、泄露密钥、修改 Cron、用控制仓库 SHA 冒充容器运行 SHA。

## 24. 常见失败与处理

- **目标**：将已知事故转化为停止规则而非临时旁路。
- **输入**：失败退出码、有限日志、时间线、环境/身份事实。
- **入口与关键检查**：检查外层超时大于内部超时；复杂 Shell 改为固定脚本；PYTHONPATH/测试夹具/快照时间使用显式契约；Compose 所有权、orphan、候选标签、readiness 预热、Cron 权限、运行 Image 身份和 Docker 空间分别核验。
- **输出**：分类为环境、代码、数据、权限、网络或工具能力的问题记录。
- **停止**：同类可信检出失败第二次、时间顺序不满足、权限/身份不明或生产边界被触碰。
- **禁止**：修复测试降低正式断言、把环境错误称作代码失败、用重试或手工补文件伪造成功。

## 25. 新功能、新服务与数据修复的不同流程

- **目标**：按变更本质选择最小且完整的流程。
- **输入**：范围卡、项目契约、数据/架构影响和用户授权。
- **入口与关键检查**：普通 Business 使用上面的 Fast Lane；高风险修改使用 hosted strict Admission；独立服务或重大架构先走新服务模板；纯数据修复走数据候选/原子发布；需要生产发布的代码或部署文件变化进入完整候选/同一 Image ID 发布链，main 接纳不自动授权发布。
- **输出**：明确流程选择和未选流程的理由。
- **停止**：数据与代码职责混合、新服务必要性未证明或试图绕过候选。
- **禁止**：把所有项目默认容器化，或把数据热更新误作镜像发布。
