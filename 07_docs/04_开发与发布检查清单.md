# 开发与生产发布操作清单

> 文档状态：当前权威操作手册。规则以根 AGENTS、项目契约及[标准开发与生产发布规范](03_标准开发与生产发布规范.md)为准。本手册不证明任何候选或发布工具已经通过真实生产门槛。

## 1. 选择任务流程

先确认业务目标、修改范围、数据写入和目标服务，再选择流程。开发阶段不执行生产章节。

| 任务 | 必要步骤 | 完成记录 |
|---|---|---|
| 普通 Business 开发 | 环境预检 → 独立分支 → 相关测试 → PR required CI → main 接纳 | PR、精确 Commit/Tree、实际测试结果 |
| Shared / Infra 或 Governance / CI | 同一开发流程，加消费者/治理/平台验证及 Maintainer review | 同次 run 的 required 结果；适用的 full 对照 |
| 数据更新或修复 | [数据规范](02_数据与输出规范.md)与[日常运行手册](06_日常运行与数据更新手册.md)中的正式入口 | 数据候选、备份、原子发布及读取验证 |
| ROUTINE_STATELESS 发布 | 同一镜像候选验证 → 页面验收 → 正式部署 → 最终验收 | 普通 acceptance / deployment record |
| ADDITIVE_REVERSIBLE 发布 | 自动可逆性/兼容性验证，再走同镜像候选和正式验收 | 分类事实、适用工具的证据及部署记录 |
| IRREVERSIBLE / DESTRUCTIVE / UNKNOWN | 严格迁移和恢复验证，独立授权 | 完整高风险证据链；UNKNOWN 不自动 PASS |

发布深度以规范 14.1–14.4 和当前评估器为准。Routine 与已证明 Additive 无 targeted recovery 或 full rollback rehearsal 硬门槛；真实恢复验证可作为诊断，提交后仍严格验真。发现破坏性证据时不得人工降级。

## 2. 环境预检与任务范围

- [ ] 按[环境规范](05_执行环境与跨环境传输规范.md)确认 OS、Shell、cwd、Git 根、HEAD、分支、工作区状态及输入的实际路径和身份。
- [ ] 运行 `04_scripts/environment/verify_development_environment.py --scope python`；前端任务选 `frontend`，两者都有选 `all`。不传 scope 保留完整预检。Python 3.12、Node 24、Corepack pnpm 10.12.1 按实际依赖核验；Windows 本地不要求 Docker。
- [ ] `git fetch origin` 与 `git ls-remote origin refs/heads/main` 核验 fresh main。选现有合适的独立 worktree 或建立 feature/fix branch；直接创建 feature/fix branch 同样合法。
- [ ] 明确改动文件、相关测试、运行服务、需要保护的数据和授权边界；普通功能使用[任务模板](templates/新功能开发任务模板.md)。

START / RESUME 会 fetch 并写 local Git metadata，不是纯 read-only。开发启动不依赖无关 local main checkout 是否 clean、mirror；只有实际同步 main 镜像才核验。runtime_target=none 不要求 runtime root、marker 或 production evidence。

停止条件：必要工具缺失、输入不可读、身份冲突或范围不明。不得自行安装替代工具、修改 PATH、猜测跨环境路径或覆盖未知文件。

## 3. 开发、测试与 GitHub 接纳

- [ ] 完成实现和相关本地测试；Shared / Infra 加消费者测试；Governance / CI 加治理和平台测试。规范保留全部 required obligations。
- [ ] 审查 diff，显式 `git add` 本次文件，提交到功能分支并创建或更新同一个 PR。
- [ ] PR 自动运行一次 `trusted-main-admission-v1`，不同时启动重复的手动 workflow。新提交取消同分支旧 run；手动入口用于明确的补充诊断。
- [ ] 应用打包来源变化运行真实镜像验证；发布工具、共享运行身份、构建或权限合同变化运行完整发布/故障回滚演练。运行合同只改 JSON 格式可以免生命周期重放，任何语义变化均进入完整演练。路由工具或 workflow 变化本身也运行完整演练。
- [ ] 核验 exact base/candidate Commit/Tree、plan、同次 run/attempt、实际 Linux / 必需 Windows 结果。required 的 FAIL、SKIP、missing 均不得记 PASS。
- [ ] Strict / Governance 保留同次 authoritative base/candidate full suite 对照，NEW_FAILURE、NEW_SKIP、REMOVED_BASE_TEST_NODE 均为 0；新增测试全绿。债务节点和数量动态报告，不维护固定白名单。fresh main 变化后重新取对应 baseline。
- [ ] Governance / CI 由 Repository Maintainer/Admin 审查后接纳。review 不能覆盖 CI 失败；按规范执行 main 同步，不 force 或 Ruleset bypass。

此阶段完成于精确测试证据和适用的 main 接纳。main != production；生产单独授权，CI PASS 不授予数据写入或 FULL DAILY 权限。治理规则集中在[规范](03_标准开发与生产发布规范.md)，不在每份任务单重复填写。

## 4. 发布准备与只读基线

只在开始已授权的发布准备时执行。先运行 exact base/target 风险分类，记录事实和未解决项。分类不等于生产批准；coverage limitation 进入 Maintainer 风险审查，不以猜测降级。

- [ ] 确认目标 Compose、project、服务、端口、网络和挂载；Spread、USDA、Oil World 单独操作。
- [ ] 只读记录正式容器/Image ID、Git/Tree、健康/HTTP、数据 Manifest、env/Compose 身份、磁盘及内存余量、并发任务和上一正式版本资产；不记录密钥内容。
- [ ] 保留可用 rollback 镜像、配置和数据边界；历史 grant 过期应按当前工具签发 fresh grant。
- [ ] 从获批 main 的完整 SHA 在全新隔离目录可信检出，核验 Commit/Tree、clean、对象完整性和传输后身份。检出失败冻结证据，在新 attempt 重试；同类对象失败第二次停止。
- [ ] 从可信源码 Build Once，记录完整 Image ID 和 OCI identity。发布工具与业务 Application Target 可以分别核验；不因工具升级重建已验收应用镜像。

停止条件：正式服务异常、身份/数据基线不明、资源不足或恢复资产缺失。不得在正式业务目录 checkout、安装、测试或构建；不得预先改正式 env/Compose 或顺带运行数据更新。

## 5. 候选与页面验收

- [ ] 候选使用独立 project/container/network、空闲 `127.0.0.1` 端口，不加入正式网络、不占正式端口。
- [ ] Production-backed immutable inputs 只读；必要写入仅落 candidate-owned isolated RW。candidate 不写 production 的 CNF、结果和历史数据。
- [ ] 当前工具机器核验 Commit/Tree/Image、mount/network/write isolation、fresh grant、runtime preflight、health/HTTP，并对比正式数据和旁路服务不变。
- [ ] 按适用工具选择 MANUAL 页面验收或 AUTOMATED DOM；MANUAL 不要求 Playwright/Chromium。维护者核对图表、公式、单位、日期、交互与持久化语义，不能覆盖机器失败。
- [ ] WAITING_FOR_MAINTAINER_UI_ACCEPTANCE 不是发布 PASS；保留候选实例及 URL。记录明确验收者、时间和精确实例/镜像身份后继续。

Routine 使用[运行工具说明](../04_scripts/runtime/说明.md)中的 build → validate → deploy 和普通 JSON 记录。Additive 使用当前支持其状态合同的工具，不因为免恢复演练而改走不支持持久状态的 Routine 工具。

按[规范第 11 节](03_标准开发与生产发布规范.md#11-当前强制发布产物)选择实际工具产物：legacy 使用 release、candidate_result、deployment_plan 及 Manifest；1.8.0 HIGH_RISK 使用受保护 request/assessment/acceptance 引用和密封计划。候选必须仍存在时记录验收；原工具要求生成计划前删除候选容器，镜像保留。该条件不适用于 Routine MANUAL 等待验收阶段。1.8.0 HIGH_RISK 独立 HTTP 候选没有后续 live 消费时，验收后可停止，正式验收后按精确清单删除；recovery rehearsal 仍保留到最后消费者及执行终态。请求和签名细节见[运行身份说明](../09_deploy/runtime_identity/说明.md)。

## 6. 正式部署与最终验收

- [ ] 已有针对精确目标与服务的生产授权；Approved identity、Commit/Tree/Image、Manifest、rollback 按适用工具核验，不手写 PASS 或补造事实。
- [ ] 执行前再次核验正式基线未漂移，只切换目标服务；使用候选验收的同一 Image ID，Deploy Same Image，不重新 build 或 pull。
- [ ] 高风险/原工具必须消费已验证 deployment_plan 和 Manifest；执行参数按工具固定，不密封后改变核心 argv。
- [ ] 检查正式运行 Image/Git/Tree、健康/HTTP、挂载、数据不变性和非目标服务不变。
- [ ] 完成维护者最终 UI/business acceptance；生产机器或页面失败时走既有 rollback 入口，不以“容器启动”宣称完成。
- [ ] 保存 deployment record；legacy 的 deployment_result、对应 Manifest 和 bundle Manifest 全部验证通过；1.8.0 HIGH_RISK 验证实际 execution-result 与计划引用，不补造 legacy bundle。

停止条件：未授权、身份/基线漂移、旁路服务变化、数据异常或就绪失败。生产确认前禁止真实 CNF save；确认后恢复正常业务写入，不新增临时运行状态机。

## 7. 回滚、清理与生产基线

- [ ] 回滚使用已核验 previous image 和配置；需要授权的运行实例创建后核验并取得 fresh grant。不得复用已停止实例的历史 grant。
- [ ] 回滚后重新检查运行身份、健康/HTTP、业务、数据和旁路服务。代码回滚不等于数据恢复；恢复数据按独立数据合同执行。
- [ ] 完成正式验收和证据归档后，只清理已授权且逐项确认无引用的候选、临时目录、旧资产；清理前确认绝对路径位于授权范围。
- [ ] 保留当前正式版本、上一可用回滚版本、业务数据、`.env` 和必要失败证据。清理不是发布成功的默认副作用。
- [ ] 生成带时间的生产身份/哈希基线，不覆盖旧记录、不收录密钥和业务正文。具体容器 ID 和某日 SHA 不能成为永久规范常量。

禁止 `docker system prune`、`docker volume prune`、`docker image prune -a`、`docker compose down`；不得删除正式容器/镜像、唯一备份或正式项目目录，不覆盖 `01_data`、`.env`、`06_outputs`、`10_logs`。

## 8. 完成记录与失败处理

只勾选实际进入的流程：

- [ ] 开发：改动文件和原因、相关测试、精确 PR/Commit/Tree、required CI 状态、适用的 review/main 接纳状态。
- [ ] 发布：分类、候选和同一 Image ID、机器结果、两次适用页面验收、生产授权、deployment record 与 rollback 来源。
- [ ] 数据：输入和输出身份、备份、发布结果和页面实际读取结果，未混入代码部署。
- [ ] 清理：具体对象、引用检查、授权、保留资产和清理后状态。

最终报告注明是否修改数据、连接服务器、部署、执行 Git，以及未解决风险。未进入生产阶段不构成普通开发未完成；进行中的 CI 或等待验收必须如实报告。

失败先保留时间、退出码和有限脱敏日志，再分类为环境、代码、数据、权限、网络或工具问题。按[环境规范](05_执行环境与跨环境传输规范.md)处理超时、UTF-8 和跨环境身份，按[运行手册](06_日常运行与数据更新手册.md)处理更新故障。不得并发重复启动、忽略退出码、放宽断言或手工补造成功产物。
