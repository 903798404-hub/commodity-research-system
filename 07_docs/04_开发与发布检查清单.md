# 标准开发与生产发布手册与验收清单

> 文档状态：当前权威操作手册。本手册把 [`03_标准开发与生产发布规范.md`](03_标准开发与生产发布规范.md) 的强制规则落实为阶段化操作；发生冲突时停止，以 `AGENTS.md`、文档索引和规范为准。本手册不证明任何候选或发布工具已经通过真实生产门槛。

## 使用方法与固定阅读顺序

先读 `AGENTS.md`、[`00_文档索引与适用范围.md`](00_文档索引与适用范围.md)、
[`05_执行环境与跨环境传输规范.md`](05_执行环境与跨环境传输规范.md)，再按任务读取
规范、项目契约和本手册。普通功能使用 [`templates/新功能开发任务模板.md`](templates/新功能开发任务模板.md)；确有独立运行必要时使用新服务模板。以下每章均给出目标、输入、入口与关键检查、输出、停止条件和禁止行为；按适用流程执行，生产章节不是普通 Business main 接纳的前置条件。

普通 Business Fast Lane：
`START / RESUME → development → push feature → trusted-main-admission-v1 PASS → exact fast-forward main`。
正式 required tests / Scope / identity evidence 使用 GitHub hosted Admission；
`complete_project.py` 与独立 integration worktree 不再是普通 Business 进入 main 的强制 Gate，
不得因未执行它们判定未完成。本地 Direct / Impact tests 和 Scope 用于开发反馈。
任何新 commit 都必须重新获得 hosted PASS，即使 Tree 相同也不得复用旧 PASS。

不适用于 shared infrastructure、governance、protected paths、production-control-plane、
FULL DAILY、Production Wrapper、Runtime、deployment 或 production data/write path。
高风险 lane 使用同一个 `trusted-main-admission-v1` 的 strict 检查；Completion 与独立 integration 可用于开发反馈或专项验收；按真实范围判断，
不能仅凭 business 标签或绿色 check 使用快车道。生产章节与专项合同继续适用。

## 1. 手册用途与阅读顺序

- **目标**：把任务分类为本地开发、数据更新、候选、正式发布、回滚或只读审计。
- **输入**：用户授权、任务范围、当前项目契约和文档索引。
- **入口与关键检查**：确认本手册适用；数据任务同时读 `02`、`06`，生产操作读 `03`、目标发布工具和密封产物。
- **输出**：记录所读文档、阶段和授权边界。
- **停止**：任务类型、授权或项目契约不明确。
- **禁止**：把 archive、旧报告或聊天摘要当作当前操作依据。

## 2. 系统与服务架构

- **目标**：确认只操作目标应用。Spread 使用根 `docker-compose.yml`、容器 `spread-dashboard`、端口 8501；USDA 使用 `09_deploy/usda_release/compose.production.yml`、project `market-data-usda`、容器 `usda-dashboard`、端口 8080；Oil World 使用 `09_deploy/oil_world_release/compose.production.yml`、独立 project、容器 `oil-world-dashboard`、端口 8081。
- **输入**：`01_系统架构与项目边界.md`、`02_configs/app_catalog.yaml`、目标 Compose 和 Docker inspect（生产阶段）。
- **入口与关键检查**：用目标服务的独立 Compose `config` 与 inspect 核验；仅目标服务可构建、候选、切换或回滚。
- **输出**：目标服务、Compose、project、端口、网络、挂载和不变服务清单。
- **停止**：Compose 所有权、project 或服务边界不唯一。
- **禁止**：共享 project 执行 `--remove-orphans`、普通发布执行 `compose down`、顺带重建其他服务。

## 3. 环境预检

- **目标**：证明命令与输入在正确环境可用。
- **输入**：实际绝对路径、Git 根、`.venv-py312`、前端项目和所需权限。
- **入口与关键检查**：运行 `04_scripts/environment/verify_development_environment.py`；Python 必须为 `>=3.12,<3.13`，Node 为 `>=24,<25`，Corepack 管理的 pnpm 必须为 `10.12.1`；Windows 本地不要求 Docker。
- **输出**：OS、Shell、cwd、Git、工具版本、输入 SHA/大小及退出码。
- **停止**：路径不可读、环境不匹配、缺少正式工具或跨环境身份不明。
- **禁止**：自动安装工具、使用 Python 3.14、Codex fallback pnpm、猜测 `/mnt/data`、Windows 或服务器路径可互访。

## 4. 新任务范围定义

Registry/4 项目先核验显式 `runtime_target`。production_container 必须有精确且有效的
runtime manifest；独立 production/release gate 中由正式 completion 主动执行目标验证器，静态与容器
验证均 PASS 才可完成。验证器/Linux builder 缺失为 BLOCKED；身份不符、机器证据缺失
或验证失败为 FAIL。不得导入手写 PASS，也不得用本机 static-only 检查替代真实镜像验证。
读取实际使用的 Compose 源和渲染身份，不以固定惯例路径代替部署事实。详见 `03` 的
Registry/4 runtime intent 与目标验证条款。

- **目标**：在写代码前锁定目标、修改面、数据边界、测试、停止点和是否部署。
- **输入**：已填模板、现有项目契约、`git status --short` 和用户授权。
- **入口与关键检查**：读取 Registry 的 project_id/change_class、owned/protected 和 tests，列出明确不变文件、数据来源/频率、服务/容器需求与授权；普通功能默认 `business`，不能自行批准 shared。
- **输出**：可审计范围卡和回滚/报告要求。
- **停止**：拟新增端口、容器、数据库、Cron 或生产变更没有明确批准。
- **禁止**：把发现的无关问题顺手纳入，或用新容器替代既有服务内的普通功能。

## 5. 本地开发

- **目标**：只在独立 feature branch/worktree 完成允许的修改，local main 保持 clean origin/main 镜像。
- **输入**：范围卡、当前 HEAD、用户原有修改清单和相关源码/测试。
- **入口与关键检查**：先用 `start_project.py --project <id> --branch feat/<name> --worktree <path>` 在线 fetch/ls-remote 预检，经授权加 `--create`；聊天旧 SHA 不作执行依据。普通 Business START / RESUME 不依赖无关 local main checkout 是否 clean、mirror 或存在；高风险 lane 保留 main mirror。candidate Registry 未自行修改、latest main 仅追加无关项目且当前身份/ownership 仍兼容时可 RESUME，main 接纳仍须针对最新 main 的 hosted PASS。使用适用的正式工具链；每次修改后审查精确 diff。
- **输出**：限定文件的可复现本地修改及专项测试结果。runtime_target=none 的 ordinary Business 不要求 runtime root、marker 或 production evidence；只有实际使用 Runtime 的任务才检查 Mode/root/marker。
- **停止**：需要修改生产数据、密钥、Docker、Compose、env、Cron 或未授权公共模块。
- **禁止**：在服务器开发、用整目录覆盖、覆盖用户已有未提交内容。

## 6. 数据更新与原子发布

- **目标**：让数据更新与代码发布完全分离并可恢复。
- **输入**：项目数据契约、权威输入、candidate/stable/backup 路径、状态文件和锁。
- **入口与关键检查**：按 `02`、`06` 与项目契约运行正式入口；核验输入 SHA、Schema、业务日期、唯一键、候选、备份和逐文件原子切换。
- **输出**：数据结果、Manifest、状态与页面/下游读取证据。
- **停止**：输入身份、锁、权限、Schema、历史记录或切换后校验异常。
- **禁止**：手工覆盖 Parquet/JSON、用代码部署替代数据结果、把正式数据烘焙进镜像。

## 7. 测试分级

- **目标**：按风险匹配专项、影响范围和完整回归。
- **输入**：修改清单、直接依赖、部署/依赖/Compose 影响和测试入口。
- **入口与关键检查**：普通 Business 可按需运行 Direct / Impact tests 和本地 Scope，正式结果检查 hosted Admission；高风险 lane 的 Direct Tests 后先运行 `audit_changed_scope.py --project <id>`，只有 `PROJECT_SCOPE=PASS` 才使用 `run_scoped_tests.py` 的 `impact`、`full` 模式。按需运行 pytest、前端测试与生产构建、Compose/Schema 契约、`compileall`、`bash -n`（环境具备时）和 `git diff --check`。
- **输出**：每条命令、退出码、通过/失败/跳过数和耗时。
- **停止**：任一必须测试失败、跳过被误记为通过、测试依赖隐式本机文件。
- **禁止**：删除测试、降低断言、扩大容差或为通过测试伪造数据。

## 8. 精确 Git 提交

- **目标**：创建只含已审计目标文件的独立提交。
- **输入**：允许文件列表、用户既有改动清单；普通 Business 的本地测试按需反馈，高风险 lane 提供必需的测试结果。
- **入口与关键检查**：依次查看 `git status`、diff/stat/name-status；只用 `git add -- <明确路径>`，再审查 cached diff/check/stat/name-status。
- **输出**：Commit SHA、Tree、Parent、标题、文件和行数。
- **停止**：暂存区出现数据、日志、env、构建物、截图或无关用户修改。
- **禁止**：`git add .`、`git add -A`、`git commit -a`、reset/clean。

## 9. GitHub 普通推送

- **目标**：让 GitHub main 成为已验证提交的唯一代码交换身份。
- **输入**：本地提交、`origin/main`、已批准网络身份。
- **入口与关键检查**：普通 Business push feature 后，按规范第 6 节通过 GitHub API 核对精确 SHA 的 successful `trusted-main-admission-v1`（GitHub Actions `integration_id=15368`）及该 run 的 `main-admission/1` artifact。核对 candidate Commit/Tree、trusted main、非空全通过 tests 和 Scope；在任务已有授权内从原 feature worktree 普通 fast-forward，无需 Completion/integration。Shared lane 从取得同一 required check 的 strict PASS 的 feature worktree 接纳。Governance root change 按 GovernanceTransition 合同核验技术 PASS 和 GOVERNANCE_ROOT_APPROVAL_REQUIRED 后，由 Maintainer/Admin 精确接纳。两者均先 fetch/ls-remote，确认 fresh main 是获批 candidate 的祖先、candidate 未变化，再执行 `git push origin <approved_candidate_sha>:refs/heads/main`；推送后核对三方 Commit/Tree 并同步 clean local main。
- **输出**：获批 HEAD、origin/main、远程 main 三方完整 SHA，以及 clean local main 的 ahead/behind=0。
- **停止**：behind 非零、远程或 candidate 身份变化、check 来源/结论或 artifact 不匹配、认证异常、Ruleset 拒绝或待推送链包含其他提交。新 candidate 必须重新获得 hosted PASS；不得关闭 Ruleset。
- **禁止**：force/force-with-lease、自动 merge/rebase/reset、永久改代理。

## 10. 服务器发布前基线

- **目标**：在任何候选前封存正式服务、数据和空间的只读事实。
- **输入**：用户批准的服务器访问、目标服务、正式 Compose/env 路径和当前部署结果。
- **入口与关键检查**：记录容器/Image ID/RestartCount/端口/挂载、HTTP、数据 Manifest、磁盘、Build Cache、当前与回滚镜像和正式仓库状态。
- **输出**：带时间戳的基线或审计证据，不复制业务数据或密钥。
- **停止**：正式服务异常、容器身份不明、数据哈希异常、Cron 风险窗口或工作区不干净。
- **禁止**：在基线阶段构建、重启、删除、修改 Compose/env/Cron 或运行数据。

正式 release preflight 必须执行规范 14.1–14.3 的风险分类与资产评估：分别记录
ROLLBACK_ASSETS_READY、EXECUTION_AUTHORIZATION、ROLLBACK_REHEARSAL_REQUIRED 和
IRREVERSIBLE_STATE_CHANGE。保留当前及上一正式版本资产；历史 grant 过期不单独阻止
ROUTINE_STATELESS；STATEFUL_OR_INFRA 必须有真实恢复验证。分类输出不等于发布批准。

## 11. 可信源码获取

- **目标**：从 GitHub 取得唯一、完整、可验证的候选构建上下文。
- **输入**：完整目标 SHA、Deploy Key、固定 SSH 包装脚本和唯一隔离目录。
- **入口与关键检查**：`ls-remote` 核验远程 SHA；全新只读浅克隆后 detached checkout，核对 HEAD、Tree、clean 和 `git fsck --connectivity-only`。
- **输出**：带命令、退出码、Commit/Tree 的可信检出记录。
- **停止**：浅克隆失败、对象错误重复出现、Tree 不一致、目录不干净或来源混合。
- **禁止**：在 `/home/ubuntu/market-data` checkout/安装/测试/构建；使用 worktree、旧迁移目录或不完整 clone 构建。

## 12. 候选镜像构建

- **目标**：从可信检出构建带完整身份的不可变候选镜像。
- **输入**：可信 Git/Tree、目标 Dockerfile、版本化 release ID、回滚对象和构建上下文。
- **入口与关键检查**：使用目标应用正式发布工具；候选标签不使用 `latest`/`new`，OCI revision=完整 Git SHA，记录完整 Image ID、Tree、构建输出和 inspect。
- **输出**：已构建镜像、release bundle/Manifest 或明确失败证据。
- **停止**：镜像身份、构建上下文、OCI、Release 或回滚对象缺失/不一致。
- **禁止**：覆盖正式/回滚标签、在正式仓库构建、把数据或 env 烘焙进镜像。

## 13. 候选容器验证

- **目标**：隔离验证目标服务而不影响正式三个容器。
- **输入**：候选 Image ID、release bundle、独立 Compose、正式数据只读视图和本机空闲端口。
- **入口与关键检查**：候选必须独立 project/容器名、只绑定 `127.0.0.1`、`restart=no`；用正式 readiness/validate 工具轮询 HTTP、日志、页面、inspect Git/Tree/Image 和数据不变性。
- **输出**：有限脱敏日志摘要、HTTP/页面/身份/旁路容器零变化证据。
- **停止**：端口公网暴露、重启、身份不一致、挂载可写、正式容器或数据改变。
- **禁止**：固定 sleep 代替就绪轮询、启动/重建 USDA 或 Oil World、候选占用正式端口。

## 14. candidate_result

- **目标**：只在候选仍存在且所有验收通过后密封候选事实。
- **输入**：已验证 release、readiness 结果、候选 inspect、候选启动前正式容器快照和 checks 文件。
- **入口与关键检查**：使用 `create_candidate_result.py`；Schema 和 Manifest 必须通过，运行时 Git SHA 必须由 inspect 实测，非人工输入。
- **输出**：不可覆盖的 `candidate_result.json` 与 `candidate_result.manifest.json`。
- **停止**：快照晚于候选启动、候选不存在、Schema/Manifest/身份失败或证据不完整。
- **禁止**：手写 JSON、补造快照、把计划值或正式仓库 HEAD 冒充运行身份。

## 15. deployment_plan

- **目标**：在候选容器已真实删除后密封唯一、非敏感的正式切换和回滚计划。
- **输入**：已验证 release、candidate_result、当前生产 Compose/env/容器/数据基线和候选 Image ID。
- **入口与关键检查**：确认候选容器不存在但候选镜像仍存在；用 `create_deployment_plan.py` 只读生成并验证 Manifest，锁定服务、project、绝对 Compose、项目目录、`current_production`、`target_release`、`deployment_tool_revision`、目标/回滚 Image ID 和 argv。A 与 B 不同是正常升级状态。
- **输出**：`deployment_plan.json`、Manifest、预演和基线对比。
- **停止**：候选容器未删、计划要求预先改生产 env/Compose、身份链不一致或回滚不明确。
- **禁止**：手写 plan、密封后 amendment 改核心 argv、用相对路径或当前目录猜测生产路径。

## 16. 正式部署

- **目标**：在用户批准后只切换计划目标服务，并复用候选的同一 Image ID。
- **输入**：用户批准、已验证 release/candidate_result/plan 及其 Manifest、可信工具检出。
- **入口与关键检查**：发布工具先确认实际 env、Compose 和容器仍等于密封基线，再原子切换 env 并从计划读取执行参数；实际 Compose argv 必须包含 `--no-build --pull never --no-deps --force-recreate`，且只针对目标服务。
- **输出**：目标服务切换记录和部署后事实。
- **停止**：未获批准、候选 Image ID 不同、旁路服务变化、就绪失败或回滚条件触发。
- **禁止**：重新构建正式镜像、`up --build`、`compose down`、prune、切换未在计划中的服务。

## 17. deployment_result

- **目标**：把正式部署完成事实密封为不可覆盖结果。
- **输入**：计划、正式容器 inspect、HTTP/页面/数据/旁路服务回归和实际运行时 Git SHA。
- **入口与关键检查**：由正式生成器写入 `deployment_result.json`、Manifest 和 bundle Manifest；计划目标、实际 Image ID、OCI、Git、Tree、数据和 HTTP 必须一致。
- **输出**：完整部署结果链。
- **停止**：任一结果/Manifest 缺失、运行时身份空或冲突、数据/其他服务变化。
- **禁止**：以容器名、标签、GitHub main 或人工描述代替结果链；缺少结果仍宣称发布完成。

## 18. 正式回归

- **目标**：证明目标服务已恢复、其他服务和运行数据未变化。
- **输入**：部署前基线、正式容器、端口、HTTP、数据 Manifest 和部署结果。
- **入口与关键检查**：核验实际 Image ID、RestartCount、健康/HTTP、页面、挂载、数据和三服务身份；无 healthcheck 的服务必须结合 HTTP 和日志。
- **输出**：部署结果中的回归结论和差异摘要。
- **停止**：目标不可用、非目标服务变化、数据哈希变更或观察到回归。
- **禁止**：用一次容器状态检查替代完整身份与业务回归。

## 19. 回滚

- **目标**：使用计划中已验证的上一 Git、Image、Compose/env 基线恢复目标服务。
- **输入**：密封计划、回滚 Image ID、前基线、回滚入口和用户批准。
- **入口与关键检查**：按密封步骤用既有精确回滚镜像创建 fresh instance，完成创建态验证、签发新 grant 后启动；重新核验 Image/Git/Tree/consumer/HTTP/数据。不得复用已停止实例的历史 grant。
- **输出**：回滚结果与新的部署结果事实。
- **停止**：唯一回滚对象不存在、数据恢复边界不明、计划未密封或旁路服务异常。
- **禁止**：重新构建、用 `latest` 猜旧版、删除失败证据或把代码回滚误作数据回滚。

## 20. 候选与失败资产清理

- **目标**：在证据链完成后仅清理明确、可恢复、已获批准的候选运行实体。
- **输入**：结果链、生产稳定证据、候选容器/镜像/data 清单和单独清理授权。
- **入口与关键检查**：候选容器必须在 plan 前删除；之后逐项核验当前正式、唯一回滚、数据、Manifest、失败证据和引用。
- **输出**：清理计划、完整 ID/路径、前后空间和零变化验证。
- **停止**：对象仍被容器/计划/结果引用、证据未密封或恢复能力不清楚。
- **禁止**：通配符删除、删除唯一回滚、自动删除 `candidate-data`、删除父目录。

## 21. 镜像与 Build Cache 治理

- **目标**：每服务仅保留当前正式镜像与一个已验证回滚镜像，并控制缓存预算。
- **输入**：Docker 镜像/容器清单、发布结果、空间审计和用户批准。
- **入口与关键检查**：分别记录逻辑 SIZE、共享层、Docker Root 实际占用和根盘；Build Cache 软目标 2GB、超过 4GB 告警，根盘 70% 提示、80% 阻断新发布。
- **输出**：对象级保留/清理清单与空间对账。
- **停止**：镜像身份/引用不明、正式或回滚对象缺失、活动构建或空间口径混淆。
- **禁止**：`docker system prune`、`docker image prune -a`、`docker volume prune`、`docker compose down`，以及把共享层重复计入释放空间。

## 22. 三服务干净生产基线

- **目标**：记录而非备份三服务的 Git、Compose、容器、镜像、数据、HTTP 和空间身份。
- **输入**：只读服务快照、六个保留镜像、数据 Manifest、磁盘与 Build Cache 数据。
- **入口与关键检查**：创建新的带时间戳 baseline，不改写旧基线；2026-07-26 的 `/home/ubuntu/production-baselines/20260726T095054Z_three-service-clean-baseline/` 仅是当日参考实例，非永久常量。
- **输出**：`baseline_manifest.json`、`baseline_result.json`、`baseline_summary.md` 及 SHA-256。
- **停止**：三服务异常、身份/数据不一致、基线目录不可写或需要复制业务数据。
- **禁止**：把基线当作业务数据备份、覆盖旧 baseline、将 env 值或密钥写入基线。

## 23. Cron 与自动更新验证

- **目标**：验证自动任务的执行用户、时区、锁、日志、权限、运行身份和稳定数据链。
- **输入**：项目契约、Cron 条目、包装脚本、日志目录、密钥路径（只查元数据）和状态/Manifest。
- **入口与关键检查**：只读确认时区、排程、flock、重定向、运行用户可写日志、容器运行身份与控制仓库身份的区分；真实执行另需用户授权。
- **输出**：无密钥内容的审计结果、权限和数据完整性结论。
- **停止**：无法确认运行用户、锁、密钥权限、日志写入或数据原子性。
- **禁止**：为诊断而运行真实更新、泄露密钥、修改 Cron、用控制仓库 SHA 冒充容器运行 SHA。

## 24. 常见失败与处理

- **目标**：将已知事故转化为停止规则而非临时旁路。
- **输入**：失败退出码、有限日志、时间线、环境/身份事实。
- **入口与关键检查**：检查外层超时大于内部超时；复杂 Shell 改为固定脚本；PYTHONPATH/测试夹具/快照时间使用显式契约；Compose 所有权、orphan、候选标签、readiness 预热、Cron 权限、运行 Image 身份和 Docker 空间分别核验。
- **输出**：分类为环境、代码、数据、权限、网络或工具能力的问题记录。
- **停止**：同类可信检出失败第二次、时间顺序不满足、权限/身份不明或生产边界被触碰。
- **禁止**：修复测试降低正式断言、把环境错误称作代码失败、用重试或手工补文件伪造成功。

## 25. 新功能、新服务与数据修复的不同流程

- **目标**：按变更本质选择最小且完整的流程。
- **输入**：范围卡、项目契约、数据/架构影响和用户授权。
- **入口与关键检查**：普通 Business 使用上面的 Fast Lane；高风险修改使用 hosted strict Admission；独立服务或重大架构先走新服务模板；纯数据修复走数据候选/原子发布；需要生产发布的代码或部署文件变化进入完整候选/同一 Image ID 发布链，main 接纳不自动授权发布。
- **输出**：明确流程选择和未选流程的理由。
- **停止**：数据与代码职责混合、新服务必要性未证明或试图绕过候选。
- **禁止**：把所有项目默认容器化，或把数据热更新误作镜像发布。

- [ ] 已有唯一文档入口，规范与手册职责清楚，相关项目契约已读取。
- [ ] 六类环境边界及任务实际需要的 Python 3.12、Node 24、Corepack pnpm 10.12.1 已核验。
- [ ] Registry/project_id、fresh remote、独立 feature worktree 已核验；普通 Business 以 hosted Scope 为准，不以无关 main checkout 状态阻塞开发。高风险 lane 与实际 main 同步核验 main clean mirror，integration/release 不在 main 验收。
- [ ] 本地→GitHub main→服务器只读检出链、三服务 Compose 边界和目标服务范围明确。
- [ ] 普通 Business：精确 candidate Commit/Tree 的 hosted Admission PASS、provider、artifact 和任务授权范围已核验，不要求 Completion/integration；Shared：trusted Scope、required/impact/必要 full tests 和精确身份的 strict hosted PASS 齐全；Governance：完整技术 PASS、精确证据和独立 Root 接纳决定齐全；Runtime 证据属于另行授权的 release gate。
- [ ] 提交只含显式文件；推送前后 ahead/behind 与三方 SHA 已核验。
- [ ] 候选使用可信检出、隔离 project、127.0.0.1、只读数据和同一 Image ID。
- [ ] release、candidate_result、deployment_plan、deployment_result 及对应 Manifest 已按阶段存在；候选容器已在 plan 前真实删除。
- [ ] 正式切换无 build、无 down、无 prune，仅切换目标服务；回滚对象明确。
- [ ] 每服务仅保留当前正式和唯一回滚镜像；Build Cache、根盘、历史证据和运行实体已分别对账。
- [ ] 新生产基线只记录身份与哈希；无密钥、env 值、业务数据或未授权用户改动进入结果。

最终输出应说明修改文件、测试、未解决风险、数据/服务器/部署/Git 的实际发生情况。仅适用 lane 的必填项缺证据时输出 STOP；普通 Business 未执行 Completion/integration 或未进入生产阶段不构成未完成。

已授权普通 Business 包含 commit/push feature，无需重复许可；main 需精确对象批准。START / RESUME 会 fetch 并写 local Git metadata，不是纯 read-only。


Governance Root of Trust：Repository Maintainer/Admin 是治理信任根。Business 正常 branch/worktree → tests → trusted admission PASS → main；Shared/high-risk 使用 strict/impact/consumer tests，未修改治理根时不增加人工治理批准。

Governance root change 完成可信身份、Scope、ownership、required/owned tests、减测和 mutation 检查后，技术失败返回 FAIL；全部通过返回 `TECHNICAL_VALIDATION=PASS`、`MAIN_ENTRY=GOVERNANCE_ROOT_APPROVAL_REQUIRED`。这是正常的待治理根接纳状态，不是普通 PASS。没有 candidate-side approval API、token、文件或 workflow 可把它升级为 PASS。最终接纳由 Repository Maintainer/Admin 在自动化之外批准精确 base/Commit/Tree。

`CANDIDATE_CONTROLLED_SELF_APPROVAL = NO`；`MAINTAINER_GOVERNANCE_ROOT_OVERRIDE = YES_BY_DESIGN`；`PROJECT_EXISTENCE_APPROVAL_REQUIRED = NO`；`ORDINARY_BUSINESS_NEEDS_HUMAN_APPROVAL = NO`。前者约束可信 validator 的权限授予，不能把候选同名绿色 check 当成可信来源证明；Maintainer 需审查执行来源及精确证据。不声称平台能防止 Admin 覆盖自己管理的规则。

Admin 权限只用于 Governance trusted-root transition 或灾难恢复，不得绕过普通 Business check、普通测试失败、scope violation、production release 或数据质量 gate。治理根接纳不能把技术失败改成 PASS。日常保持 Ruleset Active、bypass_actors=[]；极少数治理接纳按 [Governance Transition 合同](templates/GovernanceTransition.md) 的短时 Admin 操作完成并立即恢复，不能长期放宽普通开发。

Production 独立 release：Approved identity、Commit/Tree/Image、Manifest、release gate、rollback、candidate 不写 production、生产单独授权全部保留。已授权普通业务不重复申请 commit/push 或项目存在许可；任何任务明确的 main/生产禁止仍优先遵守。
