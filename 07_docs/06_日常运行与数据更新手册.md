# 日常运行与数据更新手册

> 文档状态：当前权威操作手册。本文是日常数据更新、状态检查和故障止损的当前入口；代码发布必须遵守 [`03_标准开发与生产发布规范.md`](03_标准开发与生产发布规范.md)。

## 1. 操作分类

开始前先判断任务类型：

| 情况 | 采用流程 |
|---|---|
| 国内基差 SQL 更新 | 基差数据更新，不部署代码 |
| 价差当日数据缺失 | 价差数据更新，不部署代码 |
| USDA 新报告期且 Schema/页面/算法/serving contract 未变 | 本地生成验证并发布 Runtime bundle；不提交数据、不构建镜像、不重启容器 |
| Oil World 新季度数据 | 本地不可变发布和比较；生产数据挂载更新按受控项目流程 |
| 美豆周度数据 | 使用美豆项目包装入口，不部署代码 |
| 天气稳定数据且 Schema/解析/页面代码未变 | 天气数据更新链，不重建镜像或容器 |
| 源码、配置、依赖、前端或部署文件变化 | 标准代码发布流程 |

数据更新和代码发布不得混成一次隐式操作。

代码任务先按[操作清单](04_开发与发布检查清单.md)第 1 节选择风险与工具路径。普通开发无需先执行生产步骤；已授权的 Routine / Additive 不因旧工具说明重复增加恢复演练，高风险保持严格恢复和独立授权。

正式应用、容器、端口和 URL 的当前登记以 `02_configs/app_catalog.yaml` 为准。执行生产操作前必须重新核验服务器事实。

`spread-dashboard` 预定的正式代码切换与回滚入口分别为：

```text
09_deploy/spread_release/deploy_spread_release.sh
09_deploy/spread_release/rollback_spread_release.sh
```

这组工具的能力必须以当前代码、Schema、测试和真实候选验收为准。2026-07-22
全天气发布不代表复盘提出的工具整改项已经实现；工具修复需要独立开发、测试和
候选发布。USDA 与 Oil World 的一条式工具仍待完善。

工具转为正式后，两者必须从包含目标 Release SHA 的隔离 `tool_repo_root`
执行，并读取已验证 `deployment_plan.json` 中的正式 Compose 文件、项目目录、
项目名、服务名和候选 Image ID；不得从当前目录推导生产路径。

spread 候选和正式验收还必须从 Docker inspect 实测容器
`MARKET_DATA_GIT_HEAD`，与 Release 完整 Git SHA 比较；候选结果和部署结果
分别保存该实测值。不得以计划值、正式仓库 HEAD 或人工输入代替实测值。

OCI revision 只记录完整 Git commit SHA。Tree SHA 不要求写入 OCI 标签，继续
由可信检出、Release 产物、镜像内 `/app/RELEASE.json`、候选结果、部署计划、
部署结果及各自 Manifest 传播和验证。

spread 成功和失败候选使用同一有限日志证据结构：最多最后 200 行、最多
64 KiB，记录采集时间、字节数、脱敏尾部 SHA-256、截断状态和
warning/error 数量。日志读取失败时只记录受控 `unavailable` warning；不得
保存无限完整日志、完整 inspect 环境变量或敏感值。成功摘要进入
`candidate_result.json`，并由其 Manifest 的目标文件 SHA-256 密封。

## 2. 国内基差数据

### 2.1 本地日常使用

正式原始数据：

```text
01_data/manual/榨利表/油脂油料价格.sql（basis_price 表）
```

历史 Excel `01_data/manual/basis/国内现货基差.xlsx` 仅保留为只读备份和人工核对资料。

在仓库根目录运行：

```powershell
python 04_scripts/run_local_dashboard.py
```

脚本先流式读取 SQL、选择未到期的最早合约、按工厂基差中位数生成正式数据库，输出最新日期、总行数、品种数和地区数；导入失败时不启动面板。

本地继续条件：

- SQL 身份、大小和 SHA-256 已核验；
- `basis_price` 结构、日期、品种、基差和合约正确；
- 不同合约没有交叉聚合，SQL 原始基差合同月仅作审计，正式提货月统一为“现货”；
- 没有未知品种和关键空值。

### 2.2 服务器数据更新

1. 记录本地 SQL SHA-256。
2. 使用已批准传输工具上传到固定 incoming 路径。
3. 在服务器重新计算 SQL SHA-256。
4. 两端哈希一致后，执行正式数据更新入口：

```bash
/home/ubuntu/market-data/.venv/bin/python \
  /home/ubuntu/market-data/04_scripts/update_basis_data.py
```

5. 验证候选质量门、最新业务日期、状态 JSON 和页面。
6. 验证 incoming 文件已按契约清理。

哈希不一致、合约隔离失败、校验拒绝或关键字段异常时停止。不得手工修改或复制 Parquet 绕过校验。

详细契约见 [`projects/国内基差数据更新流程.md`](projects/国内基差数据更新流程.md)。

## 3. 价差数据更新

Current 正式入口以 [production_data_delivery 合同](../09_deploy/production_data_delivery/README.md) 为准，在 Windows Approved control clone 执行：

```text
<approved-python> -I -B <approved-control-clone>/04_scripts/automation/run_production_data_delta_windows.py --config <private-config> --domain akshare
```

普通日更保持无参数并自动固定本次运行开始时的业务截止日。经独立批准的历史补录使用同一
正式入口追加 `--end-date YYYY-MM-DD`；不得调用 Legacy/Recovery 入口代替。正式运行证据
必须显示 requested/effective 日期一致，未来日期与执行链日期漂移均停止。

默认只生成 candidate；生产发布必须单独授权后显式追加 `--publish`。核验 Approved Commit/Tree、输入与数据 Manifest、生产 Current/previous、回滚对象和同一 FULL DAILY 文件锁。候选不得写 production；config/凭据位于 Git 外。发布执行 baseline → producer → package → Current → continuation 的合同，不以 main merge 代替生产授权。

旧服务器 `04_scripts/server_update_spreads.py --update-from-akshare` 仅为 **Legacy/Recovery Only**，不是 Current 正式入口。恢复时须独立授权并按现行生产数据合同验证，不直接在 host 补跑 provider。

验收须核对命令退出码、预期交易日、必需合约状态、Manifest 与页面读数；窗口外 last-valid 不等同于更新成功，状态口径按业务合同。失败时保留证据，禁止连续补跑或手工覆盖数据库。

历史月差只接受具有 `DAILY_CLOSE` 语义的价格；盘中 `current_price` 不得充当或覆盖历史收盘价。普通更新以本次请求日期范围作为业务值变更边界，正式 producer 在交付前比较 current/candidate，范围外任一业务 key 变化即失败并恢复候选前文件。确需历史修订时使用显式 `historical-reconciliation` 模式并逐项声明 `DATE|SPREAD_NAME|SEASON` 精确 key；全历史重算本身不扩大可发布范围。

正式 Windows 入口的历史修订只接受 `--historical-reconciliation-manifest <绝对路径>`，
其封闭 schema、Current 身份、原始 DAILY_CLOSE 证据和精确依赖闭包见
[`production_data_delivery/README.md`](../09_deploy/production_data_delivery/README.md#domestic-spread-历史语义修订)。
未提供 manifest 的普通日更完全保持原流程；历史修订的 candidate 和 publication 分开授权。
已经验收的历史 candidate 正式发布使用同一 Windows 入口的 `--promote-candidate`，
绑定原 reconciliation manifest、promotion evidence SHA 与旧 Current 的 ID/artifact/manifest
三项身份。服务器在同一 Current 锁内比较旧身份并原子切换；Current 移动时失败且保留候选，
不重新生成业务数据。activation image 必须实际支持 CAS 协议。完整参数及 evidence 合同见
[`production_data_delivery/README.md`](../09_deploy/production_data_delivery/README.md#domestic-spread-历史语义修订)。

## 4. USDA 月度更新

本地进入：

```powershell
cd '11_独立应用\USDA平衡表'
```

执行：

```powershell
pnpm run build:data
pnpm run check:data
pnpm run compare:data
pnpm run test
```

核验目标月份、生成矩阵、商品/国家数量、fatal、月间差异和页面预览。原始 CSV 不进入普通 Git 提交。

普通月度更新在以上命令和页面预览全部通过后：

1. 用 `09_deploy/usda_release/usda_runtime_data.py package` 从已验证 `public/data` 打包；
2. package 必须绑定成功 fetch manifest（4 metadata + 468 PSD 全成功）及 builder Git/Tree；
3. 上传不可变 bundle 到正式 incoming；
4. 服务器仅用 Python 标准库执行 validate/stage/promote，不 fetch、不 build USDA；
5. 先验证 immutable release URL，再原子切换小型 `current.json`；
6. 验证 report version、matrix、前月 snapshot、comparison 和页面；
7. 失败 release 保留在 `failed/`，旧 current 不变；rollback 只切 Runtime pointer。

普通月度数据更新不创建 Git 数据提交、不 push、不 Docker build、不切 Image、不重启容器。
Runtime release 必须自包含当前矩阵和前月 snapshot；前端页面只解析一次 current pointer，
后续请求固定到同一 release ID，避免 pointer 切换期间跨批次混读。

如果代码、配置、data schema、app contract、页面、算法、Nginx、Compose 或 Runtime 工具发生变化：

1. 显式提交并 main-first 推送；
2. 服务器在独立只读浅克隆目录检出完整 SHA；
3. 在隔离目录构建 USDA 候选镜像；
4. 运行候选容器，生成 `candidate_result.json` 和 `candidate_result.manifest.json` 并保存证据；
5. 删除候选容器并确认不存在；
6. 生成 `deployment_plan.json` 和 `deployment_plan.manifest.json`；
7. 正式切换复用候选验收的同一 Image ID；
8. 正式阶段禁止 `docker compose build`；
9. 生成 `deployment_result.json` 和 `deployment_result.manifest.json`。

代码发布仍遵守同一 Image ID 和强制部署结果原则；Runtime 数据结果与代码部署结果是两条独立事实链。

详细本地说明见 [`projects/USDA平衡表本地接入说明.md`](projects/USDA平衡表本地接入说明.md)。

## 5. Oil World 更新

授权原始资料位于 Git 仓库外，由 `OILWORLD_RAW_DATA_ROOT` 或忽略配置定位。

在 Oil World 项目目录中，先设置仓库外原始资料根目录：

```powershell
cd '11_独立应用\OilWorld平衡表'
$env:OILWORLD_RAW_DATA_ROOT = '<仓库外授权原始资料绝对路径>'
```

先执行只校验命令：

```powershell
..\..\.venv\Scripts\python.exe 04_scripts\update_oil_world.py --release 2026-09 --validate-only
```

通过后才生成 Release：

```powershell
..\..\.venv\Scripts\python.exe 04_scripts\update_oil_world.py --release 2026-09
```

`2026-09` 仅说明 `YYYY-MM` 参数格式，必须替换为本次已核验季度。

发布新季度前：

1. 确认 `{raw_root}/YYYY-MM/` 中唯一主 Excel；
2. 先执行 `--validate-only`；
3. 预演通过后执行正式生成；
4. 核验 source hash、mapping、comparison、`latest.json` 和 `releases.json`；
5. 运行 Python 和前端定向测试；
6. 本地预览详细页和 presentation。

发布期已存在、映射冲突、引用缺失或时间轴冲突时停止，不覆盖旧 release。

季度数据通过只读挂载热更新时，不应重建前端镜像。前端代码或镜像变化时，仍必须执行隔离候选、同一 Image ID、候选删除、密封计划和无 build 正式切换。

服务器正式数据挂载宿主路径和统一原子季度发布入口仍需在实际生产任务前确认。

精确输入、输出、停止条件、定向测试和本地预览命令见
[`projects/Oil World数据更新与本地验证契约.md`](projects/Oil%20World数据更新与本地验证契约.md)。该项目契约已经迁移旧手册的
可执行内容；执行日常 Oil World 本地更新不再需要读取冲突旧手册。

## 7. 天气稳定数据更新

天气代码、镜像和运行数据是三条独立身份链。仅天气稳定数据变化且 Schema、解析器、
配置语义和页面代码未变时，只执行数据更新链，不重建镜像、不替换容器；任一接口、
Schema、解析器或页面代码变化时，进入完整代码发布链并分别验收代码与数据。

### 7.1 清单与身份

- 实际文件数、作物、国家、相对路径、大小和 SHA-256 以当次数据 Manifest 为准。
- “16 个 Parquet + 16 个状态 JSON”只属于 2026-07-22 首次全天气发布历史事实，
  不是固定数量或通用门槛。
- 运行前、传输后、候选运行后和正式切换后均逐文件比较 SHA-256；聚合哈希不能替代
  逐文件身份。
- 页面标准日期只读取对应状态 JSON 的 `observed_latest_date`，不得硬编码日期、使用
  文件 mtime 或模型预测截止日冒充数据更新时间。

### 7.2 权限预检

正式切换前必须以实际业务运行用户预演并记录：

1. 正式 incoming 目录可创建且位于目标同一文件系统；
2. 目标目录所有者、组和权限符合运行契约；
3. processed/weather 目录原子 rename 权限有效；
4. update_status 临时文件创建、验证和逐文件原子 rename 权限有效；
5. 切换后业务运行用户可读取全部授权文件。

任一权限在预演阶段失败即停止，不得等到数据激活阶段才临时扩大权限。

### 7.3 原子切换

- `01_data/processed/weather` 使用同一文件系统的 incoming 完成普通复制、逐文件
  SHA/格式/业务身份验证，再执行目录级原子切换。
- `01_data/update_status` 是共享目录，只允许对当次 Manifest 明确列出的天气状态
  JSON 逐文件写入唯一临时文件，严格 UTF-8/JSON 和业务身份验证后原子 rename。
- 禁止整体替换 `update_status`，禁止删除或覆盖非天气状态文件。
- 缺文件、额外冲突文件、SHA 不一致、JSON 损坏或跨文件系统 rename 均必须停止。

首次天气发布允许正式天气文件为 0，但必须生成空基线 Manifest；非首次发布若正式
文件数意外为 0，必须与上一份数据更新结果或 `deployment_result` 对账后停止。

### 7.4 结果、回滚和清理

数据更新成功后必须生成数据更新结果及其 Manifest，记录目标数据 Manifest、切换前后
逐文件身份、权限预检、状态文件更新和页面核验。代码未变化时不得用代码部署结果代替
数据更新结果。

切换前稳定数据、状态文件备份、incoming、候选数据和失败证据是数据回滚对象。至少在
结果及 Manifest 密封、生产稳定确认且取得独立清理授权前保留；不得自动随容器或临时
运行视图清理。

## 8. 状态检查

生产只读检查至少包括：

- `02_configs/app_catalog.yaml` 与实际容器的对应关系；
- `docker ps`；
- 目标容器状态、实际 Image ID、OCI revision 和 RestartCount；
- 目标服务本机 HTTP；
- Git/部署结果和 Manifest；
- 数据状态 JSON；
- 最近任务日志；
- 磁盘和 Docker 占用。

容器没有 Docker healthcheck 时，空 health 值不表示页面正常，必须结合 HTTP 和日志。

## 9. 常见故障止损

| 故障 | 检查 | 停止原则 |
|---|---|---|
| 页面打不开 | 容器、端口、日志、本机 HTTP | 容器退出、端口未监听或启动错误时停止 |
| 容器重启 | 状态、RestartCount、日志 | 不反复手工 restart，准备回滚 |
| 基差更新拒绝 | Excel 历史、哈希和错误 | 不手工改 Parquet |
| 上传未生效 | 本地/服务器 SHA 和 incoming | 哈希不同不执行更新 |
| 数据为空 | 状态、稳定文件、页面日志 | 不用旧样例覆盖正式数据 |
| 自动任务缺失 | cron、锁、进程和日志 | 不确认原任务状态时不重复启动 |
| 磁盘不足 | `df`、Docker 使用量 | 不执行 prune，进入独立清理任务 |
| Git 不干净 | status、diff 和来源 | 不 reset/restore/clean；无法解释就停止 |
| 新镜像失败 | 候选结果、日志、旧 Image ID | 不继续部署其他应用 |

## 10. 回滚和清理

- 数据更新回滚按项目数据契约执行，不等同于代码镜像回滚。
- 代码回滚使用部署计划锁定的上一 Git 和 Image ID。
- 正式切换或回滚均不得重新构建镜像。
- 清理必须是独立任务。
- 不得删除当前生产数据、唯一原始资料、唯一回滚镜像或发布事实链。
- 禁止 Docker prune 和未经核验的递归删除。
