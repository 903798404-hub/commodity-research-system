# v2 执行源码保护

`production-execution-grant/2` 使用已签名绑定的 `runtime-manifest/2` 确定
`source_inputs`。容器 verifier 要求所有声明文件存在、路径无别名且受只读保护；
整个执行源码根目录也必须属于签名的 protected roots，并且实际只读。
源码根及其后代不得存在覆盖挂载，包括只读覆盖，以避免替换镜像中已批准的代码。

独立 CLI 镜像无需建立与其执行无关的 `05_apps` 目录。实际需要的入口、初始化文件
和源码依赖必须声明在 manifest 中；缺失声明文件仍拒绝授权。
旧 grant 合同继续验证既有编号目录，不改变 Git worktree 身份和 FULL DAILY 行为。

以上源码检查与已有签名、角色、Commit/Tree、RELEASE、manifest、marker、实例 nonce、
有效期和 runtime mounts 检查共同生效。candidate-validation 不授予 production write。

## Grant schema 审计与 task 扩展

当前权威合同为 `production_grant.py`；JSON Schema 只是同形 oracle。正式链路是：

- GRANT_SCHEMA：`production-execution-grant/1`–`/4`，exact fields、未知字段拒绝。
- SIGNER：root host 上唯一的 `host_authorization.issue_execution_grant`，Ed25519；没有 task signer。
- CONSUMER：容器内 `production_identity.verify_execution`，每次调用重验原始材料，不缓存授权。
- RUNTIME_MANIFEST：grant/4 只配 `runtime-manifest/3`，policy/6 candidate、policy/7 production。
- CONTAINER_BINDING：64-hex Docker ID、随机 32-hex hostname nonce 和受保护 host observation。
- MOUNT_BINDING：实际 mounts canonical SHA、manifest exact RO/RW roots、实际 mount permission。
- IMAGE_BINDING：immutable `sha256:` Image ID、OCI labels、RELEASE bytes。
- APPROVED_COMMIT_BINDING / APPROVED_TREE_BINDING：Approved、RELEASE、OCI label 三方一致。
- EXPIRY：grant 最长一小时；task request 最长一天，二者在消费时均须未过期。
- SECRET_CONTRACT：manifest secret references、实际只读 `/run/secrets/*` mount、policy target 集合
  三方精确一致；签名只包含 secret identity target，不包含 secret 内容。

grant/4 的完整 payload 是 grant/3 的全部字段：`grant_id/issued_at/expires_at/identity_kind/
authorization_mode/artifact_origin/role/project_id/module_id/service_id/runtime_id/approved_commit/
approved_tree/release_commit/release_tree/image_id/release_sha256/runtime_manifest_sha256/
runtime_marker_sha256/runtime_root/writable_roots/protected_mounts/rendered_compose_sha256/
mount_contract_sha256/actual_config_sha256/container_id/hostname_nonce/runtime_manifest_schema_version/
identity_root_role/candidate_scope_id/candidate_scope_sha256`，再加
`task_id/task_request_id/task_request_sha256/runtime_observation_sha256/approved_read_roots/
approved_secret_targets`。签名覆盖整个 canonical payload。

示例 soybean capture policy 仅用于说明 scope，不是生产 policy，也不包含业务逻辑：

```json
{
  "task_scope": {
    "task_id": "market-capture",
    "request_container_path": "/run/market-data-grants/task-request.json",
    "runtime_observation_container_path": "/run/market-data-grants/runtime-observation.json",
    "approved_read_roots": ["/runtime/capture-request", "/runtime/calendar"],
    "approved_write_roots": ["/runtime/capture-snapshots", "/runtime/lifecycle-events"],
    "approved_secret_targets": ["/run/secrets/tankan.env"]
  }
}
```

真实 capture 代码审计依据是 `capture_public_intraday.py`：读取 exact request/calendar，写显式
snapshot root，并读取 Tankan secret；Phase A/B 生命周期未来另需 event root。示例不授予 CNF、
materialization、Public Current 或 FULL DAILY write。metadata 可以出现 business date/session 等不透明值，
但 consumer 只用签名 task identity，不把 metadata 当 capability。
