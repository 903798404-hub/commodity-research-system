# Application Service Write Identity

本合同只为经过正式部署批准、长期运行的应用服务增加第二种受控写入身份。原 Machine Execution Grant 路径继续逐次验证，不降级、不改为 optional。它不是 CNF Editor 人员授权，也不改变 Production Promotion 的 Commit/Tree/Image 接纳条件。

## 可信启动链

1. 受保护的主机发布流程依既有正式合同核对 Approved Commit/Tree、精确 Image ID、Compose、实际容器和挂载；容器须处于 `created`，尚未启动。`routine_release.py` 的既有 `create → grant_and_start` 路径仍使用同一精确镜像和原签名 grant。
2. 管理员为每个新容器预先分配独立、空的 `/run/secrets/market-data-service.json` 文件来源。主机目录须 root-owned、0700；文件须 root-owned、可由容器的明确非 root GID 读取、不可被其他用户读取。Compose 通过 `SPREAD_SERVICE_CREDENTIAL_FILE` 将该文件作为只读 Docker file-secret 注入，不以环境变量传递凭证。不得复用旧部署已填充的文件。
3. 主机 `issue_application_service_credential` 重新观察并核对获批镜像/容器、受保护 policy 和精确挂载，从 policy 的 `application_service` 子对象取得 `service_id`、`runtime_id`、`allowed_writable_roots`。每个允许目录必须是实际核验过的独立 RW mount；`/runtime` 本身不能授权。主机只向空文件的原 inode 写入实际 container ID、随机部署 ID 和随机凭证，再确认容器内字节与主机一致。异常时不启动服务，失败目录不得重用。
4. 原 `issue_execution_grant` 随后在签名之前检查服务凭证的 container ID、服务/运行时身份、marker 和根目录与本次实际容器及受保护 policy 一致；旧部署的凭证不能随新 grant 进入新容器。原 Machine Grant 的签名及消费校验仍完整执行。`routine_release` 仅在上述两种核验都成功时启动精确容器。手动受保护启动路径同样必须先执行服务凭证签发，再执行原 grant issuer，最后启动。服务凭证不是 Machine Grant 的替代品。
5. 应用通过 `establish_application_service_context` 读取固定只读 secret 路径，验证 service/module/runtime/marker 和最小写根，取得仅在当前进程有效的 `ApplicationServiceContext`。每次 `assert_runtime_write` 重新检查进程、marker、凭证文件身份和目标根；凭证消失或轮换即失败。新容器必须使用新空文件和新凭证；旧凭证文件不可重新签发。该凭证没有 15 分钟 TTL，其寿命与被批准的容器部署一致。

业务服务不能以环境变量、容器名称、runtime marker、目录可写性或手工构造 Context 取得此权限。没有服务凭证时默认拒绝。无需 Docker socket、task-scoped grant、hostname nonce 或新增签名体系。

## 权限分离

`application_service.allowed_writable_roots` 是受保护 host policy 的精确列表，签发时与实际 RW mount 逐项比较。Soybean 所需根应单独选择 snapshot 和 operational 根；不得默认为整个 `/runtime`、Public Current、FULL DAILY 或其他商品的根。业务调用仍由 Human CNF Editor session 决定是否允许用户保存人工 CNF：人员授权和应用服务写入授权必须同时满足。AM/PM 正式 seal 不需要人员授权，但必须取得合法应用服务写入身份。此 shared 合同不实现 CNF 页面或 seal 业务入口。

`seal_intraday_snapshot` 继续使用现有不可变存储函数；Release ID、schema、content hash、原子写、NO_CHANGE 和冲突规则均未修改。应用身份和原 Machine Grant 身份只能通过同一 `assert_runtime_write` 进入写入边界。

## 运维边界

当前 Windows 开发机不能运行真实 Linux Docker 容器；本 Candidate 的本机测试证明合同、顺序和拒绝行为。真实容器的 root-owned secret source、非 root 可读性、只读挂载、精确 Image ID 与启动后读写须在后续 Hosted Admission 验证；本文件不表示已部署或已 Production Promotion。
