## 1.1 Change Boundary / Execution Contract

普通业务不再手填 Git/Registry 事实。执行 `start_project.py --project <id> --branch feat/<name>
--worktree <绝对路径> --create`；工具 fetch/ls-remote 后返回 STARTED 或 RESUMED，自动提供
HEAD、Tree、branch、worktree、baseline、owned paths、changed files 和测试入口。
新普通项目允许可信 AUTO BOOTSTRAP；现有项目不允许自我扩权。

人工只提供业务目标、验收标准和特殊权限决定。停止条件为身份/ownership 冲突、未知 dirty state、
测试失败或需要 shared/protected/governance/production 权限。生产与部署任务继续使用专项合同。

普通 Business Fast Lane：
`START / RESUME → development → push feature → trusted-main-admission-v1 PASS → exact fast-forward main`。
GitHub hosted Admission 是正式 required tests / Scope / identity evidence；
`complete_project.py` 与独立 integration worktree 不再是普通 Business 进入 main 的强制 Gate，
不得因未执行它们判定未完成。接纳必须使用同一个获批 candidate Commit/Tree；
任何新 commit 都必须重新获得 hosted PASS，即使 Tree 相同也不得复用旧 PASS。
按规范第 6 节回查 GitHub Actions `integration_id=15368` 的 check 与该 run artifact。

不适用于 shared infrastructure、governance、protected paths、production-control-plane、
FULL DAILY、Production Wrapper、Runtime、deployment 或 production data/write path；
高风险 lane 使用同一个 `trusted-main-admission-v1` 的 strict 检查；Completion 与独立 integration 可用于开发反馈或专项验收。

## 2.1 使用方法

1. 复制本模板到任务描述、PR 说明或验收记录；不要把它另存为长期项目契约。
2. 生成 Change Boundary、数据边界和停止条件；空白项视为未获授权。
3. 读取根 AGENTS、文档索引及 Registry；用 `start_project.py --project <id> --branch feat/<name> --worktree <path>` 在线预检，加 `--create` 才从最新 origin/main 建立独立 worktree，不改 local main。
4. 工具输出 worktree、Git root/common dir、branch、HEAD/Tree、status、测试入口和 forbidden paths；普通业务不要求人工抄录。特殊 Runtime 访问按原专项合同核验。
5. 普通 Business 可用本地 Direct / Impact tests 和 Scope 快速反馈；高风险 lane 的 Direct Tests 后、Impact/完整回归前必须运行 Project Scope Gate。普通 `business` 任务出现 Shared Dependencies 修改时停止；只有预先分类为 `shared` 的任务可按扩大后的边界继续。
6. 普通 Business 提交并 push feature，取得 hosted PASS 后在任务已有授权内精确 fast-forward，不要求独立 integration。高风险 lane 使用 hosted strict Admission；候选或正式发布仍需独立授权。
7. 若规则会长期适用于一个具体项目，更新 `projects/` 中现有契约；没有契约时才新增一份并登记到文档索引。

测试入口（既有项目从 Registry 生成；新项目按可信标准 namespace 发现）：

```powershell
python 04_scripts/quality/run_scoped_tests.py --mode special --tests 08_tests/<当前模块测试>.py
python 04_scripts/quality/audit_changed_scope.py --project <project_id>
python 04_scripts/quality/run_scoped_tests.py --mode impact --tests 08_tests/<当前模块测试>.py 08_tests/<直接依赖测试>.py
python 04_scripts/quality/run_scoped_tests.py --mode full
python 04_scripts/quality/run_scoped_tests.py --mode impact --tests 08_tests/<测试>.py --dry-run
```

完整回归不是每次小修改的默认动作。`--dry-run` 只展示计划，不执行测试。

## 3. 阶段与闸门

普通 Business 按上面的 Fast Lane 完成开发接纳，保留显式暂存、diff 审查及任务授权范围核验，不受下表的本地重复验证、Completion/integration 或生产阶段约束。下表用于高风险修改及另行授权的生产阶段，原严格验证不变。

| 阶段 | 允许做什么 | 禁止做什么 | 进入条件 | 退出条件 |
|---|---|---|---|---|
| `planning` | 填写范围卡、查阅契约 | 修改业务或扩大范围 | 有明确需求 | 范围、非目标、批准边界明确 |
| `preflight` | 核验环境、baseline、Worktree、Runtime、输入和原有修改；START/RESUME 会 fetch 并写 local Git metadata | 写入业务数据、连接服务器 | 已完成 planning | Git/Runtime/输入/测试身份和工作区状态已记录 |
| `implementation` | 仅改 Allowed Paths，运行 Direct Tests | 顺手重构、commit/push/部署 | preflight 通过 | Direct Tests 和本地检查通过 |
| `verification` | 先运行 Scope Gate，再运行 Impact/必要 Full 和页面验收 | 自动修复审计发现 | implementation 通过 | `PROJECT_SCOPE=PASS`、shared 分类一致、required tests 通过且无 BLOCKER |
| `commit` | 审查 diff、显式暂存、创建提交 | push、候选或部署 | verification 通过且属于已授权开发范围 | 提交只含允许文件 |
| `candidate` | 依现有发布规范准备候选验收 | 正式切换 | commit 通过且用户批准 | 候选证据和验收通过 |
| `production` | 依已批准计划正式发布 | 重新构建、扩大目标服务 | candidate 通过且用户批准 | 部署结果与回滚对象已核验 |
| `closed` | 输出结果、记录后续问题 | 追加范围外整改 | 前阶段事实已记录 | 用户确认交付完成 |

高风险 main 接纳前必须取得 strict hosted Admission PASS；生产容器验收按独立 release gate 执行。

## 4. 增量审计与问题池

```powershell
python 04_scripts/quality/audit_changed_scope.py --project <project_id>
```

Project 模式固定比较 `origin/main...HEAD` 及 staged/unstaged/untracked 变化，读取正式 Registry；输出 `PROJECT_SCOPE=PASS/FAIL` 与 `SHARED_CHANGE=YES/NO`。business 不可覆盖 owned、change_class、baseline 或豁免 known-existing；shared/protected 越界必须停止。完整参数与停止规则以标准规范和 CLI `--help` 为准，此模板不再复制另一份门禁说明。低层 `--owned` 只保留给测试或事先获批的 shared 任务。门禁不修复、不提交、不推送、不部署。

发现问题不代表获得修复权限。范围外问题只记录，不修改。除非公共模块是本次功能的直接阻断原因，否则不得顺手重构。

| 问题描述 | 发现任务 | 相关文件 | 问题分类 | 证据 | 是否阻断当前功能 | 建议后续任务 |
|---|---|---|---|---|---|---|
| | | | `BLOCKER` / `FOLLOW_UP` / `OUT_OF_SCOPE` / `INSUFFICIENT_EVIDENCE` | | 是 / 否 | |

- `BLOCKER`：阻断本次开发或上线；仅在用户批准后修复。
- `FOLLOW_UP`：与本次相关但不阻断；记录为后续独立任务。
- `OUT_OF_SCOPE`：与本次无关；只记录，不修改。
- `INSUFFICIENT_EVIDENCE`：证据不足；不得修改，补足证据或取得范围决定前不得进入下一阶段。


Governance Transition：普通 Business 与 STRICT_SHARED 沿各自 trusted tests/Scope 的 required check 接纳，不新增人工项目或治理批准。只有修改 Admission、Registry/ownership/test policy、治理 workflow、bootstrap 核心或治理 required tests 等 trusted-root 资产时，分类为 `GOVERNANCE_TRANSITION`。所有安全检查继续执行；缺少外部 maintainer approval 时返回 `GOVERNANCE_TRANSITION_PENDING`，不自动 main-entry PASS。

`PROJECT_EXISTENCE_APPROVAL_REQUIRED = NO`；`GOVERNANCE_TRUST_ROOT_APPROVAL_REQUIRED = YES`（仅 trusted-root 修改）。已授权 Business 开发不重复申请 commit/push 或治理许可；普通 main 操作按任务现有授权执行，不附加本机制的人为审批。本轮任务若明确禁止 main 操作仍必须停止。

审批使用 GitHub 原生 main 上的手动 workflow dispatch，绑定精确 base main SHA、candidate Commit 与 Tree，由 GitHub API 核验 maintainer/admin、可信 workflow 路径、运行身份与成功结论。candidate 文件、commit message、branch name、环境变量中的声明均不是审批；仅 run ID 是待核验的查询指针。批准不覆盖 Scope、减测、required 删除或未授权 production change，也不授权部署。

详见 [Governance Transition 合同与首次启用限制](GovernanceTransition.md)。生产继续独立 release / Approved identity / Commit/Tree/Image / 数据 Manifest / rollback / 单独授权。当前部署状态不能从本候选文档推断。
