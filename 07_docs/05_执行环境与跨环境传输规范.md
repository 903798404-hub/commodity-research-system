# 执行环境与跨环境传输规范

> 文档状态：当前权威规范。本文是环境预检、路径身份、跨环境传输、Shell、UTF-8 和超时治理的当前执行依据。

## 1. 目的和范围

本文防止任务因环境识别错误、路径猜测、附件不可达、跨环境身份丢失、超时处理不当或编码损坏而失败或重复执行。

适用于开发、测试、诊断、发布准备、生产操作和跨环境文件传输。根 [`AGENTS.md`](../AGENTS.md) 中的环境预检是强制闸门；本文提供详细方法，不降低数据和部署保护要求。

## 2. 六个隔离环境

### 2.1 Windows 本地开发环境

Windows 本地仓库使用环境占位路径表示：

```text
<实际 Windows 仓库根>\market-data
```

具体已核验实例只登记在 `projects/生产只读检出实例登记.md`，不得复制进长期规范。该环境负责代码和文档修改、本地测试、Git 提交和 GitHub 推送。必须确认实际 Git 根，不能仅凭目录名称判断。

### 2.2 Codex 执行和附件环境

Codex 只能使用当前可访问工作区和已进入当前文件系统的附件。不得猜测附件位于 Downloads、桌面、仓库或其他常见目录。

### 2.3 ChatGPT 会话沙箱

`/mnt/data/<filename>` 只属于相应 ChatGPT 会话。Windows、Codex 和生产服务器不能自动访问。用户必须下载或重新附加文件，文件才可能进入 Codex 可访问环境。

### 2.4 Ubuntu 生产服务器

正式项目目录通常为：

```text
/home/ubuntu/market-data
```

服务器路径必须先只读确认。Windows 文件、Codex 附件和 ChatGPT 沙箱文件不会自动出现在服务器。

### 2.5 GitHub 远程环境

GitHub 的分支、Commit 和对象身份只通过经过核验的远程命令确认。Windows 本地
`origin/main`、本地 HEAD 或服务器缓存对象都不能代替 `ls-remote` 的远程事实。
本地代理失效时，只能对需要的单条 Git 命令临时清空代理；不得永久修改 Git、系统
代理或 VPN 配置。

### 2.6 Docker 镜像和容器环境

Docker 镜像文件系统、未启动的镜像、候选容器和正式容器是不同边界。镜像中的路径
不等于宿主机路径，候选容器可见的数据也不等于正式数据已经发布。镜像身份、容器
运行身份和宿主机数据 Manifest 必须分别核验。

上述六个环境中的路径、进程、凭据和同名文件默认互不相同，不得跨环境臆测路径或
以同名推断同一身份。

## 3. 强制预检

正式执行前至少输出：

1. 操作系统和版本；
2. Shell 和版本；
3. 当前工作目录；
4. Git 根目录；
5. 完整 HEAD、分支和 `git status --short`；
6. 每个输入的实际绝对路径；
7. 输入存在性、可读性、大小和必要的 SHA-256；
8. 每条关键命令所属环境；
9. 目标环境是否能直接访问输入；
10. 是否需要跨环境传输；
11. 任务实际依赖的工具；
12. 当前最小权限是否满足任务。

不相关工具可标记为“不需要”，不得把不相关工具缺失误报为任务失败。

本地工具 `04_scripts/environment/verify_development_environment.py` 支持 `--scope python`、`--scope frontend` 与 `--scope all`。纯 Python 任务无需 Node/Corepack/pnpm；前端任务核验前端合同，混合任务选 all。不传参数仍检查全部工具链。该选择只排除不相关依赖，不替代 Git、输入、权限和跨环境预检。

同仓库 linked worktree 可复用已有正式 Python 环境，先核验两个检出的 `pyproject.toml`、`requirements.in`、`requirements.txt`、`requirements-dev.in`、`requirements-dev.txt` 与 `Dockerfile` 的 Git blob 身份一致（不要将 CRLF/LF 差异误认为依赖变化）。再用实际解释器执行预检，显式 `--root <持有 .venv-py312 的检出绝对路径> --scope python`；另外记录本次开发 worktree 的 Git/输入身份。依赖合同不同则不能据此复用通过结果；不创建替代环境或使用迁移专用 `--allow-candidate` 绕过。

新检出可能缺少被 Git 忽略的编号空目录。需要 Registry/结构测试时，先核验目录契约；在确认是本次独立开发工作区后，可创建缺少的 `01_data`、`06_outputs`、`10_logs` 空目录，仅补目录结构，不生成或复制业务文件。正式服务器不使用此方法补造数据；业务输入缺失仍停止。Hosted CI 使用现有 `required_lane_fixtures.py --prepare-checkout-directories` 准备一次性检出。

预检失败时停止，只报告已确认事实、单一缺失条件、影响和安全恢复步骤。不得自行安装软件、创建相似替代文件、复制未知同名文件、修改 PATH、扩大权限或降低身份校验。

## 4. 路径和文件身份

路径只在所属环境有效。同名文件不代表同一文件。

文件跨环境后必须重新确认：

- 绝对路径；
- 大小；
- SHA-256；
- 修改时间；
- 所有者和权限；
- 预期用途；
- 是否允许覆盖。

发布、生产诊断或数据替换中，源端和目标端 SHA-256 不一致必须停止。不得使用模糊路径、未展开变量、通配符或“第一个同名文件”作为正式输入。

## 5. 跨环境传输

### 5.1 ChatGPT 到 Codex

1. 用户下载文件或将文件附加到 Codex。
2. Codex 定位当前环境中的实际路径。
3. 验证存在、可读、大小和必要的 SHA-256。
4. 验证通过后才作为任务输入。

不得把 ChatGPT 回复中的 `/mnt/data/...` 当作 Windows 本地路径。

### 5.2 Windows 到 Ubuntu 的一次性脚本

一次性只读脚本优先通过既有 SSH 连接的标准输入以前台方式执行。执行前必须完成：

- 本地绝对路径和可读性确认；
- 语法和危险命令审查；
- SHA-256；
- 目标主机和既有身份确认；
- 内外层超时预算；
- 输出、错误和退出码保留方案。

不得用后台任务或复杂单行引号绕过 PowerShell 输入限制。需要逐字节传输时使用字节安全入口。

### 5.3 持久文件

服务器需要长期保留的文件可以使用 SCP 或 Git 可信检出。必须明确源/目标绝对路径、所有者、权限、覆盖授权和传输前后 SHA-256。

默认不允许覆盖未知正式文件。

### 5.4 正式开发和发布文件

正式代码和部署工具优先使用：

```text
本地 Git 提交
→ GitHub main
→ 服务器只读独立浅克隆
→ 完整 SHA 核验
```

不得长期依赖聊天附件、临时 SCP 文件或来源不明压缩包作为生产构建输入。

服务器可信检出必须以完整 Git SHA 为目标，并从全新唯一目录开始。首次失败后冻结
失败目录、stderr、退出码和时间证据，在新的唯一 `attempt` 目录重新检出；禁止在
失败 Git 对象库上继续 fetch、checkout、reset 或 repair。第二次同类对象失败时停止
重试，专项检查并发清理、外层超时、Git maintenance、文件系统、I/O 和 OOM。

### 5.5 候选数据视图

候选数据只能使用普通字节复制构造，禁止硬链接、符号链接和 reflink；源和目标不得
共享 inode 或依赖写时复制语义。候选容器应挂载完整独立的 `01_data` 视图，禁止在
只读父挂载下叠加 destination 重叠的子挂载。复制前后必须比较相对路径、大小、
SHA-256、UTF-8/JSON 和必要的数据格式可读性。

### 5.6 一次性脚本

一次性脚本执行前必须自检参数、路径、Unicode、NUL 字节和 dry-run 结果。每一步应先
记录 `started`，结束后记录 `exit_code`；无论成功或失败，都必须在 `finally` 路径生成
有限、脱敏的失败摘要和最后状态。不得因 `set -e`、异常或外层超时在证据写入前静默
退出。

## 6. 长任务和超时

长命令必须前台运行并返回明确退出码。禁止使用：

```text
nohup
后台执行
Start-Job
不等待的 Start-Process
忽略退出码
```

外层超时必须大于命令内部超时，并为连接、输出刷新和清理留出缓冲。内部 Git timeout 为 900 秒时，外层应明显大于 900 秒。

完成判定至少包括：

- 进程已退出；
- 退出码明确；
- 完成标记存在；
- stdout/stderr 已保留；
- 必要时输出大小稳定且 SHA-256 已记录。
- 每个关键步骤的 `started`、`exit_code` 和 `finally` 摘要已落盘。

不得仅因刚启动时输出为 0 字节就重复启动任务。超时应报告为执行时间或工具边界问题，不能自动归类为代码失败。

## 7. Shell、UTF-8 和中文路径

- 命令语法必须匹配实际 Shell。
- 不得把 Bash 语法直接用于 PowerShell，或把 Windows 路径直接用于 Linux。
- 复杂远程操作优先使用已审查脚本、SSH 标准输入、SCP、Git 或目标环境 Python。
- 禁止通过复杂多层单行命令传递大量脚本正文。
- 多行远程脚本应使用安全引用方式，禁止 `eval`。

涉及中文路径、中文正文、JSON 或 Markdown 时：

1. 严格 UTF-8 解码；
2. 避免系统代码页文本管道；
3. 传输后核对大小和 SHA-256；
4. 必要时做 UTF-8 往返校验；
5. 检查中文文件名和目录层级；
6. 检查换行、引号、JSON 和 Markdown 围栏。

损坏标志：

- ASCII 问号替代中文；
- `U+FFFD`；
- 中文路径缺失、截断或乱码；
- 换行、引号或转义异常；
- JSON 无法严格解析；
- Markdown 正文或代码块破坏。

发现损坏立即停止，不得覆盖正式文件、Manifest、部署结果、数据或治理文档。

## 8. 问题分类和停止

结论必须区分：

- 环境问题；
- 代码问题；
- 数据问题；
- 权限问题；
- 网络问题；
- 工具能力问题。

不得把环境缺失描述为代码失败，也不得为了通过测试而降低安全标准。

停止报告应包含：

- 失败类别；
- 已确认事实；
- 唯一缺失条件；
- 由谁提供；
- 条件满足后从哪个安全步骤继续。

## 9. 现有工具与新增工具

本地工具链预检使用 `04_scripts/environment/verify_development_environment.py`；发布身份与运行验证使用索引登记的 runtime 工具，按当前接口执行。一次性诊断脚本没有因成功运行过而成为正式入口。

新增诊断或发布工具仍须完成需求、开发、测试、危险命令审查、编码验证和代码评审。历史脚本与单次执行事实放入 archive，不作为当前授权。
