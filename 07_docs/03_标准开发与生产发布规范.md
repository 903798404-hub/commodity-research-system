# 标准开发与生产发布规范

> 文档状态：当前权威规范。本文用“必须、不得、应当、停止”定义开发、测试、Git、候选构建和生产发布的强制边界；逐步操作见 [`04_开发与发布检查清单.md`](04_开发与发布检查清单.md)。

## 0. 规范边界与用语

本文只定义长期、通用且可执行的约束，不记录某次发布的容器 ID、镜像标签、IP、
环境变量值或临时目录。此类事实只能作为带日期的实例保存在 `archive/`、密封发布
产物或生产基线中，执行时必须重新核验。

- **必须**：缺失即不得进入下一阶段。
- **不得**：禁止的行为；即使某次操作看似成功也不能作为例外。
- **应当**：默认做法；若不采用，必须记录原因、风险和替代验证。
- **停止**：保持已验证对象不变，报告已确认事实；不得用猜测、降级断言或旁路继续。

规范、手册、模板和归档的职责由 [`00_文档索引与适用范围.md`](00_文档索引与适用范围.md)
定义。下级文档不得放宽本文；手册不得把尚未通过真实候选门槛的工具称为正式生产工具。

不得要求为本项目安装这些工具。生产构建在获批的隔离服务器来源执行，
候选验收与正式部署必须复用完全相同的 Image ID。

## Mainstream Development Governance

### Full Regression Policy

Strict / Governance 的 full repository regression 使用 `ALL_GREEN`：只执行本次 exact candidate 的完整 Linux suite 一次，全部测试必须通过，零失败、零 skip。Windows-required 继续在同次 Windows hosted 硬 Gate 执行。完整计划仍从 authoritative base 与 candidate 的 Git 测试来源及平台声明生成，不减少 base required/future/impact obligations；candidate 新增/修改测试真正执行。

本地开发默认先运行与改动相关的测试；Strict / Governance 的完整结果由 Hosted CI 对 exact candidate 执行一次并验收，不要求每次本地编辑先重跑整仓 suite。必要时可以显式执行本地完整诊断，但它不替代同次 hosted run/attempt 的接纳证据。新提交或 main 基线变化仍须重新取得精确候选的 required/full 结果。

trusted required、future-required、impact/consumer、platform-required 和 candidate changed/added tests 均是绝对全绿硬 Gate，FAIL、SKIP、missing 均失败。full suite 也不再容忍既有失败，不维护 failure allowlist；full fallback 不得减少明确 required/impact obligation。

完整结果必须绑定 exact candidate Commit/Tree、required/full plan、同次 run/attempt，以及实测 runner、Python、锁、系统包、字体、环境变量和 pytest 配置。collection error、环境准备失败、receipt/plan/身份不一致、源码变更、运行未完成或必需收集缺失直接 FAIL。main 变化后重新生成计划并取得精确候选证据。普通无 Windows 依赖 Business 不启动无关 Windows suite。main-entry PASS 不授予生产发布权限。

旧 `NO_NEW_REGRESSION` 双份工具保留为显式历史诊断，不再进入 main required workflow，也不能替代 ALL_GREEN。过渡退出依据见[历史核验记录](archive/mainstream-full-green-retirement-20261006.md)，具体测试数量和某日 SHA 不作永久规则。


统一流程：`main → feature/fix branch → implementation → automated tests → required CI → main`。
Repository Maintainer/Admin 审查并接纳 Governance / CI candidate；review 是 integration decision，不是 CI failure。并行任务或共享可编辑检出使用独立 worktree，串行开发可复用现有独立检出；可用 START / RESUME 自动 fetch 并建立工作区，也可直接建立 feature/fix branch，不存在项目存在审批。

Registry 是 project/module metadata、ownership documentation、test mapping、impact analysis、runtime target 和维护责任登记，不是普通源码修改的 hard authorization。无 owner 不阻止合法项目启动；同一个明确的 Governance / CI candidate 可以原子修改 Registry、owner、test mapping、Admission、workflow、相关实现、测试和文档。不得借 metadata 偷偷扩大无关模块 Scope、减少 required tests 或取得生产权限。

Business 运行 scoped required tests；Shared / Infra 增加 impact/consumer tests，未映射 shared source 使用更广回归；Governance / CI 运行 governance regression 和相关平台 CI，并记录 `CHANGE_CLASS = GOVERNANCE_OR_CI`、`MAINTAINER_REVIEW_REQUIRED = YES`。技术验证 PASS 时 `trusted-main-admission-v1` PASS；failing tests、Scope violation、required test deletion、Registry 减测和未授权 production mutation 始终 FAIL，review 不能覆盖失败。

required plan 保留 base required/future/impact obligations，并 UNION candidate 新增/修改测试及 candidate 新增 mapping。candidate tree 中的测试版本必须真正执行，collection 非空，失败和 skip 均不得记为 PASS。Windows-specific required tests 使用 `windows-2022`；跨平台测试使用 Linux。最终 required check 聚合同一 base / candidate Commit/Tree、plan 和 workflow run/attempt 的实际平台 job；缺少必需平台结果即 FAIL。没有 Windows dependency 的 Business 不启动 Windows suite。

候选 workflow 是 Maintainer review 的信任对象；不承诺防御恶意 Maintainer 修改自己的 CI。一个 candidate 完成相关实现和 CI，无须先安装 owner 或 executor、无须分阶段 main transition。没有 candidate approval server、审批 token 或额外 GitHub App。

main Ruleset 保持 Active、required check `trusted-main-admission-v1`、non-fast-forward/deletion protection；不使用 bypass 作为正常开发路径，不修改 GitHub settings。提交前检查 diff/scope/tests；只显式 git add 文件。任何新 commit 都重新取得 exact hosted evidence。取得测试 PASS 后，main 接纳仍按任务授权，由 Maintainer 决定；本地 main 保持 clean 镜像，接纳只用普通 fast-forward，不 force、rebase、squash 或额外 merge commit。

`PROJECT_EXISTENCE_APPROVAL_REQUIRED = NO`；`ORDINARY_BUSINESS_NEEDS_HUMAN_APPROVAL = NO`；`REGISTRY_IS_HARD_AUTHORIZATION = NO`；`STAGED_GOVERNANCE_MIGRATION_REQUIRED = NO`。

`main != production`。生产单独授权；Approved identity、Commit/Tree/Image、Manifest、release gate、rollback、candidate 不写 production 均保留。Registry ownership、CI PASS 和进入 main 不授予 server deployment、production data mutation、FULL DAILY 或 runtime grant 权限。Production Release 合同独立执行。

### CI 触发与验证深度

同一个 PR 更新只自动运行一次 required workflow；不同时使用 feature push 和 PR 双重触发。保留 workflow_dispatch 作为明确的诊断入口，同分支并发只保留最新 run。没有 PR 的分支不自动取得 main 接纳证据。

应用打包来源变化仍运行真实 Docker 镜像与身份验证。发布工具、共享运行身份、构建合同、运行权限及演练实现变化保留六条完整演练；仅 CI 编排变化运行真实发布成功与故障回滚两条路径，仍执行镜像验证、过期记录重验与隔离检查；纯页面业务变更不重复整套生命周期演练。运行合同仅 JSON 格式变化可以免生命周期重放，但任何来源路径、挂载、权限、入口或其他语义变化，以及不能解析的合同差异，均进入完整演练。纯说明 Markdown 仅在 base 与 candidate 的已提交 runtime source_inputs 均证明它不是运行输入时免生命周期演练；缺身份、缺清单或清单不可解析保持严格分流。被打包的 Markdown、混合代码改动和运行权限改动继续验证。完整演练始终包含真实镜像验证；required / impact / platform 测试覆盖不因该分流减少。

本地 `requirements-dev.in/.txt`、Hosted 的 `windows-py312.in/.txt` 与 `aggregate-py312.in/.txt`、`08_tests/shared/test_module_test_map.py`、`04_scripts/quality/full_regression.py`、`platform_test_plan.py`、`required_lane_fixtures.py` 属于已核验的非发布消费者输入，仅在 base 与 candidate 的已提交运行清单均证明它们不属于 source_inputs 或 build 输入时，免完整发布生命周期演练。Windows 锁仅用于 Windows job，aggregate 锁仅用于最终聚合 job；相关消费者边界由回归测试检查。本地开发锁变化不隐式替换 Hosted 的实际 `.txt` 锁。Linux、host-tools、browser 锁、发布测试、未知 quality/shared 文件及混合发布改动继续完整演练；CI 路由与门禁编排至少进入真实两条路径验证；缺身份、缺构建声明或不可解析清单不享受豁免。required、impact、平台测试和同次 candidate full 验证继续保留。

演练范围由密封计划的 `spread_release_profile` 声明：

| 档位 | 适用变更 | 真实路径 |
|---|---|---|
| `none` | 页面业务、非运行 Markdown、已核验非发布 CI 辅助输入 | 不运行发布生命周期演练，保留相关 required/full/platform 测试 |
| `ci-wiring` | 仅 `platform_ci.py` 或 required workflow 编排，可混合已证明无运行消费者的输入 | `success`、`failure`；保留同镜像过期重验、fresh 授权和真实回滚 |
| `full` | 发布、授权、共享运行身份、持久化/构建合同、演练实现、未知输入或混合发布改动 | 上述两条加 `authorization`、`aged-authorization`、`directory-drift`、`rollback-timeout` |

编排文件在 base 或 candidate 的已提交镜像输入中被消费时不享受两条路径豁免。未知、损坏或缺失来源保持完整演练。非发布 Python 辅助输入及其配套测试另由消费者契约测试确认没有被运行入口、应用或演练加载，新增运行引用必须退出豁免。配套测试的精确豁免集合为 `08_tests/test_full_regression.py`、`test_main_admission.py`、`test_documentation_contract.py` 和 `08_tests/quality/` 下的 `test_release_ci_routing.py`、`test_required_lane_fixtures.py`、`test_ci_dependency_locks.py`；不是整个测试目录的通配豁免。

最终 main check 核验同次 run/attempt、candidate Commit/Tree、声明档位和完整实际路径，并逐一检查原始索引证据哈希。缺少、失败、部分路径、错误档位、不同运行记录或证据漂移均 FAIL；两条编排演练不得冒充六条完整演练。required/full/Windows 覆盖、独立生产授权及实际超时政策保持原约束。

Python 依赖安装可以使用按平台、Python 版本和锁文件身份分键的下载缓存；缓存命中仍执行 hash 校验。Hosted 的 Linux / Windows Python 3.12、Python 3.10 host 工具、浏览器 Python 包与最终聚合器分别使用 [`04_scripts/quality/locks/`](../04_scripts/quality/locks/README.md) 中的完整依赖闭包，安装必须使用 `--require-hashes` 并执行 `pip check`；full candidate 使用 candidate 的 Linux 锁。系统包、字体和 Hosted runner 仍记录实际身份，不宣称由 Python hash 锁固定；同次完整结果和环境身份继续保留。本地及生产继续使用原有根目录 `.txt` 锁，镜像依赖和生产授权不变。环境预检按任务实际依赖选择 python、frontend 或 all；不传参数维持完整预检。

当前 strict / governance 使用单次 candidate full regression；既有 debt ratchet 已退出。发布演练严格按上述密封计划分流：已证明不被运行或发布消费者加载的 full 验证辅助输入及配套测试可为 none；仅 CI 编排为 ci-wiring；发布、运行、演练实现或未知影响为 full。不得跳过计划要求的真实路径，也不得把已核验的非发布辅助输入额外升级为完整演练。CI 中间诊断产物保留14天、最终 main admission 产物保留90天；生产仍需的 CI/发布证据必须在过期前封存到 Git 外的受保护恢复存储，不能仅依赖 GitHub artifact。保留天数不改变 main/production 的身份验证和授权。

Windows Hosted CI 的 Python 环境隔离要求：

- 每个 Windows job 在 runner 临时目录中创建独立虚拟环境，不使用 `--system-site-packages`。依赖安装前核验 `sys.prefix != sys.base_prefix`，避免将项目依赖装入 runner 的全局 Python 环境。
- 安装、`pip check` 和测试必须使用同一虚拟环境的解释器。可以显式调用该解释器，或将虚拟环境的 `Scripts` 目录加入当前 job 的 `GITHUB_PATH`；不修改开发者电脑或服务器的系统 `PATH`。
- 按该 job 的 Python 版本使用对应平台的哈希锁，保留 `--require-hashes` 和 `pip check`。runner 预装工具（如 `pipx`）与项目锁冲突时，先修复环境隔离，不为迁就预装工具而擅自升级项目依赖、修改锁文件或跳过校验。
- 下载缓存仍按平台、Python 版本和锁文件身份分键；不将 runner 的预装包或全局环境作为项目依赖来源。环境准备失败应保留日志并如实报告，修复后重新取得精确候选验证结果。

实现参见 [required workflow 的 Windows job](../.github/workflows/trusted-main-admission.yml)；此规则不改变本地开发环境、生产镜像依赖或日常数据更新流程。

## Runtime 与测试映射

#### Registry/4 runtime intent 与目标验证

`project_registry.py` 同时读取 `project-registry/1` 至 `project-registry/4`。
既有 Registry/3 记录保持原状；版本能力上线不隐式迁移项目，不改变 ownership、
frozen 状态或生产权限。迁移 Registry 至 v4 可与对应源码在同一 candidate 中审查；v4 新增或迁移记录
必须显式提供 `runtime_target`：`none`、`library_only`、`windows_git_worktree`
或 `production_container`，不允许缺省或未知值。旧记录继续按旧版本读取，不能在
旧 schema 偷加 production target 绕过验证；其显式迁移之后启用新门禁。
v4 顶层可提供 `legacy_registry_commit`，必须是可信 origin/main 祖先中的完整 Commit，
其 Registry 必须为有效 v1–v3。只有同时与该历史对象及当前 origin/main 对应记录完全
一致的旧记录，才允许尚未声明 target；任何修改、新记录、历史状态复活或已迁移项目
降级均拒绝。不自动给旧项目填 none/library_only；每条迁移必须独立审计实际 runtime。

当前 Registry 已采用 v4 与显式 `legacy_registry_commit`。`dev-governance` 声明 `none`；
新增 `shared-production-infrastructure` 声明 `library_only`，仅交付跨 Git/OCI 的身份库、
宿主验证工具和签名授权合同，不是业务生产服务。它只拥有 Registry 列出的精确文件，
不拥有治理入口、Dockerfile、Compose 或业务代码；不因此获得部署或数据写入权限。
其他未迁移记录保持旧对象与当前主线双重相等校验。登记通过不表示身份库已实现，
更不表示 Target Runtime Container Validation、AM/PM wiring 或 production release 已通过。

`production_container` 必须提供精确、已存在的 `runtime_contract` 文件路径；禁止
glob、绝对路径、越界、符号链接或 junction，也拒绝跨 build 字段的重复路径/大小写别名。
治理入口严格检查 `runtime-manifest/1`、`runtime-manifest/2` 和 `runtime-manifest/3` 的 project/module/service、target/identity、入口、
容器工作目录、roots/mounts 权限对应、环境/secret引用、依赖、生产/Preview策略和必需
probe集合，以及 Dockerfile、dockerignore、依赖合同和 Compose 源文件路径。实际文件
供给、容器路径/权限与运行语义由独立基础设施验证器负责；静态声明不构成 deployability PASS。

v2/v3 由当前治理 checkout 内的共享解析器按源码字节加载，不使用 caller 的已安装包或 ignored
bytecode。它额外要求明确身份根、初始化 argv 和受控 source inputs，完整合同见
[`生产 Runtime Manifest 合同`](projects/生产RuntimeManifest合同.md)。三个版本的 JSON
均拒绝重复键；这是明确的读取收紧，不允许重复 schema key 把 v2 隐式降为 v1。
v1 的既有结构规则保留，不能因存在 v2 就自动获得新语义。v2 的全部 source inputs、
共享解析器和 Schema 文件均纳入 Git 跟踪、精确文件与 SHA 绑定；缺失、ignored-only、
路径别名、与清单或验证器重复的输入不能用于通过候选验证。host 对 v2 的适配仍须独立验收。

v3 另外要求显式环境绑定、禁止环境变量列表和候选只读输入。治理使用共享解析器的
精确字段与交叉引用规则，确认所有声明文件存在；正式 candidate binding 再逐一检查
fixture 的 Git 跟踪与字节身份。`candidate_runtime_inputs.sha256` 必须等于对应 Git blob
的 SHA-256，fixture 与源码、清单、build/validator 输入的重复或别名均拒绝。Windows
CRLF checkout 可经 Git filter 证明与提交相同，但哈希始终绑定原始 Git 字节；这不允许
真实内容漂移、ignored-only 或未跟踪文件通过。

v1/v2 保持 `target-runtime-validator/1`；v3 必须绑定 `target-runtime-validator/2`，旧版
引擎/记录的 PASS 不能作为 v3 验收。此治理适配不实现新引擎、record、host 或容器授权
消费者；在各自适配与实际验收完成之前，v3 container completion 仍不得 PASS。fixture
只属于候选输入证据，不能进入可提升镜像或生产存储，更不能充当真实 AM/PM 时间验收。

生产容器项目 completion 必须从 clean committed candidate 执行目标验证器，获得
`TARGET_RUNTIME_STATIC_VALIDATION=PASS` 与 `TARGET_RUNTIME_CONTAINER_VALIDATION=PASS`。
原有 Scope、required/future-required tests、拒绝 skip/xfail 和候选不变检查全部保留。
Completion 不接受手写 PASS 或未签名的外部 evidence。默认主动执行候选中固定位置的
`04_scripts/runtime/validate_target_runtime.py`。
入口尚未实现或获准 Linux builder 不可用时 `PROJECT_COMPLETION=BLOCKED`（退出码 3），
不得以 static-only 或 skip 替代完整 PASS。验证器失败、缺少机器证据、身份不符均 FAIL。
非 container target 不强制 Docker；Windows 无 Docker 不等于代码失败。

`target-runtime-evidence/1` 必须绑定完整 Commit/Tree、Runtime Manifest、Dockerfile、
dockerignore、依赖合同、全部 Compose 源和验证器源码的 SHA-256，以及 validator version、
实际 Image ID 和实际 rendered Compose SHA-256。必须提供 Linux 隔离 builder observation、
与 candidate 相符的 OCI/Tree/source/render identity，以及全部正反向 probes 的 PASS。
这些字段由后续 trusted host/CI engine实际采集；字段值本身不是 builder授权或签名。
源码哈希以 Git blob 的原始字节为准，
避免 Windows checkout CRLF 转换伪造身份变化；工作树输入必须仍与对应 Git blob 一致。
绑定对象变化使旧证据失效，不接受其他候选的结果。

跨环境验收可显式使用 `complete_project.py --project <project_id> --candidate-record <绝对路径>`。
此入口仍执行全部 required/future-required tests；仅将本机调用 Docker 引擎替换为验证
同一精确候选的 `candidate-validation-record/1`。记录只能由既有受保护 Linux
`pre_release_runtime.py` 自行执行真实引擎后，以 candidate-validation 域密钥签发；
Completion 不接受原始 `target-runtime-evidence/1`、调用方公钥或调用方 probe 声明。
解析器与 trust 必须先在当前 GitHub main 获批，候选对应 Git blob 必须与 main 相等；
从已批准 Git blob 加载解析器，禁止借候选修改公钥或解析器来自签验收。
origin 必须指向本系统正式 GitHub 仓库；main 必须仍与 origin/main 一致且为候选祖先。
记录签名、目的、域、撤销、有效期、
完整候选 binding 与全部 13 项观察必须通过现有校验。记录位于源码外普通非链接文件，
在全部测试和身份验证期间保持字节不变；验证前后重新核对批准来源、记录及候选。
该模式保留已验证的不可变 Image ID，不再次构建；输出记录其 SHA、record ID、
authority commit 和有效期。非 container 项目不能携带此参数；错误记录直接 FAIL，
不得自动改走本地引擎以掩盖失败。缺少记录时保留原有引擎 PASS/FAIL/BLOCKED 语义。
候选验证记录不等于 Production Approval 或 production write grant；正式发布仍须对实际
生产实例进行 same-image pre-release revalidation。
Registry/4 能力发布本身不表示容器验证器、Production Runtime v2 或业务 wiring 已闭包。

### 3.2 Runtime Mode 与写入保护

`runtime_target=none` 的 ordinary Business 不要求 runtime root、marker 或 production evidence，
无需创建占位 marker。只有实际使用 Runtime 的任务才适用相应 Runtime Mode/root/marker 检查；
高风险 lane 与生产 Runtime 合同不变。

当前 `03_src/agri_research_agent/shared/runtime_context.py` 实现五种 Runtime Mode：

| 模式 | 当前语义 |
|---|---|
| `fixture`（`RuntimeMode.FIXTURE`） | 测试夹具和系统临时目录内的临时 runtime root |
| `isolated-dev`（`RuntimeMode.ISOLATED_DEV`） | feature/worktree 自己的开发 Runtime，只能写自身 root |
| `formal-readonly`（`RuntimeMode.FORMAL_READONLY`） | 可读取经过批准且身份匹配的正式 Runtime，禁止写入 |
| `production-write`（`RuntimeMode.PRODUCTION_WRITE`） | 正式数据更新入口；要求 formal identity、预期 runtime ID、formal classification 和正式门禁 |
| `candidate-validation`（`RuntimeMode.CANDIDATE_VALIDATION`） | 独立临时容器验证；要求候选域执行授权与 candidate-validation marker，不能授权生产写入 |

生产写入须显式选择 Git 或 OCI execution request 并通过对应验证，不作类型探测后的
fallback。Git 路径保持真实检出与 Approved Commit/Tree 检查；OCI 路径需要受信任 host
签名及镜像内身份共同验证，不依赖镜像中的 `.git`。现有 FULL DAILY Wrapper 的独立
bootstrap/Approved 校验不因此被替换。能力进入 main 不表示信任公钥已配置或生产已部署。

Runtime root 使用 `.market-data-runtime.json` 标识。`RuntimeContext` 执行 fail closed：
marker 缺失、runtime identity/classification/module 不匹配、目标 resolve 后越界、
符号链接或 junction 穿越边界、formal-readonly 写入等情况均拒绝。linked Git Worktree
不得进入 production-write；生产正式写入必须来自经过批准的正式入口。该保护只说明
当前 RuntimeContext 已能执行的本地边界，不代表任何未来服务器写入流程已经实现。

### 3.3 Reference Data 与 legacy test-data compatibility

Feature Worktree 因 Git ignore 可能天然没有 `01_data/`、`06_outputs/`、`10_logs/` 等
本地运行内容。不得为了让测试通过而默认复制正式 Runtime、复制
current/previous/release index、创建指向正式可写 Runtime 的 junction/symlink，或让
多个 Worktree 共享 writable Runtime。

开发和测试所需数据按以下优先级选择：

1. fixture；
2. isolated-dev Runtime；
3. 经过批准的只读 reference snapshot；
4. 明确批准的 formal-readonly 数据。

对尚未完全解耦 Git 外历史测试数据的 legacy tests，可以在稳定、只读的参考数据环境
中运行测试，同时显式加载 Feature Worktree 源码。该兼容方式必须记录源码绝对路径、
参考数据来源和只读保证；测试不得更新正式数据，也不得因此获得 production-write。
此方式称为 **legacy test-data compatibility**，不是新业务数据架构的推荐模式。

### 3.4 Python 环境

多个 Worktree 不得同时对同一个 venv 执行安装、升级或卸载。任务不修改依赖且已有
验证过的解释器足以运行测试时，可以通过绝对路径调用该解释器，但必须记录解释器
绝对路径和 Python 版本，并保持依赖环境只读。若 feature 需要新增依赖、改变版本或
重新解析环境，必须使用独立环境，并把依赖变化列入明确开发范围。本文不要求每个
Worktree 机械复制完整 venv。

### 3.5 Scoped Tests 与 module_test_map

`02_configs/module_test_map.yaml` 是代码模块到 `direct_tests`、`impact_tests`、
`dependents` 和 `full_regression_when_changed` 的声明式映射。它提供影响范围事实，
不取代 `04_scripts/quality/run_scoped_tests.py` 测试入口，也不取代
`04_scripts/quality/audit_changed_scope.py` 范围审计入口。

- Direct Tests 验证被修改模块自身；
- Impact Tests 验证其直接依赖和相关业务；
- Full Regression 在公共或高风险模块声明要求、发布条件触发或任务明确要求时执行。

当前 `shared.runtime_context` 属于高风险共享基础，配置为
`full_regression_when_changed: true`。不得把当前某次实施的具体文件数或测试数量作为
长期规则。


## 7. 生产服务器只读身份

服务器读取 GitHub 必须使用：

- 仓库专用只读 Deploy Key；
- 固定 SSH 包装脚本；
- 已核验的 GitHub 主机身份；
- 最小权限和明确文件权限。

禁止：

- Deploy Key 开启写权限；
- 从服务器执行 `git push`；
- 将私钥写入 Git、文档、日志、聊天、镜像或审计文件；
- `StrictHostKeyChecking=no`；
- 用 `ssh-keyscan` 自动接受未知主机；
- 用临时个人凭据替代正式只读身份。

当前公共实例登记见 [`projects/生产只读检出实例登记.md`](projects/生产只读检出实例登记.md)。执行时必须重新核验，不得永久复用文档中的哈希或指纹。

## 8. 服务器可信检出

正式标准是服务器独立只读浅克隆，不使用 worktree。

固定要求：

1. 在全新、唯一的临时隔离目录开始。
2. 使用固定 SSH 包装脚本执行 `git ls-remote`，取得远程 `main` 完整 SHA。
3. 正式部署确认目标完整 SHA 等于本次明确批准的 SHA，且位于刚核验的远程 `main` 历史中；候选快照阶段则核对获批 candidate ref 的在线 SHA 与目标完全一致。
4. 使用只读 Deploy Key 建立独立浅克隆；正式部署取得可信 `main` 中的批准提交，候选快照取得上述获批 ref。浅历史不足以证明祖先关系时，必须补齐所需历史后验证，不得推断通过。
5. 检出目标完整 SHA，并保持 detached HEAD。
6. 核验本地完整 HEAD、Tree SHA、工作区 clean。
7. 执行必要的 `git fsck --connectivity-only`。
8. 记录检出命令、退出码、SHA、Tree 和验证结果。
9. 验证全部通过后，才允许把候选源目录原子发布为隔离的完整 SHA 目录。
10. 只有 `checkout_passed=true` 和 Manifest 通过才允许构建。

可信检出必须使用完整目标 Git SHA。首次检出失败后，必须冻结失败目录及日志，
在新的唯一 `attempt` 目录重新开始；不得在失败的 Git 对象库中继续 fetch、checkout、
reset、repair 或作为构建输入。第二次出现同类对象错误时停止盲目重试，转入文件系统、
并发清理、外层超时、I/O 或 OOM 专项调查。

绝对禁止在 `/home/ubuntu/market-data` 正式仓库中执行：

- 新版本 checkout 或分支切换；
- 依赖安装；
- 测试；
- 镜像构建；
- 作为候选构建上下文；
- 任何会改变正式仓库 HEAD 或工作区的准备操作。

## 9. 候选镜像

所有候选构建必须在隔离候选源目录完成。

候选镜像必须：

- 使用版本化、不可变、绑定 Git SHA 的镜像引用；
- 禁止使用 `latest`、`new`、无标签或 Compose 隐式镜像名作为身份；
- 记录完整 Image ID；
- `org.opencontainers.image.revision` 等于目标完整 Git SHA；
- 记录必要的 source、created、title 和 version；
- 保留原始构建命令、退出码、输出和 inspect；
- 不覆盖当前正式镜像标签或回滚对象；
- 通过目标应用所需的镜像和部署契约验证。

候选容器启动前必须执行 seal preflight，同时验证不可变标签、完整 Image ID、
OCI revision、Git Commit、Git Tree 和 Release 元数据。任一字段缺失或不一致立即
停止；不得修改既有候选结果或失败证据使其看似通过。

OCI revision 只承担完整 Git commit SHA 身份。Tree SHA 不要求写入 OCI
标签；它由可信 `tool_repo_root` 的 `HEAD^{tree}`、Release 产物、镜像内
`/app/RELEASE.json`、候选结果、部署计划、部署结果及各自 Manifest 传播和
验证。

候选验收与正式部署必须复用完全相同的 Image ID。该原则适用于三个正式应用，不因某个应用尚未完成自动化工具建设而降低。

## 10. 候选容器和验收

候选容器必须：

- 只绑定 `127.0.0.1` 测试端口；
- restart policy 为 `no`；
- 正式数据只读挂载；
- 日志、缓存和临时文件写入候选隔离目录；
- 核验容器 ID、Image ID、OCI revision、容器内 `RELEASE.json` 的 Git/Tree
  SHA，以及 Docker inspect 实测运行时 `MARKET_DATA_GIT_HEAD`；
- 检查根页面、健康接口、RestartCount、日志和受影响页面；
- 验证其他生产容器、正式 Git 和业务数据没有变化；
- 截图或浏览器证据必须来自候选容器。

验收结束后：

1. 只有实际候选容器的 Image ID、OCI revision、容器内 Git/Tree SHA 和
   inspect 实测运行时 Git SHA 全部匹配 Release 后，才生成不可覆盖的
   `candidate_result.json`；运行时 Git SHA 不得人工输入。
2. 生成并验证 `candidate_result.manifest.json`。
3. 保存必要日志、inspect、HTTP、页面和数据不变性证据。成功和失败候选均
   使用同一有限日志摘要：最多最后 200 行、最多 64 KiB，记录采集时间、
   原始采样字节数、脱敏尾部 SHA-256、截断状态和 warning/error 数量；不得
   保存无限完整日志、完整 inspect 环境变量或敏感值。日志读取失败只能记录
   受控 `unavailable` warning。
4. legacy 路径的成功候选和失败候选均删除候选容器；1.8.0 HIGH_RISK 的独立 HTTP 候选按第 15 节的资源引用规则清理。
5. legacy 路径重新证明候选容器不存在。
6. 保留已验收候选镜像 Image ID、`candidate-data`、数据 Manifest、候选结果及
   Manifest、失败证据和可信源码身份。
7. legacy 路径只有完成以上步骤，才允许生成 `deployment_plan.json` 和 `deployment_plan.manifest.json`。

候选容器、候选镜像、`candidate-data`、候选运行视图、候选结果和失败证据是不同
生命周期对象。候选容器不得长期保留；候选运行视图可以按证据和批准规则清理。
`candidate-data` 至少保留到 `deployment_result`、其 Manifest 和 bundle Manifest
密封、生产稳定性确认、复盘归档完成且另行获得明确清理授权；不得随候选容器自动
删除。

## 11. 当前强制发布产物

本节下表及 bundle 细则适用于原 legacy 发布工具；ROUTINE_STATELESS 使用 14.4 的普通记录。ADDITIVE_REVERSIBLE 按支持其持久状态合同的工具保存适用证据，免恢复演练不等于免身份或部署结果检查。先确定工具和风险，不把不同工具的产物名称拼成额外 Gate。

1.8.0 HIGH_RISK 使用正式 producer/verifier 密封的 deployment_plan 及 Manifest，绑定受保护的 request、Review、assessment、目标 CandidateValidationRecord、适用的原回滚 acceptance、实例构造和回滚资产。正式执行入口产生不可覆盖的 execution-result.json，记录 target/rollback/cleanup 实际结果和阶段时间；不伪称其已经生成 legacy deployment_result bundle。接口和引用校验见[运行工具说明](../04_scripts/runtime/说明.md)。独立 HTTP 候选与 recovery live 依赖分别管理，按第 15 节清理。

当前强制事实链产物是：

| 目标产物 | 对应 Manifest |
|---|---|
| `release.json` | `release.manifest.json` |
| `candidate_result.json` | `candidate_result.manifest.json` |
| `deployment_plan.json` | `deployment_plan.manifest.json` |
| `deployment_result.json` | `deployment_result.manifest.json` |
| 部署结果集合 | `deployment_result.bundle.manifest.json` |

要求：

- 四类 JSON、对应 Manifest 和部署结果 bundle Manifest 均采用排他创建实现；内容在内存完成序列化和
  校验、临时文件完整写入并 `flush`/`fsync` 后，以硬链接排他创建正式路径，
  不得通过 `os.replace` 覆盖已有目标；
- 每个 Manifest 至少密封目标文件名、SHA-256、字节大小、目标 Schema 版本、生成时间、Release Git SHA、Tree SHA 和 Image ID；候选结果与部署结果 Manifest 还密封容器 inspect 实测的运行时 Git SHA；
- 任何后续阶段读取 `release.json`、`candidate_result.json`、`deployment_plan.json` 或 `deployment_result.json` 前，必须先验证对应 Manifest；
- `release.env` 和 `checksums.sha256` 暂作为 Release 兼容产物继续生成；`checksums.sha256` 仍校验 `release.json` 与 `release.env`，但不能替代 `release.manifest.json`；
- `deployment_plan.json` 必须从已验证的 Release 和候选结果继承 Git SHA、Tree SHA
  与候选 Image ID，并显式记录 `tool_repo_root`、`production_compose_file`、
  `production_project_dir`、Compose 项目名、服务名和独立的
  `deployment_tool_revision`；业务 Release revision 与发布工具 revision
  可以不同，不得因工具升级要求重新构建已验收业务镜像；
- 计划生成前必须只读审计当前生产 Compose、env、容器、镜像、数据、端口和挂载，
  并同时锁定当前基线与目标身份，至少包括
  `production_baseline_compose_sha256`、`production_baseline_env_identity`、
  `production_baseline_image_id`、`target_compose_sha256`、`target_env_identity`、
  `target_image_id`、`target_git_commit`、`target_git_tree` 和目标数据 Manifest；
- 生成计划不得要求生产 Compose 或 env 已经等于目标 Release。Compose 与 env 必须
  一次性审计、一次性预演、一次性纳入计划，并在正式部署事务中联合原子同步；失败时
  按计划锁定的生产基线联合回滚；
- 正式执行 argv 必须直接进入 `deployment_plan` Schema 并由 Manifest 密封。核心
  安全参数变化时必须重新生成计划及 Manifest，不得在计划密封后用独立 execution
  amendment 补充或改变正式切换参数；
- 首次数据发布允许 `first_release=true` 且 `existing_file_count=0`，但必须生成空
  基线 Manifest。非首次发布若正式文件数意外为 0，必须与上一份
  `deployment_result` 对账并停止；
- `tool_repo_root` 是已批准发布工具的独立只读检出；`production_compose_file` 是正式切换实际使用的 Compose 文件；`production_project_dir` 是 Compose 相对路径、挂载源和 `env_file` 的正式解析基准；
- 计划中的生产 Compose 路径必须为经过校验的绝对路径。不得通过脚本目录、当前工作目录或 `/home/ubuntu/market-data` 的 HEAD 隐式推导；
- Release Git SHA、Tree SHA 和候选 Image ID 在候选结果、部署计划和部署结果任一级不一致时必须停止；
- `candidate_result.json` 必须保存候选容器 inspect 实测的运行时 Git SHA
  及有限脱敏日志摘要；其 Manifest 通过目标文件 SHA-256 密封该摘要身份；
  `deployment_result.json` 必须分别保存计划目标 Git SHA、正式容器 inspect
  实测运行时 Git SHA 和验证结果。缺失、空值、冲突值或不一致时不得生成成功结果；
- `deployment_result.json`、对应 Manifest 和 bundle Manifest 是正式部署的强制
  最后阶段；缺少任一产物不得宣称发布完整完成；
- 代码、镜像和运行数据必须形成三条分别密封的身份链：Git Commit/Tree、候选及
  正式 Image ID、逐文件数据 Manifest。代码已进入 Git 不代表数据已发布，镜像验收
  成功也不代表运行数据已发布；
- 缺失事实只能进入明确标记的追溯重建流程，不得伪造原始测量值。

- 浏览器检查 JSON
- 自动化生成的部署前/后生产基线

只有对应脚本、Schema 和测试完成后，才可将增强项升级为强制要求。

上述产物、Tree SHA 传播、候选结果生成、计划生成、正式切换和部署结果记录的候选
实现位于 `09_deploy/spread_release/`，适用于 `spread-dashboard`。当前工具已实现
`current_production`/`target_release`、plan 内 argv、执行前基线防漂移、
执行阶段 env 原子切换与回滚恢复。候选数据生命周期仍按本规范的
独立契约处理。USDA 与 Oil World 必须遵守同一事实链和

另外两个应用已经自动化。

## 12. 正式部署

正式部署必须按已验收工具执行。以下逐项 argv、env 更新和 bundle 名称属于 legacy 路径；1.8.0 HIGH_RISK 使用上述受保护计划及正式 high_risk_execution.py 入口，在锁内完成 preconditions 后精确 stop → create → fresh credential/grant → start → accept → observation，失败按计划 fresh rollback。不得混用 legacy compose-up 入口；两条路径均保留同一 Image ID、独立授权、正式数据和其他服务保全。

legacy 正式部署必须：

1. 获得用户对目标完整 SHA、同一 Image ID 和密封计划的明确批准。
2. 重新验证 Release、候选结果、部署计划及其 Manifest。
3. 从隔离只读检出中的发布脚本执行，并证明 `tool_repo_root`
   的 HEAD 和 Tree SHA 等于计划密封的 `deployment_tool_revision`；
   不得要求它等于业务 Release，也不得要求正式仓库 HEAD 等于新 SHA。
4. 从已验证计划读取 `production_compose_file`、`production_project_dir`、Compose 项目名、服务名和 `candidate_image_id`。
5. legacy 路径证明候选容器已经删除；1.8.0 HIGH_RISK 分开核验 HTTP 候选与 recovery live 依赖，不以删除 rehearsal 作为计划前置。
6. 证明目标 Image ID 与候选验收 Image ID 完全相同。
7. 在任何写入前重新确认实际 env、Compose 和容器仍等于计划密封的
   `current_production`；随后由官方 helper 原子更新 env 为 `target_release`。
8. 从计划读取已经密封的执行 argv，只切换计划指定的目标服务，并同时包含
   `--no-build --pull never --no-deps --force-recreate`。
9. Compose 可以保留静态 `build:` 定义；安全门槛检查实际执行 argv，不得仅因
   YAML 存在 `build:` 就拒绝。正式事务禁止 `docker build`、`docker compose build`、
   `--build`、`latest`、`docker compose down` 和任何 prune。
10. 不无必要地重建或重启其他应用。
11. 核验正式容器实际 Image ID、OCI revision、容器内 Git/Tree SHA 和 Docker
    inspect 实测运行时 `MARKET_DATA_GIT_HEAD`；实测运行时 Git SHA 必须等于
    计划目标完整 SHA，实际 Image ID 必须等于候选结果和部署计划记录值。
12. 验证端口、挂载、环境、HTTP、页面、数据和其他应用不变。
12. 最后生成并密封 `deployment_result.json`、`deployment_result.manifest.json`
    和 `deployment_result.bundle.manifest.json`。

对尚未完成一条式自动化部署的应用，可以使用经过审核的受控步骤，但仍必须满足同一 Image ID、无正式阶段 build、明确回滚对象和强制部署结果要求。工具缺口必须如实记录。

#### 未启动容器授权的分步切换

要求对未启动容器签发 production grant 的 Runtime，可在已审核并密封的计划中使用
`compose create → pre-release → grant → docker start`。实际服务器的 `compose create`
没有 `--no-deps` 参数，因此创建 argv 必须包含 `--no-build --pull never --force-recreate`，
并先验证目标 Compose 仅有本次服务、没有依赖、profiles、links、extends 或 lifecycle hooks。
不得给 create 添加不存在的参数，也不得用 `compose up` 提前启动。
启动 argv 只允许 `docker start <created-container-id>`；该 ID 必须由本次 create 后的 inspect
获得，并与 pre-release 报告和 grant 一致。计划必须事先声明这个唯一实测绑定及完整命令模板，
不得允许操作者另填 ID、修改参数或补写 execution amendment。此命令本身不能构建、拉取镜像或启动依赖。
创建和启动前后均核验 Image ID、配置、挂载、容器清单和其他服务身份；grant 前启动、
额外服务变化或镜像变化立即失败。计划还必须预封旧容器停止与改名保留、失败恢复原名并启动
的精确步骤，并规定服务不可用窗口。此分步方式只替代直接 up 的四参数切换形式，其余事实链、
审批、数据保护、排他封存和回滚要求全部保留。
受控步骤可定义独立的 artifact schema 版本，但仍使用第 11 节的强制文件名及对应 Manifest，
逐阶段验证引用和实测值；不得冒用旧发布工具的 Schema 版本或绕过 Runtime 身份校验。

当宿主 policy 的 `actual_config_sha256` 只能在 create 后测量时，Release 和 Plan 必须在
create 前密封受保护的 `policy_template` 路径、字节 SHA-256、全部静态策略字段、唯一的
最终 policy 路径和派生命令模板。模板只允许缺少 `actual_config_sha256`；该字段必须按
宿主现有 observation 原语对本次 Docker Config、HostConfig、Path、Args 计算，写入
不可覆盖的 `created_instance_binding`。模板不是有效的宿主 policy，禁止将模板哈希、
占位值或预测值称为最终 policy 哈希。

create 后先封存实例 binding，再从已核验模板仅补入 binding 的 `actual_config_sha256`，
排他新建通过既有宿主 parser 的最终 policy。其余字段必须与模板逐字段一致；不得借此
改变角色、镜像、Commit/Tree、挂载、Compose、环境、candidate record 或信任域。随后
排他封存 `policy_binding`，记录 Release/Plan/template/created-instance-binding 和最终
policy 的 SHA-256；pre-release、grant、start 和 Result 均须复核这条派生链及同一实例。
最终 policy 的字节 SHA-256 与宿主报告中的规范化 policy digest 应分别记录和核验。
所有路径、派生字段、校验和 argv 都必须事先进入 Plan；这不是计划密封后追加参数的
execution amendment。旧计划没有该规则时必须重新生成并密封，不能事后补填或覆盖。

创建态与运行态配置摘要必须分别保留原始观测值。Docker Engine `26.1.3`、cgroup `2`
存在已复现的首次 start 转换：`HostConfig.OomKillDisable` 从严格布尔 `false` 变为 JSON
`null`。其依据是 [Moby 对默认值及不支持能力的处理](https://github.com/moby/moby/blob/v26.1.3/daemon/daemon_unix.go)。
只允许在新 Plan 的 `checks.start_config_transition` 中预封该版本、cgroup、字段、前后值
及唯一输出路径，并新增紧随 start、先于 health/consumer 的 `validate_start_transition`
argv。创建、pre-release、grant 前仍须按现有原语精确核对创建态原始摘要；不得改写
created binding、policy、grant，或把规范化值声称为 Docker 原始观察。

启动后先计算完整 Config、HostConfig、Path、Args 的真实原始摘要，再仅在比较副本中
将实际存在的该 `null` 还原为 `false`；副本完整摘要必须等于 created binding 摘要。
字段缺失、`true`、数值 `0`、其它配置变化、引擎或 cgroup 不符均失败。排他封存
`controlled-runtime-start-transition/1` 见证，记录 Plan/binding/实例/镜像身份、版本、
字段和实测前后值、创建态/运行态/比较副本摘要及观察时间。Result 原有
`actual_config_sha256` 保存真实运行态摘要，原有 `binding_sha256` 继续引用创建态；
不增加 Result 顶层字段。Bundle 必须增加唯一 `start_transition` role，并交叉核对
见证路径、Plan、binding、policy/grant/pre-release 的创建态摘要、Result 运行态摘要，
以及唯一成功的见证步骤。后续运行态观察必须精确等于首次运行态摘要，不能反复容忍
转换或反向漂移。见证包含 `failure_reason`：PASS 时为 null；转换校验失败时必须封存
FAILED 见证、固定失败原因和所有已实测摘要，只有无法取得的观测摘要允许为 null。
失败见证须绑定失败步骤及 FAILED/ROLLED_BACK Result，不能转为成功。仅在 start 未成功
且见证步骤尚未执行时可使用原有未执行占位；禁止把已执行但失败的见证伪装成未执行。
这仅是上述已测部署启动转换的规则，不改变 Runtime 验签、权限、时效或通用身份算法。

受控执行须读取最新已明确批准的治理说明，并在 Release/Plan 中单独固定其完整
`governance_revision` Commit/Tree 和文档 SHA-256；运行时不得自动跟随 main。该治理
身份与发布工具 revision、目标业务 Commit/Tree 和已验收 Image ID 分别绑定。治理说明
更新不会自动升级目标生产镜像，也不修改 Runtime 的验签、grant 有效期或续签能力。

## 13. 生产身份

本章镜像身份针对代码部署；FULL DAILY 数据更新不以开发 caller 的 main/clean 身份为门禁。
其正式身份是 Approved Production Commit/Tree、clean detached control-plane 与 tool-repo，
实际业务入口/import/cwd 来自 tool-repo。运行说明统一见 [Windows Wrapper](../04_scripts/automation/说明.md)。

Prewarm 不参与 DATA_READY 核心判定；Prewarm Separation 仍为未闭包 candidate，不得宣称已生产启用。

不得使用以下单一信息证明生产版本：

- 目录修改时间；
- 容器名称；
- 镜像标签字符串；
- GitHub main；
- 旧容器 `Config.Image`；
- `latest` 或 `new`。

- `deployment_result.json` 和 Manifest；
- 正式容器实际 Image ID；
- OCI revision；
- 容器内 `RELEASE.json` 的完整 Git SHA 和 Tree SHA；
- Docker inspect 从 `Config.Env` 实测的 `MARKET_DATA_GIT_HEAD`，以及它与计划
  目标完整 SHA 的验证结果；

- HTTP、页面和数据挂载状态。

## 14. 回滚

回滚对象必须在部署计划中明确并经过预校验：

- 上一完整 Git SHA；
- 上一可用 Image ID；
- 生产基线 Compose、env、数据 Manifest、正式容器配置、端口、挂载和环境；
- 回滚脚本或受控步骤；
- 健康检查和数据不变性验证。

回滚禁止重新构建镜像、使用 `latest` 猜测旧版本或删除失败证据。

`spread-dashboard` 使用仓库当前密封 Release 契约指定的部署和回滚脚本。USDA、Oil World 在自动化完善前必须保留明确的上一 Image ID 和受控回滚记录。

### 14.1 发布风险与回滚资产

发布准备使用 `04_scripts/runtime/pre_release_runtime.py` 的 release assessment；不得把
运行容器历史 execution grant 仍有效作为所有 release 的回滚前提。以下状态独立：

- `ROLLBACK_ASSETS_READY`：当前及上一正式版本的完整 Commit/Tree、不可变 Image、
  Release Manifest、可恢复 Compose/env 配置、data/schema 身份和 fresh recovery 步骤均已核验。
- `EXECUTION_AUTHORIZATION`：真正 fresh create/start、restart/recovery 的实例授权。
  创建仍先于签发；启动必须在 fresh grant 有效期内、绑定同一 created instance。
  已运行 production 的存在和健康不因历史 grant 到期而失效；这不撤销 Runtime 对后续
  受保护操作的验签和写入前校验，也不允许复用、续期或为已启动实例补签旧 grant。
- `ROLLBACK_REHEARSAL_REQUIRED`：由机器风险分类决定的真实恢复验证要求。

`ROUTINE_STATELESS` 必须证明无不可逆状态变化、数据/schema 兼容、回滚资产齐全、
新 candidate 验证通过和生产验收计划齐全；不强制恢复演练，历史 grant 过期不单独失败。
UI、presentation、无状态逻辑和只读 consumer 是低风险候选类型，不是文件名豁免。
`STATEFUL_OR_INFRA` 保留上述有状态、Runtime/Compose/mount、授权及未知执行代码风险，
但不自动要求完整 rollback rehearsal。验证深度取决于机器证据、可逆性及有效 Maintainer risk review：

| 分类 | FULL_ROLLBACK_REHEARSAL_REQUIRED | TARGETED_RECOVERY_VALIDATION_REQUIRED |
|---|---|---|
| ROUTINE_STATELESS | NO | NO |
| STATEFUL_OR_INFRA + ADDITIVE_REVERSIBLE | NO | NO |
| STATEFUL_OR_INFRA + IRREVERSIBLE_OR_DESTRUCTIVE | YES | YES |
| STATEFUL_OR_INFRA + NEEDS_MAINTAINER_RISK_REVIEW | 暂按 YES | YES，等待风险 review，不自动 PASS |

`STATE_CHANGE_CLASS` 从 exact base/target 的 code/runtime delta 生成；caller flag、metadata
或 state_plan 声明不得降低机器风险。ADDITIVE_REVERSIBLE 要求新增独立持久存储、既有数据/
schema/挂载不变、无删除/迁移/单向转换、旧版本不破坏新 state、原 target 重挂同一来源可读。
当前 `release_reversibility.py` 保留有界静态证明，不继续为每个业务 env/function 扩展分析器。
机器独立输出 MACHINE_DESTRUCTIVE_EVIDENCE 和 MACHINE_STATE_CHANGE_CLASS：
明确发现 schema migration、existing history rewrite/delete、one-way conversion 等破坏性
证据时为 YES，人工不得降级；NO 只表示未发现明确证据，不是证明没有任何风险。
NO 且完整证明 additive 时自动得到 ADDITIVE_REVERSIBLE；NO 但遇到 unsupported
business/config semantics 时得到 NEEDS_MAINTAINER_RISK_REVIEW，不等价于 irreversible，
也不自动 PASS。缺失/无效证据及 state_plan 的 irreversible=UNKNOWN 仍停止。

Maintainer 根据 code diff、tests、存储路径、migration facts、rollback compatibility audit
记录 ADDITIVE_REVERSIBLE 或 HIGH_RISK。普通 JSON assessment 的 maintainer_risk_review
包含 reviewer、timestamp、base/target（Commit/Tree）、authoritative_main（Commit/Tree）、
machine_findings、maintainer_classification、reason；保留机器原结论和人工结论，不能改写
机器 findings。机器 YES 时 additive decision 必须拒绝；HIGH_RISK 继续完整恢复要求。
这属于 release risk review，不是 Governance bypass；没有新 approval server、签名 token
或新 workflow。真实 candidate/恢复证据的既有身份与 execution grant 检查不变。

review 消费时实时读取 origin main，并重算 exact base/target 的机器 findings；任一 Commit/
Tree/main/findings 改变均失效，评估结束再次核对 main。旧评估器输出不能当作新 review。
Routine 无需 review。review 不能覆盖候选机器失败、真实 destructive evidence、
未知数据兼容性或 fresh grant 失败；它只确认可逆性分类，不是生产授权。
`ROLLBACK_REHEARSAL_REQUIRED` 是 FULL_ROLLBACK_REHEARSAL_REQUIRED 的兼容字段。

Additive 的强制路径是 exact base/target 可逆性分类、自动兼容性检查、同一镜像 Candidate
机器检查与 Maintainer 业务验收、同一镜像生产切换、生产机器检查和最终人工验收。
`FULL_ROLLBACK_REHEARSAL_REQUIRED=NO` 且 `TARGETED_RECOVERY_VALIDATION_REQUIRED=NO`。
真实 targeted recovery 是可选诊断/独立加固；若主动提交证据仍须通过原验证器，失败不能伪装成 PASS。
旧版不必理解新数据，但旧版不得修改或删除新状态，兼容 re-upgrade 必须可重新读取。
不可逆/破坏性迁移仍需完整 recovery rehearsal 和另行批准的数据迁移流程；演练 PASS
不能自动授权不可逆迁移。NEEDS_MAINTAINER_RISK_REVIEW 不因完整演练 PASS 自动完成风险 review。

已由机器证明或有效 Maintainer risk review 接纳为 additive 的发布可使用短 Maintenance Window：production switch → machine
smoke → Maintainer manual UI acceptance。最终确认前不进行真实 CNF save，确认后恢复正常
业务操作。这是操作纪律，不新增 enable/disable 状态机，也不允许人工覆盖机器失败。
Routine Release 的现有入口和验收语义不变。

风险分类从精确 Git 两端及 base 已登记 Runtime build contract 读取完整 diff，包含删除。
`RUNTIME_EFFECTIVE_DELTA` 分开记录打包范围和运行作用范围。以两端 runtime entrypoint、
initialization commands、Compose 文件引用为根，追踪本地 Python imports（含函数内部及两侧
分支）、包初始化、literal module load 和文件/basename 引用。source_inputs 是打包身份清单，
不是“全部执行”的声明。完整静态闭包之外、仅被 COPY 的工具记录 `PACKAGED_INACTIVE_CHANGE`；
运行闭包中的变化记录 `RUNTIME_ACTIVE_CHANGE`。未知动态代码加载不允许证明工具不活跃。
不支持或变化的 build、Compose、环境、挂载、依赖和 runtime identity/grant 合同，以及
DB/schema/migration、生产数据写入仍升级风险；不能因为“不常运行”而豁免 scheduler/provider。
普通 application executable change（页面、计算、校验、应用层读写授权控制）本身不是状态变化；
在没有新持久状态、存储路径/格式、迁移或部署合同变化且静态执行作用可证明时可为
ROUTINE_STATELESS。presentation 按新增执行作用检查：允许本地 list/dict/month shaping、
只读时钟和可追踪无状态 helper，保留未变化操作；新增未知调用、参数/全局写入或持久写入
仍升级风险。它是可审查的静态
风险模型，不是任意 Python 的完整无副作用证明，也不能替代实际 candidate/consumer 验收。
调用者没有 low-risk 覆盖参数，报告绑定完整 base/target Commit/Tree、运行闭包和逐文件原因。
受保护 state plan 中的迁移事实只能提高风险，不能降低 Git 检测的风险。

### 14.2 发布评估与恢复实现

正式评估使用受保护的精确源码、候选记录、state plan、acceptance plan 和上一版本回滚资产；结果不是生产授权。Routine 与已证明 ADDITIVE_REVERSIBLE 可令 recovery_evidence 为 null；不可逆/破坏性风险继续走正式高风险验证，UNKNOWN 不得自动放行。

请求字段、签名 grant、rollback asset、恢复 namespace 投影和实际 observation 的实现合同见[底层 Runtime 说明](../09_deploy/runtime_identity/说明.md#release-assessment-parser-与受保护输入)。普通业务开发者无需执行 recovery 工具。任何主动提交的 recovery evidence 仍须由原验证器严格验证；失败不得改称 PASS。

### 14.3 回滚资产与 Runtime namespace

保留当前及上一正式版本的 Commit/Tree/Image、Manifest、Compose/env、必要 data/schema
身份和受控恢复步骤；只有 local Image ID 时明确标记不覆盖 host loss。恢复 namespace
与 artifact identity 分开核验，不改变业务 env、历史来源或 RO/RW。具体网络投影、grant
和 Docker 兼容规则只在[底层 Runtime 说明](../09_deploy/runtime_identity/说明.md)定义。

独立授权的 isolated recovery rehearsal 可按底层严格 sandbox contract，将原 RW host
source 替换为 root-controlled allocation 内的独立普通字节副本/空目录。所有 container
target、RO/RW 及原有 RO/RW source alias 关系必须保留；其他生产只读输入不变。
这是 rehearsal 的显式例外，不修改正式 deployment source，不授权真实生产写入，
不降低风险或更换身份模型。真实证据仍要求 production-domain grant；Hosted 不能替代。

### 14.4 Candidate 与 Production 同镜像发布

机器直接分类为 ROUTINE_STATELESS，或机器无 destructive evidence 且 coverage limitation 经绑定 exact base/target/tree、authoritative main、diff、machine findings 和完整 state/infra 事实的 Maintainer review 正式解析为 `FINAL_RELEASE_TREATMENT=ROUTINE_STATELESS`，可使用既有 `04_scripts/runtime/routine_release.py`。任何 persistent/write/storage/schema/data/mount/deployment/network/stateful unresolved 事实均禁止人工解析为 Routine；机器 destructive evidence 永远不能覆盖。已证明 ADDITIVE_REVERSIBLE 沿用 stateful 评估和受保护候选合同，但不要求 targeted/full recovery rehearsal。两者均按 Build Once → exact image Candidate → machine smoke → Maintainer UI/business acceptance → Deploy Same Image → Production machine smoke → Maintainer final acceptance → deployment record；不能由人工覆盖机器失败。

Candidate 必须独立 project/container/network，localhost-only；Production-backed inputs RO，必要 RW 仅落 candidate-owned isolated storage。fresh instance/grant、Commit/Tree/Image、Manifest、mount/network identity、runtime preflight、health/HTTP 仍是硬 Gate。MANUAL 不要求 Playwright/Chromium；AUTOMATED 保留浏览器真实页面验证。MANUAL 机器通过后 `WAITING_FOR_MAINTAINER_UI_ACCEPTANCE` 不是最终 PASS，用户确认前不得 production switch。候选与正式部署必须复用完全相同的 Image ID。目标工具 Commit 与 Application Target Commit 可分离核验。

具体命令、请求字段、同一镜像记录、candidate-ui/production-ui 和失败回滚处理见[Routine Release 实现说明](../04_scripts/runtime/说明.md)。高风险仍使用独立严格发布流程，不进入 Routine 入口。

## 15. 清理

清理是独立任务。默认禁止：

```text
docker system prune
docker image prune
docker image prune -a
docker volume prune
docker compose down
```

清理前必须盘点容器、镜像、构建源、`candidate-data`、Release、候选结果、计划、
部署结果、Manifest、回滚对象、失败证据和磁盘使用。

任何删除对象必须同时满足：

1. 不是当前正式对象；
2. 不被任何容器引用；
3. 不被发布事实链或 Manifest 作为必需实体引用；
4. 不是唯一回滚对象；
5. 不是事故复盘的唯一证据；
6. 有明确对象名、完整 ID 或经核验的绝对路径；
7. 已获得单独批准。

发布完成记录同时列出资源状态和精确清单：等待验证、等待页面验收、当前生产、保留回滚、失败待排查、已归档、待清理、已清理。记录对象 ID/路径、所属 release、消费者引用、恢复来源和变更时间；清单可由现行工具或人工汇总生成，不宣称工具已自动实现归档或删除。等待验收与失败未终结对象不能因超时变成垃圾；`已归档` 不自动等于 `待清理`。

至少保留每个服务当前正式版本与上一可用回滚版本，以及它们的完整依赖闭包、数据兼容恢复材料、唯一备份和必要失败证据，不把“保留两个镜像”当作删除其余镜像的充分条件。已结束、无 live/必需事实引用的历史源码和工具副本可以在完整备份、逐项校验及独立清理授权后迁出服务器，保留恢复索引和事实；不得改写 Manifest 或历史路径来伪造无引用。恢复未实测时如实记录验证程度。

系统日志、业务日志、Docker 日志和 CI 产物的期限按[数据规范第8节](02_数据与输出规范.md#8-备份保留和清理)分别管理。可再生成缓存按已盘点对象处理；没有自动 prune、发布后自动删资源或新增定时任务。本规则修改不改变服务器当前日志配置。

legacy 候选容器必须在部署计划前删除。1.8.0 HIGH_RISK 独立 HTTP 候选在验收完成且没有后续 live 引用时可停止，并在正式验收后删除；必须记录引用检查与精确实例。恢复 rehearsal、sandbox 和 grant 保留至最后消费者完成及执行终态，失败待恢复资源不提前删除。候选镜像、
`candidate-data` 和候选证据仍按上述规则保留和评估。结果链未全部密封、生产尚未
稳定、复盘未归档或没有独立清理授权时，不得清理 `candidate-data`。

## 16. 停止条件

以下任一情况必须停止：

- baseline HEAD/Tree 不一致；
- Feature Worktree 不在预期 branch，或存在无法解释的工作区修改；
- 输入数据或 Reference Data 身份无法确认；
- 实际使用 Runtime 的任务，其 Runtime Mode、marker、module 或 resolved root 无法确认；
- 正式 Runtime 被错误赋予写权限，或 linked worktree 试图进入 production-write；
- 修改超出 Change Boundary；
- Shared Dependencies 的修改扩大了影响面，但测试范围未重新计划；
- required Direct/Impact/Full Tests 或本地页面/业务验收失败；
- Git root、common dir、branch、Commit 或 Tree 身份不一致；
- 正式部署目标 SHA 未进入已在线核验的远程 main 历史，或不等于明确批准的生产 SHA；
- 独立候选获取的 SHA 不等于获批 candidate ref 的在线实测 SHA；
- 只读身份、主机身份或包装脚本无法核验；
- 检出不是 detached HEAD、工作区不干净或 fsck 失败；
- 候选源位于正式仓库；
- 候选或正式 Image ID 不一致；
- legacy 候选容器未在计划前删除，或任何路径提前清理仍被 live 消费的恢复资源；
- 计划要求生产 Compose/env 预先等于目标，或没有同时锁定当前基线和目标身份；
- 正式执行 argv 缺少四个安全参数，或包含实际 build、`latest`、`down`、prune；
- 计划密封后试图通过独立 amendment 改变核心执行参数；
- 数据、挂载或其他应用出现非预期变化；
- 回滚对象不明确；
- 强制产物或 Manifest 缺失；
- 用户已有修改、生产事实或文件身份无法解释。

触发停止条件后，不得通过复制未知数据、修改正式 Runtime、扩大权限、跳过测试或
直接去服务器验证来绕过停止点。



START / RESUME 会 fetch 并写 local Git metadata，不是纯 read-only。开发启动不依赖无关 local main checkout 是否 clean、mirror；只有实际 main 同步才核验镜像。runtime_target=none 不要求 runtime root、marker 或 production evidence。可选工具入口 `start_project.py --project <id> --branch feat/<name> --worktree <path> --create`；直接创建 feature/fix branch 同样合法。普通已授权任务无需重复 commit/push 许可。

`complete_project.py --candidate-record <记录>` 是可选专项验收；若调用，全部 required tests 与签名容器门禁仍完整执行，不是 main-entry 前置条件。

执行 `git fetch origin`、`git ls-remote origin refs/heads/main` 核对 fresh main；聊天历史 SHA 不是执行权威。
Prewarm Separation 仍为未闭包 candidate；此次 CI 简化不改变生产功能状态。

### Production tooling 源码与生产状态

Main Admission 的 `checks.production_artifact_roles` 区分 repository definition 与 live instance。
`09_deploy` 不是目录级禁改区：Python/Shell/PowerShell 工具、JSON schema、工具配置、
Compose/Dockerfile 源文件、环境示例和模板属于 `PRODUCTION_TOOLING_SOURCE_CHANGE`，
进入 Shared/Infra testing；同时修改 Governance/CI 时按 Governance/CI 审查。
保持 base required/impact/full 与 candidate 新增测试，不要求 ownership bootstrap。

data/output/log、实际 .env、live/state/runtime/release/evidence/grant/secret allocation、
私钥、数据库和未知部署产物仍为 `PRODUCTION_MUTATION`。结构化实例中的 grant/policy/
signed-record/controlled-runtime schema、实例和生成时间身份优先于普通配置扩展名；
`.schema.json` 中描述这些字段的 schema definition 不等于实例。比较 diff 两侧，不能通过
删除、重命名或把旧 state 内容改成配置来隐藏 mutation。`04_scripts/runtime` 是既有工具
源码包，内部 live/state 子目录不因包名取得豁免。维护规则在既有 Admission classifier，
不创建新权限服务，也不依赖项目 owner 才能启动。

此分类只判断 Git artifact，不执行脚本，不证明任意源码无副作用。源码定义包含 deploy、
restart、grant 签发或数据库写入函数，仍是待测试/审查的代码；实际调用这些函数、修改服务器
环境、操作容器生命周期或生产数据，继续由独立 Production Release/数据授权合同控制。
`MAIN_ENTRY != PRODUCTION_RELEASE_AUTHORIZED`，main PASS 的生产授权字段仍为 false。
不得把源码分类 PASS 当成部署、生产 grant 或数据写入许可。

Routine 人工验收是正常 release checkpoint，不是 Governance approval。如果自动化低风险 UI 验收显著增加基础设施复杂度而人工成本低，默认允许人工验收，不为自动化率强制新增基础设施。
