# 标准开发与生产发布规范

> 文档状态：当前权威规范。本文用“必须、不得、应当、停止”定义开发、测试、Git、候选构建和生产发布的强制边界；逐步操作见 [`04_开发与发布检查清单.md`](04_开发与发布检查清单.md)。

## 0. 规范边界与用语

本文只定义长期、通用且可执行的约束，不记录某次发布的容器 ID、镜像标签、IP、
环境变量值或临时目录。此类事实只能作为带日期的实例保存在 `archive/`、密封发布
产物或生产基线中，执行时必须重新核验。

- **必须**：缺失即不得进入下一阶段。
- **不得**：禁止的行为；即使某次操作看似成功也不能作为例外。
- **应当**：默认做法；若不采用，必须记录原因、风险和替代验证。
- **停止**：保持已验证对象不变，报告已确认事实；不得用猜测、降级断言或旁路继续。

规范、手册、模板和归档的职责由 [`00_文档索引与适用范围.md`](00_文档索引与适用范围.md)
定义。下级文档不得放宽本文；手册不得把尚未通过真实候选门槛的工具称为正式生产工具。

## 1. 适用范围

本文定义 `market-data` 单仓库的标准开发、测试、Git、GitHub、服务器可信检出、候选镜像、候选容器、正式部署、部署结果、回滚和清理规则。

`09_deploy/spread_release/` 中的实现能力必须以当前代码、Schema、测试和真实候选
验收为准。2026-07-22 全天气发布的完成不代表复盘提出的工具整改项已经实现；
任何工具升级必须另行开发、测试并完成候选发布，不得由本文规则反推工具已经具备
相应能力。USDA 和 Oil World 的一条式工具仍待实现。

适用于：

- `spread-dashboard`
- `usda-dashboard`
- `oil-world-dashboard`
- 后续纳入本仓库的农产品研究应用

项目契约可以增加更严格要求，但不得降低本文的 Git 身份、同一 Image ID、数据保护和生产停止标准。

所有阶段还必须遵守以下跨文档硬边界：

- ChatGPT 会话沙箱、Windows 本地仓库、Codex 可执行环境和 Ubuntu 生产服务器相互隔离；路径不是文件身份，跨环境必须显式传输并重新核验。
- 本地正式验证使用 `.venv-py312` 与 Python `>=3.12,<3.13`；前端使用 Node `>=24,<25`、Corepack 管理的 pnpm `10.12.1`、`pnpm install --frozen-lockfile`。环境不满足时停止，不自动安装或使用替代工具。
- 业务代码和业务数据分离。正式数据默认只读挂载；候选不生成、不填补或覆盖正式数据，除非任务明确是经过独立授权的数据发布。
- 本地 Windows 是开发源，GitHub `main` 是代码交换与身份真源；服务器只通过已核验 Deploy Key 获取目标完整 SHA，不承担日常开发。
- 三服务的 Compose 所有权、项目名、端口和运行边界以 `01`、目标独立 Compose 与实际配置为准。单服务操作不得隐式解析、重建或重启另两个服务。

## 2. 唯一正式链路

```text
任务定义
→ 确定 Project
→ 声明 Change Boundary
→ 确认基线身份
→ 建立或进入 Feature Worktree
→ Worktree Preflight
→ 选择 Runtime Mode
→ 确认输入数据 / Reference Data
→ 本地开发
→ Direct Tests
→ Impact Tests
→ 必要时 Full Regression
→ 本地页面 / 业务验收
→ 范围审计
→ 显式 Git 提交
→ 集成稳定 main
→ 普通 fast-forward 推送 origin/main
→ 服务器独立只读浅克隆完整 SHA
→ 隔离目录构建候选镜像
→ 候选容器验收
→ 密封 candidate_result 和证据
→ 删除候选容器
→ 密封 deployment_plan
→ 用户批准
→ 使用同一 Image ID 正式切换
→ 密封 deployment_result、Manifest 和 bundle Manifest
→ 验证生产身份和数据不变性
```

本地开发和必要验收完成前，不得用候选服务器或正式服务器代替本地开发测试。
Feature Worktree 本身没有候选、生产或部署权限；进入候选阶段仍须获得独立授权，
并完整遵守本文既有的可信检出、同一 Image ID、结果密封和回滚规则。

`main` 在远程表示可信主线，在本地工作区表示稳定集成线；两者都不表示当前生产
版本。生产身份必须由部署结果、Manifest、生产基线、正式镜像 ID 和运行容器注入
的完整 Git SHA 共同证明。

## 3. 开发前范围契约

每次开发开始前必须填写 Change Boundary / Execution Contract，至少明确：

- `Project`；
- `Baseline HEAD / Tree`；
- `Workspace / Worktree`；
- `Allowed Paths`；
- `Shared Dependencies`；
- `Forbidden Paths`；
- `Required Tests`（Direct、Impact、是否要求 Full）；
- `Runtime Mode` 和正式 Runtime 访问权限；
- `Data Input / Reference Data`；
- `Deployment Permission`；
- 回滚要求和 `Stop Conditions`。

`Allowed Paths` 是本次默认可写范围。`Shared Dependencies` 是项目可能调用、但不因
调用而自动获得修改权限的公共模块。修改 Shared Dependencies 前必须重新评估
Change Boundary，并依据 `02_configs/module_test_map.yaml` 扩大测试范围。
`Forbidden Paths` 默认不可修改；如果实施中确实需要修改 forbidden 或未批准的
shared 路径，必须停止当前实施并重新取得范围决定，不得静默扩大任务。

不得在开发或发布过程中无依据扩大范围。发现无关测试数据、历史模块或其他应用阻断任务时，应先判断是否真的属于本次风险，而不是通过修改无关对象绕过失败。

### 3.1 main 与 Feature Worktree

本地 `main` 工作区是稳定集成线，主要用于稳定基线、只读审计、集成已完成的
feature、集成测试和进入后续发布流程。新的、持续时间较长或与其他项目并行的
feature 默认使用独立 Git Worktree；价差、品种榨利、外盘持仓等后续并行项目应
优先采用该方式。非常小、范围明确且不会造成并行工作区冲突的维护任务，可以按
任务的明确权限直接处理，不强制为每一行修改创建 Worktree。

并行 feature 不得共享同一个可写源码工作区。每个 Feature Worktree 必须具有明确的
project、branch、baseline、Change Boundary 和 Runtime Mode。创建或进入 Worktree
后的 preflight 至少核验：

- Git root 和 Git common dir；
- branch、完整 HEAD、Tree 和 `git status --short`；
- Change Boundary、Shared Dependencies 和 forbidden paths；
- Runtime Mode、resolved runtime root 和 `.market-data-runtime.json`；
- Python/测试入口和必要输入身份。

Feature Worktree 默认 `deployment_permission = none`。创建 branch 或 linked worktree
不会自动授予 candidate、production、production-write、push、merge 或部署权限。
[`04_开发与发布检查清单.md`](04_开发与发布检查清单.md) 第 5 章所称“Windows 正式
仓库”，在本流程中指属于唯一 Git 基线、经过核验的本地源码工作区，可以是获批的
Feature Worktree；它不表示并行 feature 应长期直接写入本地 `main` 工作区。

### 3.2 Runtime Mode 与写入保护

当前 `03_src/agri_research_agent/shared/runtime_context.py` 实现四种 Runtime Mode：

| 模式 | 当前语义 |
|---|---|
| `fixture`（`RuntimeMode.FIXTURE`） | 测试夹具和系统临时目录内的临时 runtime root |
| `isolated-dev`（`RuntimeMode.ISOLATED_DEV`） | feature/worktree 自己的开发 Runtime，只能写自身 root |
| `formal-readonly`（`RuntimeMode.FORMAL_READONLY`） | 可读取经过批准且身份匹配的正式 Runtime，禁止写入 |
| `production-write`（`RuntimeMode.PRODUCTION_WRITE`） | 正式数据更新入口；要求 formal identity、预期 runtime ID、formal classification 和正式门禁 |

Runtime root 使用 `.market-data-runtime.json` 标识。`RuntimeContext` 执行 fail closed：
marker 缺失、runtime identity/classification/module 不匹配、目标 resolve 后越界、
符号链接或 junction 穿越边界、formal-readonly 写入等情况均拒绝。linked Git Worktree
不得进入 production-write；生产正式写入必须来自经过批准的正式入口。该保护只说明
当前 RuntimeContext 已能执行的本地边界，不代表任何未来服务器写入流程已经实现。

### 3.3 Reference Data 与 legacy test-data compatibility

Feature Worktree 因 Git ignore 可能天然没有 `01_data/`、`06_outputs/`、`10_logs/` 等
本地运行内容。不得为了让测试通过而默认复制正式 Runtime、复制
current/previous/release index、创建指向正式可写 Runtime 的 junction/symlink，或让
多个 Worktree 共享 writable Runtime。

开发和测试所需数据按以下优先级选择：

1. fixture；
2. isolated-dev Runtime；
3. 经过批准的只读 reference snapshot；
4. 明确批准的 formal-readonly 数据。

对尚未完全解耦 Git 外历史测试数据的 legacy tests，可以在稳定、只读的参考数据环境
中运行测试，同时显式加载 Feature Worktree 源码。该兼容方式必须记录源码绝对路径、
参考数据来源和只读保证；测试不得更新正式数据，也不得因此获得 production-write。
此方式称为 **legacy test-data compatibility**，不是新业务数据架构的推荐模式。

### 3.4 Python 环境

多个 Worktree 不得同时对同一个 venv 执行安装、升级或卸载。任务不修改依赖且已有
验证过的解释器足以运行测试时，可以通过绝对路径调用该解释器，但必须记录解释器
绝对路径和 Python 版本，并保持依赖环境只读。若 feature 需要新增依赖、改变版本或
重新解析环境，必须使用独立环境，并把依赖变化列入明确开发范围。本文不要求每个
Worktree 机械复制完整 venv。

### 3.5 Scoped Tests 与 module_test_map

`02_configs/module_test_map.yaml` 是代码模块到 `direct_tests`、`impact_tests`、
`dependents` 和 `full_regression_when_changed` 的声明式映射。它提供影响范围事实，
不取代 `04_scripts/quality/run_scoped_tests.py` 测试入口，也不取代
`04_scripts/quality/audit_changed_scope.py` 范围审计入口。

- Direct Tests 验证被修改模块自身；
- Impact Tests 验证其直接依赖和相关业务；
- Full Regression 在公共或高风险模块声明要求、发布条件触发或任务明确要求时执行。

当前 `shared.runtime_context` 属于高风险共享基础，配置为
`full_regression_when_changed: true`。不得把当前某次实施的具体文件数或测试数量作为
长期规则。

## 4. 本地开发和测试

1. 读取 `AGENTS.md`、[`00_文档索引与适用范围.md`](00_文档索引与适用范围.md)、本文、[`05_执行环境与跨环境传输规范.md`](05_执行环境与跨环境传输规范.md) 和相关项目契约；日常更新任务同时读取 [`06_日常运行与数据更新手册.md`](06_日常运行与数据更新手册.md)。
2. 确定 Project，填写 Change Boundary，并记录 baseline HEAD/Tree。
3. 建立或进入批准的 Workspace/Feature Worktree，完成 Worktree preflight。
4. 选择 Runtime Mode，确认输入数据、Reference Data 和 Python 解释器身份。
5. 识别用户原有修改和未跟踪文件，不覆盖、还原或夹带；只修改 Allowed Paths。
6. 先运行 Direct Tests，再按 `module_test_map` 和实际依赖运行 Impact Tests；满足声明条件时运行 Full Regression。
7. 运行必要的 Python、前端、页面、业务验收、静态部署契约和语法检查。
8. 使用 `audit_changed_scope.py` 或等价明确证据完成范围审计，并运行 `git diff --check`、审查 diff、stat 和 name-status。
9. 确认未越界修改业务数据、凭据、日志、cron、Docker、Compose 或服务器配置；只有获得独立授权才进入 commit、main 集成或后续发布阶段。

Windows 本地没有 Docker、Podman 或 WSL 属于正常状态。本地不负责生产镜像构建，也不得要求为本项目安装这些工具。

紧急线上修复也不得在服务器形成独立代码分支。为止损而采取的任何代码修复，必须回流本地唯一开发源，完成测试、显式提交和 main-first 推送，再按本文完整发布链生成新的 Release、候选、计划和部署结果。

## 5. Git 提交

只能使用显式路径暂存：

```powershell
git add -- path/to/file1 path/to/file2
```

禁止：

```text
git add .
git add -A
git commit -a
```

提交闸门：

1. `git status --short`
2. `git diff --check`
3. `git diff --stat`
4. `git diff --name-status`
5. 显式 `git add -- <允许文件>`
6. `git diff --cached --check`
7. `git diff --cached --stat`
8. `git diff --cached --name-status`
9. 运行提交前测试和语法检查
10. 创建含义明确的业务提交
11. `git show --check --stat --oneline HEAD`
12. 确认提交只含允许文件

不得将 `.env`、运行数据、日志、缓存、授权原始资料或无关用户修改带入提交。

## 6. GitHub main-first 推送

本仓库采用 main-first：

1. 本地测试和提交通过。
2. 获取远程状态并确认没有意外变化。
3. 本地 `main` 只领先预期提交。
4. 使用普通 fast-forward 推送 `origin/main`。
5. 推送后核对本地 HEAD、`origin/main` 和 `ls-remote main` 指向同一完整 SHA。

建议核验：

```bash
git status --branch --short
git remote -v
git branch -vv
git rev-parse HEAD
git fetch origin
git rev-parse origin/main
git log --oneline origin/main..HEAD
git diff --name-status origin/main..HEAD
git push origin main
git fetch origin
git rev-parse HEAD
git rev-parse origin/main
git ls-remote origin refs/heads/main
```

禁止 force push。GitHub main 更新不会自动改变生产。

## 7. 生产服务器只读身份

服务器读取 GitHub 必须使用：

- 仓库专用只读 Deploy Key；
- 固定 SSH 包装脚本；
- 已核验的 GitHub 主机身份；
- 最小权限和明确文件权限。

禁止：

- Deploy Key 开启写权限；
- 从服务器执行 `git push`；
- 将私钥写入 Git、文档、日志、聊天、镜像或审计文件；
- `StrictHostKeyChecking=no`；
- 用 `ssh-keyscan` 自动接受未知主机；
- 用临时个人凭据替代正式只读身份。

当前公共实例登记见 [`projects/生产只读检出实例登记.md`](projects/生产只读检出实例登记.md)。执行时必须重新核验，不得永久复用文档中的哈希或指纹。

## 8. 服务器可信检出

正式标准是服务器独立只读浅克隆，不使用 worktree。

固定要求：

1. 在全新、唯一的临时隔离目录开始。
2. 使用固定 SSH 包装脚本执行 `git ls-remote`，取得远程 `main` 完整 SHA。
3. 确认远程 SHA 等于本次批准的目标完整 SHA。
4. 使用只读 Deploy Key 浅克隆远程 `main`。
5. 检出目标完整 SHA，并保持 detached HEAD。
6. 核验本地完整 HEAD、Tree SHA、工作区 clean。
7. 执行必要的 `git fsck --connectivity-only`。
8. 记录检出命令、退出码、SHA、Tree 和验证结果。
9. 验证全部通过后，才允许把候选源目录原子发布为隔离的完整 SHA 目录。
10. 只有 `checkout_passed=true` 和 Manifest 通过才允许构建。

可信检出必须使用完整目标 Git SHA。首次检出失败后，必须冻结失败目录及日志，
在新的唯一 `attempt` 目录重新开始；不得在失败的 Git 对象库中继续 fetch、checkout、
reset、repair 或作为构建输入。第二次出现同类对象错误时停止盲目重试，转入文件系统、
并发清理、外层超时、I/O 或 OOM 专项调查。

绝对禁止在 `/home/ubuntu/market-data` 正式仓库中执行：

- 新版本 checkout 或分支切换；
- 依赖安装；
- 测试；
- 镜像构建；
- 作为候选构建上下文；
- 任何会改变正式仓库 HEAD 或工作区的准备操作。

## 9. 候选镜像

所有候选构建必须在隔离候选源目录完成。

候选镜像必须：

- 使用版本化、不可变、绑定 Git SHA 的镜像引用；
- 禁止使用 `latest`、`new`、无标签或 Compose 隐式镜像名作为身份；
- 记录完整 Image ID；
- `org.opencontainers.image.revision` 等于目标完整 Git SHA；
- 记录必要的 source、created、title 和 version；
- 保留原始构建命令、退出码、输出和 inspect；
- 不覆盖当前正式镜像标签或回滚对象；
- 通过目标应用所需的镜像和部署契约验证。

候选容器启动前必须执行 seal preflight，同时验证不可变标签、完整 Image ID、
OCI revision、Git Commit、Git Tree 和 Release 元数据。任一字段缺失或不一致立即
停止；不得修改既有候选结果或失败证据使其看似通过。

OCI revision 只承担完整 Git commit SHA 身份。Tree SHA 不要求写入 OCI
标签；它由可信 `tool_repo_root` 的 `HEAD^{tree}`、Release 产物、镜像内
`/app/RELEASE.json`、候选结果、部署计划、部署结果及各自 Manifest 传播和
验证。

候选验收与正式部署必须复用完全相同的 Image ID。该原则适用于三个正式应用，不因某个应用尚未完成自动化工具建设而降低。

## 10. 候选容器和验收

候选容器必须：

- 只绑定 `127.0.0.1` 测试端口；
- restart policy 为 `no`；
- 正式数据只读挂载；
- 日志、缓存和临时文件写入候选隔离目录；
- 核验容器 ID、Image ID、OCI revision、容器内 `RELEASE.json` 的 Git/Tree
  SHA，以及 Docker inspect 实测运行时 `MARKET_DATA_GIT_HEAD`；
- 检查根页面、健康接口、RestartCount、日志和受影响页面；
- 验证其他生产容器、正式 Git 和业务数据没有变化；
- 截图或浏览器证据必须来自候选容器。

验收结束后：

1. 只有实际候选容器的 Image ID、OCI revision、容器内 Git/Tree SHA 和
   inspect 实测运行时 Git SHA 全部匹配 Release 后，才生成不可覆盖的
   `candidate_result.json`；运行时 Git SHA 不得人工输入。
2. 生成并验证 `candidate_result.manifest.json`。
3. 保存必要日志、inspect、HTTP、页面和数据不变性证据。成功和失败候选均
   使用同一有限日志摘要：最多最后 200 行、最多 64 KiB，记录采集时间、
   原始采样字节数、脱敏尾部 SHA-256、截断状态和 warning/error 数量；不得
   保存无限完整日志、完整 inspect 环境变量或敏感值。日志读取失败只能记录
   受控 `unavailable` warning。
4. 成功候选和失败候选均删除候选容器。
5. 重新证明候选容器不存在。
6. 保留已验收候选镜像 Image ID、`candidate-data`、数据 Manifest、候选结果及
   Manifest、失败证据和可信源码身份。
7. 只有完成以上步骤，才允许生成 `deployment_plan.json` 和 `deployment_plan.manifest.json`。

候选容器、候选镜像、`candidate-data`、候选运行视图、候选结果和失败证据是不同
生命周期对象。候选容器不得长期保留；候选运行视图可以按证据和批准规则清理。
`candidate-data` 至少保留到 `deployment_result`、其 Manifest 和 bundle Manifest
密封、生产稳定性确认、复盘归档完成且另行获得明确清理授权；不得随候选容器自动
删除。

## 11. 当前强制发布产物

当前强制事实链产物是：

| 目标产物 | 对应 Manifest |
|---|---|
| `release.json` | `release.manifest.json` |
| `candidate_result.json` | `candidate_result.manifest.json` |
| `deployment_plan.json` | `deployment_plan.manifest.json` |
| `deployment_result.json` | `deployment_result.manifest.json` |
| 部署结果集合 | `deployment_result.bundle.manifest.json` |

要求：

- 四类 JSON、对应 Manifest 和部署结果 bundle Manifest 均采用排他创建实现；内容在内存完成序列化和
  校验、临时文件完整写入并 `flush`/`fsync` 后，以硬链接排他创建正式路径，
  不得通过 `os.replace` 覆盖已有目标；
- 每个 Manifest 至少密封目标文件名、SHA-256、字节大小、目标 Schema 版本、生成时间、Release Git SHA、Tree SHA 和 Image ID；候选结果与部署结果 Manifest 还密封容器 inspect 实测的运行时 Git SHA；
- 任何后续阶段读取 `release.json`、`candidate_result.json`、`deployment_plan.json` 或 `deployment_result.json` 前，必须先验证对应 Manifest；
- `release.env` 和 `checksums.sha256` 暂作为 Release 兼容产物继续生成；`checksums.sha256` 仍校验 `release.json` 与 `release.env`，但不能替代 `release.manifest.json`；
- `deployment_plan.json` 必须从已验证的 Release 和候选结果继承 Git SHA、Tree SHA
  与候选 Image ID，并显式记录 `tool_repo_root`、`production_compose_file`、
  `production_project_dir`、Compose 项目名、服务名和独立的
  `deployment_tool_revision`；业务 Release revision 与发布工具 revision
  可以不同，不得因工具升级要求重新构建已验收业务镜像；
- 计划生成前必须只读审计当前生产 Compose、env、容器、镜像、数据、端口和挂载，
  并同时锁定当前基线与目标身份，至少包括
  `production_baseline_compose_sha256`、`production_baseline_env_identity`、
  `production_baseline_image_id`、`target_compose_sha256`、`target_env_identity`、
  `target_image_id`、`target_git_commit`、`target_git_tree` 和目标数据 Manifest；
- 生成计划不得要求生产 Compose 或 env 已经等于目标 Release。Compose 与 env 必须
  一次性审计、一次性预演、一次性纳入计划，并在正式部署事务中联合原子同步；失败时
  按计划锁定的生产基线联合回滚；
- 正式执行 argv 必须直接进入 `deployment_plan` Schema 并由 Manifest 密封。核心
  安全参数变化时必须重新生成计划及 Manifest，不得在计划密封后用独立 execution
  amendment 补充或改变正式切换参数；
- 首次数据发布允许 `first_release=true` 且 `existing_file_count=0`，但必须生成空
  基线 Manifest。非首次发布若正式文件数意外为 0，必须与上一份
  `deployment_result` 对账并停止；
- `tool_repo_root` 是已批准发布工具的独立只读检出；`production_compose_file` 是正式切换实际使用的 Compose 文件；`production_project_dir` 是 Compose 相对路径、挂载源和 `env_file` 的正式解析基准；
- 计划中的生产 Compose 路径必须为经过校验的绝对路径。不得通过脚本目录、当前工作目录或 `/home/ubuntu/market-data` 的 HEAD 隐式推导；
- Release Git SHA、Tree SHA 和候选 Image ID 在候选结果、部署计划和部署结果任一级不一致时必须停止；
- `candidate_result.json` 必须保存候选容器 inspect 实测的运行时 Git SHA
  及有限脱敏日志摘要；其 Manifest 通过目标文件 SHA-256 密封该摘要身份；
  `deployment_result.json` 必须分别保存计划目标 Git SHA、正式容器 inspect
  实测运行时 Git SHA 和验证结果。缺失、空值、冲突值或不一致时不得生成成功结果；
- `deployment_result.json`、对应 Manifest 和 bundle Manifest 是正式部署的强制
  最后阶段；缺少任一产物不得宣称发布完整完成；
- 代码、镜像和运行数据必须形成三条分别密封的身份链：Git Commit/Tree、候选及
  正式 Image ID、逐文件数据 Manifest。代码已进入 Git 不代表数据已发布，镜像验收
  成功也不代表运行数据已发布；
- 缺失事实只能进入明确标记的追溯重建流程，不得伪造原始测量值。

以下暂列为待实现增强项，不是当前强制产物：

- `approval_record.json`
- 部署前 runtime JSON
- 部署后 runtime JSON
- 浏览器检查 JSON
- 自动化生成的部署前/后生产基线

只有对应脚本、Schema 和测试完成后，才可将增强项升级为强制要求。

上述产物、Tree SHA 传播、候选结果生成、计划生成、正式切换和部署结果记录的候选
实现位于 `09_deploy/spread_release/`，适用于 `spread-dashboard`。当前工具已实现
`current_production`/`target_release`、plan 内 argv、执行前基线防漂移、
执行阶段 env 原子切换与回滚恢复。候选数据生命周期仍按本规范的
独立契约处理。USDA 与 Oil World 必须遵守同一事实链和
同一 Image ID 原则，但一条式自动化工具仍待实现；不得把 spread 工具的存在描述成
另外两个应用已经自动化。

## 12. 正式部署

正式部署必须：

1. 获得用户对目标完整 SHA、同一 Image ID 和密封计划的明确批准。
2. 重新验证 Release、候选结果、部署计划及其 Manifest。
3. 从隔离只读检出中的发布脚本执行，并证明 `tool_repo_root`
   的 HEAD 和 Tree SHA 等于计划密封的 `deployment_tool_revision`；
   不得要求它等于业务 Release，也不得要求正式仓库 HEAD 等于新 SHA。
4. 从已验证计划读取 `production_compose_file`、`production_project_dir`、Compose 项目名、服务名和 `candidate_image_id`。
5. 证明候选容器已经删除。
6. 证明目标 Image ID 与候选验收 Image ID 完全相同。
7. 在任何写入前重新确认实际 env、Compose 和容器仍等于计划密封的
   `current_production`；随后由官方 helper 原子更新 env 为 `target_release`。
8. 从计划读取已经密封的执行 argv，只切换计划指定的目标服务，并同时包含
   `--no-build --pull never --no-deps --force-recreate`。
9. Compose 可以保留静态 `build:` 定义；安全门槛检查实际执行 argv，不得仅因
   YAML 存在 `build:` 就拒绝。正式事务禁止 `docker build`、`docker compose build`、
   `--build`、`latest`、`docker compose down` 和任何 prune。
10. 不无必要地重建或重启其他应用。
11. 核验正式容器实际 Image ID、OCI revision、容器内 Git/Tree SHA 和 Docker
    inspect 实测运行时 `MARKET_DATA_GIT_HEAD`；实测运行时 Git SHA 必须等于
    计划目标完整 SHA，实际 Image ID 必须等于候选结果和部署计划记录值。
12. 验证端口、挂载、环境、HTTP、页面、数据和其他应用不变。
12. 最后生成并密封 `deployment_result.json`、`deployment_result.manifest.json`
    和 `deployment_result.bundle.manifest.json`。

对尚未完成一条式自动化部署的应用，可以使用经过审核的受控步骤，但仍必须满足同一 Image ID、无正式阶段 build、明确回滚对象和强制部署结果要求。工具缺口必须如实记录。

## 13. 生产身份

不得使用以下单一信息证明生产版本：

- 目录修改时间；
- 容器名称；
- 镜像标签字符串；
- GitHub main；
- 旧容器 `Config.Image`；
- `latest` 或 `new`。

生产身份至少核验：

- `deployment_result.json` 和 Manifest；
- 正式容器实际 Image ID；
- OCI revision；
- 容器内 `RELEASE.json` 的完整 Git SHA 和 Tree SHA；
- Docker inspect 从 `Config.Env` 实测的 `MARKET_DATA_GIT_HEAD`，以及它与计划
  目标完整 SHA 的验证结果；
- 当前生产 Git/基线记录；
- HTTP、页面和数据挂载状态。

## 14. 回滚

回滚对象必须在部署计划中明确并经过预校验：

- 上一完整 Git SHA；
- 上一可用 Image ID；
- 生产基线 Compose、env、数据 Manifest、正式容器配置、端口、挂载和环境；
- 回滚脚本或受控步骤；
- 健康检查和数据不变性验证。

回滚禁止重新构建镜像、使用 `latest` 猜测旧版本或删除失败证据。

`spread-dashboard` 使用仓库当前密封 Release 契约指定的部署和回滚脚本。USDA、Oil World 在自动化完善前必须保留明确的上一 Image ID 和受控回滚记录。

## 15. 清理

清理是独立任务。默认禁止：

```text
docker system prune
docker image prune
docker image prune -a
docker volume prune
docker compose down
```

清理前必须盘点容器、镜像、构建源、`candidate-data`、Release、候选结果、计划、
部署结果、Manifest、回滚对象、失败证据和磁盘使用。

任何删除对象必须同时满足：

1. 不是当前正式对象；
2. 不被任何容器引用；
3. 不被发布事实链或 Manifest 作为必需实体引用；
4. 不是唯一回滚对象；
5. 不是事故复盘的唯一证据；
6. 有明确对象名、完整 ID 或经核验的绝对路径；
7. 已获得单独批准。

候选容器不进入长期清理评估，因为它必须在部署计划前删除；候选镜像、
`candidate-data` 和候选证据仍按上述规则保留和评估。结果链未全部密封、生产尚未
稳定、复盘未归档或没有独立清理授权时，不得清理 `candidate-data`。

## 16. 停止条件

以下任一情况必须停止：

- baseline HEAD/Tree 不一致；
- Feature Worktree 不在预期 branch，或存在无法解释的工作区修改；
- 输入数据或 Reference Data 身份无法确认；
- Runtime Mode、marker、module 或 resolved root 无法确认；
- 正式 Runtime 被错误赋予写权限，或 linked worktree 试图进入 production-write；
- 修改超出 Change Boundary；
- Shared Dependencies 的修改扩大了影响面，但测试范围未重新计划；
- required Direct/Impact/Full Tests 或本地页面/业务验收失败；
- Git root、common dir、branch、Commit 或 Tree 身份不一致；
- 目标 SHA 与远程 main 不一致；
- 只读身份、主机身份或包装脚本无法核验；
- 检出不是 detached HEAD、工作区不干净或 fsck 失败；
- 候选源位于正式仓库；
- 候选或正式 Image ID 不一致；
- 候选容器未在计划前删除；
- 计划要求生产 Compose/env 预先等于目标，或没有同时锁定当前基线和目标身份；
- 正式执行 argv 缺少四个安全参数，或包含实际 build、`latest`、`down`、prune；
- 计划密封后试图通过独立 amendment 改变核心执行参数；
- 数据、挂载或其他应用出现非预期变化；
- 回滚对象不明确；
- 强制产物或 Manifest 缺失；
- 用户已有修改、生产事实或文件身份无法解释。

触发停止条件后，不得通过复制未知数据、修改正式 Runtime、扩大权限、跳过测试或
直接去服务器验证来绕过停止点。
