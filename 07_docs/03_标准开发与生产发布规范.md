# 标准开发与生产发布规范

> 文档状态：当前权威规范。本文用“必须、不得、应当、停止”定义开发、测试、Git、候选构建和生产发布的强制边界；逐步操作见 [`04_开发与发布检查清单.md`](04_开发与发布检查清单.md)。

## 0. 规范边界与用语

本文只定义长期、通用且可执行的约束，不记录某次发布的容器 ID、镜像标签、IP、
环境变量值或临时目录。此类事实只能作为带日期的实例保存在 `archive/`、密封发布
产物或生产基线中，执行时必须重新核验。

- **必须**：缺失即不得进入下一阶段。
- **不得**：禁止的行为；即使某次操作看似成功也不能作为例外。
- **应当**：默认做法；若不采用，必须记录原因、风险和替代验证。
- **停止**：保持已验证对象不变，报告已确认事实；不得用猜测、降级断言或旁路继续。

规范、手册、模板和归档的职责由 [`00_文档索引与适用范围.md`](00_文档索引与适用范围.md)
定义。下级文档不得放宽本文；手册不得把尚未通过真实候选门槛的工具称为正式生产工具。

## 1. 适用范围

本文定义 `market-data` 单仓库的标准开发、测试、Git、GitHub、服务器可信检出、候选镜像、候选容器、正式部署、部署结果、回滚和清理规则。

`09_deploy/spread_release/` 中的实现能力必须以当前代码、Schema、测试和真实候选
验收为准。2026-07-22 全天气发布的完成不代表复盘提出的工具整改项已经实现；
任何工具升级必须另行开发、测试并完成候选发布，不得由本文规则反推工具已经具备
相应能力。USDA 和 Oil World 的一条式工具仍待实现。

适用于：

- `spread-dashboard`
- `usda-dashboard`
- `oil-world-dashboard`
- 后续纳入本仓库的农产品研究应用

项目契约可以增加更严格要求，但不得降低本文的 Git 身份、同一 Image ID、数据保护和生产停止标准。

所有阶段还必须遵守以下跨文档硬边界：

- ChatGPT 会话沙箱、Windows 本地仓库、Codex 可执行环境和 Ubuntu 生产服务器相互隔离；路径不是文件身份，跨环境必须显式传输并重新核验。
- 本地正式验证使用 `.venv-py312` 与 Python `>=3.12,<3.13`；前端使用 Node `>=24,<25`、Corepack 管理的 pnpm `10.12.1`、`pnpm install --frozen-lockfile`。环境不满足时停止，不自动安装或使用替代工具。
- 业务代码和业务数据分离。正式数据默认只读挂载；候选不生成、不填补或覆盖正式数据，除非任务明确是经过独立授权的数据发布。
- 本地 Windows 是开发源，GitHub `main` 是代码交换与身份真源；服务器只通过已核验 Deploy Key 获取目标完整 SHA，不承担日常开发。
- 三服务的 Compose 所有权、项目名、端口和运行边界以 `01`、目标独立 Compose 与实际配置为准。单服务操作不得隐式解析、重建或重启另两个服务。

## 2. 按修改范围选择正式链路

普通 Business Fast Lane：
`START / RESUME → development → push feature → trusted-main-admission-v1 PASS → exact fast-forward main`。

GitHub hosted Admission 是普通 Business 的正式 required tests / Scope / identity evidence。
本地 Direct / Impact tests 和 Scope 用于快速反馈；`complete_project.py` 与独立 integration
worktree 不再是普通 Business 进入 main 的强制 Gate，不得因未执行它们判定未完成。
接纳只允许 successful check 对应的同一个 candidate Commit/Tree；任何新 commit 都必须
重新获得 hosted PASS，即使 Tree 相同也不得复用旧 PASS。具体 API 回查见第 6 节。

本简化不适用于 shared infrastructure、governance、protected paths、production-control-plane、
FULL DAILY、Production Wrapper、Runtime、deployment 或 production data/write path。
按真实完整 diff、可信 Registry 和专项合同判断，不能仅凭 business 标签或绿色 check 使用快车道。
高风险 lane 使用同一个 `trusted-main-admission-v1` 的 strict 检查；Completion 与独立 integration 可用于开发反馈或专项验收，保留原测试与 Runtime 合同。
下列严格链路用于这些高风险修改及需要另行授权的生产发布；普通 Business 接纳 main 后即结束开发接纳，
不因此进入服务器、候选或生产阶段。

```text
任务定义
→ 确定 Project
→ 读取 Project Registry / 声明 Change Boundary
→ git fetch + git ls-remote 确认 fresh origin/main 身份
→ 从该身份创建独立 Feature Worktree（不改 local main）
→ Worktree Preflight
→ 选择 Runtime Mode
→ 确认输入数据 / Reference Data
→ 本地开发
→ Direct Tests
→ Project Scope Gate --project <project_id>
→ Impact Tests
→ 必要时 Full Regression
→ 本地页面 / 业务验收
→ 范围审计
→ 显式 Git 提交
→ push feature / hosted technical validation（Shared 要求 strict PASS；Governance 要求完整技术 PASS）
→ 仅 GOVERNANCE_TRANSITION 需要 Maintainer/Admin 接纳精确 Commit/Tree/base
→ 从获批 branch 普通 fast-forward 更新 origin/main
→ 同步 clean local main 镜像
→ 独立生产候选/release 授权（以下不是 main-entry 前置条件）
→ 服务器独立只读浅克隆完整 SHA
→ 隔离目录构建候选镜像
→ 候选容器验收
→ 密封 candidate_result 和证据
→ 删除候选容器
→ 密封 deployment_plan
→ 用户批准
→ 使用同一 Image ID 正式切换
→ 密封 deployment_result、Manifest 和 bundle Manifest
→ 验证生产身份和数据不变性
```

本地开发和必要验收完成前，不得用候选服务器或正式服务器代替本地开发测试。
Feature Worktree 本身没有候选、生产或部署权限；进入候选阶段仍须获得独立授权，
并完整遵守本文既有的可信检出、同一 Image ID、结果密封和回滚规则。

`main` 在远程表示可信主线，在本地 checkout 表示该远程主线的 clean 镜像；两者都不表示当前生产
版本。生产身份必须由部署结果、Manifest、生产基线、正式镜像 ID 和运行容器注入
的完整 Git SHA 共同证明。

## 3. 开发前范围契约

普通业务 Change Boundary 由 START / RESUME 和 Scope 工具生成 Git/Registry 事实：
HEAD/Tree、branch、worktree/common dir、baseline、owned paths、changed files 和 required tests。
人工只保留业务目标、验收标准及特殊权限决定，不重复填写上述机器事实。
生产、部署、Runtime 的专项执行合同仍按后文原规则执行。

`Allowed Paths` 是本次默认可写范围。`Shared Dependencies` 是项目可能调用、但不因
调用而自动获得修改权限的公共模块。修改 Shared Dependencies 前必须重新评估
Change Boundary，并依据 `02_configs/module_test_map.yaml` 扩大测试范围。
`Forbidden Paths` 默认不可修改；如果实施中确实需要修改 forbidden 或未批准的
shared 路径，必须停止当前实施并重新取得范围决定，不得静默扩大任务。

普通业务 feature 的 `change_class` 固定为 `business`。Weather producer、shared Public
refresh、统一 refresh、`market_data/`、`shared/`、质量/自动化控制面和部署基础设施默认
属于 shared/protected 边界；即使把这些路径写入 `Allowed Paths`，`business` 任务仍必须
失败。只有任务开始前明确分类为 `shared` infrastructure change，并声明其 owned paths，
才允许通过 Scope Gate。其他业务项目不在当前 owned paths 内，因此同样失败。

不得在开发或发布过程中无依据扩大范围。发现无关测试数据、历史模块或其他应用阻断任务时，应先判断是否真的属于本次风险，而不是通过修改无关对象绕过失败。

### 3.1 main 与 Feature Worktree

项目与边界由可信 main 的 `02_configs/project_registry.json` 和 bootstrap policy 决定。
普通 business candidate 不可修改既有项目记录；shared_dependencies 只读。shared/governance candidate 仅使用可信 Registry 已有 owner 进入 strict lane；forbidden 与未授权 production change 失败，candidate Registry 不给自身扩权。
新普通 business project 不再要求预先登记审批：START 生成一个固定格式记录，仅预留
`03_src/agri_research_agent/<project_id 转下划线>` 和 `08_tests/<同名>`。namespace 必须
与可信文件、其他 ownership/只读接口、protected/shared 边界无冲突；不授予 Runtime 或生产权限。
必须提供 `08_tests/<同名>/test_project.py`，可信 Admission 发现该 namespace 全部 `test_*.py`，
逐文件要求非空收集、全部 PASS，不信任 candidate 自选的 required_tests 或测试配置。
普通 business bootstrap 的 Registry delta 只允许末尾精确新增这一个项目；改变现有记录、根策略或裁判文件不能沿 business lane 自我批准。合法治理修改走 strict lane，始终由 trusted-main policy 判断。

标准入口 `04_scripts/quality/start_project.py --project <id> --branch feat/<name>
--worktree <绝对路径> --create` 在线 fetch/ls-remote，从 fresh main 创建并输出 `STARTED`；
已有一致的 branch/worktree 返回 `RESUMED`，校验本地 project 绑定和完整 dirty diff，不覆盖文件。
START / RESUME 自动输出 Change Boundary。业务目标、验收标准和特殊权限由人工决定。
普通 Business 由 hosted Admission 绑定 candidate identity、验证 Scope 并执行真实测试；
精确 bootstrap delta 不再因 Registry 尚未预存在 main 而失败。既有项目的自我扩权仍拒绝。
Completion 可选执行，若调用仍完整验证；高风险 main-entry correctness 由 hosted strict lane 验证；生产验收另行授权。
聊天历史 SHA 不是执行权威。bootstrap 不授予 shared、governance、deployment 或 production-control-plane 权限。
低层 `--owned` 仍只用于测试和明确批准的 shared 任务。

本地 `main` checkout 必须保持为 clean `origin/main` 镜像，只用于只读审计和同步；不得
用于 feature 修改、临时 merge、集成测试、验收或 release。所有 feature（包括小型维护）、
integration 和 release 都使用各自 branch/worktree。完成并获批的 branch 直接以普通
fast-forward 更新远程 `main`，随后才同步本地 `main` 镜像。
普通 Business START / RESUME 与本地 Scope 不依赖无关 local main checkout 是否 clean、mirror
或存在；高风险 lane 与实际 main 同步继续保留原 main mirror 要求。
candidate Registry 与分叉基线一致、latest main 仅追加无关项目记录时，当前项目 trusted
identity/ownership 保持兼容即可 RESUME；candidate 自己修改 Registry 仍严格检查。
这不豁免 main 接纳前的 freshness：仍须取得针对最新可信 main 的 hosted PASS。

并行 feature 不得共享同一个可写源码工作区。每个 Feature Worktree 必须具有明确的
project、branch、baseline 和机器生成的 Change Boundary。创建或进入 Worktree
后的 preflight 至少核验：

- Git root 和 Git common dir；
- branch、完整 HEAD、Tree 和 `git status --short`；
- Change Boundary、Shared Dependencies 和 forbidden paths；
- 仅实际使用 Runtime 的任务核验 Runtime Mode、resolved runtime root 和 `.market-data-runtime.json`；
- Python/测试入口和必要输入身份。

Feature Worktree 默认 `deployment_permission = none`。创建 branch 或 linked worktree
不会自动授予 production candidate、production、production-write、main merge 或部署权限；已授权开发包含 commit/push feature。
[`04_开发与发布检查清单.md`](04_开发与发布检查清单.md) 第 5 章所称“Windows 正式
仓库”，在本流程中指属于唯一 Git 基线、经过核验的本地源码工作区，可以是获批的
Feature Worktree；它不表示并行 feature 应长期直接写入本地 `main` 工作区。

#### Registry future 文件与完成验收

Registry `project-registry/2` 增加可选 `future_owned_paths` 和 `future_required_tests`。
原有 `owned_paths`、`required_tests` 仍必须存在；v1 保持兼容。future 字段只允许精确
仓库相对文件路径，不允许 glob、目录授权、越界或 symlink/junction；使用统一 separator
和大小写身份检查冲突。文件创建前后均按精确路径归属，不扩展到 sibling 或子路径。
future tests 必须位于 `08_tests/`、使用 `test_*.py` 命名（声明中不允许通配符），且属于该项目。
future ownership 不得侵占其他项目 ownership、只读依赖或 forbidden scope；business 不得
借 future 绕过 shared/protected。frozen 保护不变，新普通项目按受控 bootstrap 处理。

Registry 静态验证和 project start 允许 future 文件缺失，不要求所有已登记项目已完成。
普通 Business 的 future tests 由 hosted Admission 正式执行，无需重复 Completion/integration。
高风险 lane 的 required/future-required、impact 与必要 full tests 由可信 Registry 和 module map 确定，逐文件非空收集且全部通过。正式执行 candidate tree 的测试版本；required path 删除以 `REQUIRED_TEST_REMOVED` 失败。candidate 新增或修改 owned test namespace 的 regression test 必须加入计划：

`trusted_required_tests UNION candidate_changed_or_added_tests_in_owned_test_namespace`

测试配置与 Scope 使用 trusted main；candidate 修改 Registry/test map 不得减少可信测试集合。测试身份同时记录 trusted blob、candidate blob 和 SHA256，所有 PASS 绑定同一 candidate Commit/Tree。普通 Business 不运行被其合法替代的旧 test blob。

`runtime_target=production_container` 的真实运行与签名容器证据属于独立 production/release gate，不是 main-entry 前置条件。受保护 builder 仍从明确获批的完整 SHA 获取 clean detached 源码，执行容器探针并签发 candidate record。若使用 `complete_project.py --candidate-record <记录>`，必须执行全部 required tests 与签名容器门禁；独立 integration 可作专项验收，不能用 Disabled Ruleset 接纳 main。
候选 Commit/Tree、输入或镜像改变必须重做相应验收。正式部署只能提升明确批准、属于可信 main 历史的精确 Commit/Tree 和同一已验证 Image ID；candidate 不写 production，Approved 身份、数据 Manifest、rollback 和生产单独授权全部保留。

#### Registry reserved namespace 与项目文档分区

Registry `project-registry/3` 增加可选 `reserved_paths`，用于经独立治理批准的目录子树。
v1/v2 和普通 `owned_paths` 的存在性要求不变；`future_owned_paths` 仍是精确文件。
reservation 声明采用仓库相对路径，不带 glob；仅 leaf 目录可缺失，其直接父 namespace
必须真实存在于仓库内。不自动创建目录，拒绝文件、绝对路径、点段、重复 separator、
Windows 保留名、尾随点/空格、symlink/junction、仓库根和顶层整目录授权；
`03_src/agri_research_agent` 和 `07_docs/projects` 也不能被整棵 reservation。

所有项目的普通 ownership、future 精确文件和 reserved 子树进行同一 ancestor/descendant
冲突检查，按 slash 和 Windows casefold 比较；不允许多个 owner。声明本身不接受反斜杠；
Scope 的 Windows 路径比较可统一 separator。reserved 不得覆盖只读依赖、forbidden 或
business protected；最低 shared 文件保护仍在 Scope Gate 逐文件执行。

ready 沿用原状态：有普通/future/reserved ownership，且有 required/future-required tests
即可通过静态 readiness；无需预先创建 reserved leaf。首次创建子树内文件属于该项目，
父目录其他文件、sibling 和上游仍不归属。新普通项目可按可信 bootstrap policy 启动；
普通 Business 的真实测试由 hosted Admission 验证，高风险 lane 由 hosted strict 检查 required/impact/必要 full tests；
reservation 不授予业务解冻或生产操作权限。

`dev-governance` 的 `07_docs` ownership 收窄为 00–06 全局规则文件、`07_docs/templates`
和生产只读检出实例登记；原有其他治理入口保持。未来项目可独立 reservation
`07_docs/projects/<namespace>`，不能整棵拥有 `07_docs/projects` 而侵占已登记 sibling。
本能力不登记任何真实 Notification 项目，也不改变既有业务 readiness。

#### Registry/4 runtime intent 与目标验证

`project_registry.py` 同时读取 `project-registry/1` 至 `project-registry/4`。
既有 Registry/3 记录保持原状；版本能力上线不隐式迁移项目，不改变 ownership、
frozen 状态或生产权限。迁移 Registry 至 v4 必须通过独立治理登记；v4 新增或迁移记录
必须显式提供 `runtime_target`：`none`、`library_only`、`windows_git_worktree`
或 `production_container`，不允许缺省或未知值。旧记录继续按旧版本读取，不能在
旧 schema 偷加 production target 绕过验证；其显式迁移之后启用新门禁。
v4 顶层可提供 `legacy_registry_commit`，必须是可信 origin/main 祖先中的完整 Commit，
其 Registry 必须为有效 v1–v3。只有同时与该历史对象及当前 origin/main 对应记录完全
一致的旧记录，才允许尚未声明 target；任何修改、新记录、历史状态复活或已迁移项目
降级均拒绝。不自动给旧项目填 none/library_only；每条迁移必须独立审计实际 runtime。

当前 Registry 已采用 v4 与显式 `legacy_registry_commit`。`dev-governance` 声明 `none`；
新增 `shared-production-infrastructure` 声明 `library_only`，仅交付跨 Git/OCI 的身份库、
宿主验证工具和签名授权合同，不是业务生产服务。它只拥有 Registry 列出的精确文件，
不拥有治理入口、Dockerfile、Compose 或业务代码；不因此获得部署或数据写入权限。
其他未迁移记录保持旧对象与当前主线双重相等校验。登记通过不表示身份库已实现，
更不表示 Target Runtime Container Validation、AM/PM wiring 或 production release 已通过。

`production_container` 必须提供精确、已存在的 `runtime_contract` 文件路径；禁止
glob、绝对路径、越界、符号链接或 junction，也拒绝跨 build 字段的重复路径/大小写别名。
治理入口严格检查 `runtime-manifest/1`、`runtime-manifest/2` 和 `runtime-manifest/3` 的 project/module/service、target/identity、入口、
容器工作目录、roots/mounts 权限对应、环境/secret引用、依赖、生产/Preview策略和必需
probe集合，以及 Dockerfile、dockerignore、依赖合同和 Compose 源文件路径。实际文件
供给、容器路径/权限与运行语义由独立基础设施验证器负责；静态声明不构成 deployability PASS。

v2/v3 由当前治理 checkout 内的共享解析器按源码字节加载，不使用 caller 的已安装包或 ignored
bytecode。它额外要求明确身份根、初始化 argv 和受控 source inputs，完整合同见
[`生产 Runtime Manifest 合同`](projects/生产RuntimeManifest合同.md)。三个版本的 JSON
均拒绝重复键；这是明确的读取收紧，不允许重复 schema key 把 v2 隐式降为 v1。
v1 的既有结构规则保留，不能因存在 v2 就自动获得新语义。v2 的全部 source inputs、
共享解析器和 Schema 文件均纳入 Git 跟踪、精确文件与 SHA 绑定；缺失、ignored-only、
路径别名、与清单或验证器重复的输入不能用于通过候选验证。host 对 v2 的适配仍须独立验收。

v3 另外要求显式环境绑定、禁止环境变量列表和候选只读输入。治理使用共享解析器的
精确字段与交叉引用规则，确认所有声明文件存在；正式 candidate binding 再逐一检查
fixture 的 Git 跟踪与字节身份。`candidate_runtime_inputs.sha256` 必须等于对应 Git blob
的 SHA-256，fixture 与源码、清单、build/validator 输入的重复或别名均拒绝。Windows
CRLF checkout 可经 Git filter 证明与提交相同，但哈希始终绑定原始 Git 字节；这不允许
真实内容漂移、ignored-only 或未跟踪文件通过。

v1/v2 保持 `target-runtime-validator/1`；v3 必须绑定 `target-runtime-validator/2`，旧版
引擎/记录的 PASS 不能作为 v3 验收。此治理适配不实现新引擎、record、host 或容器授权
消费者；在各自适配与实际验收完成之前，v3 container completion 仍不得 PASS。fixture
只属于候选输入证据，不能进入可提升镜像或生产存储，更不能充当真实 AM/PM 时间验收。

生产容器项目 completion 必须从 clean committed candidate 执行目标验证器，获得
`TARGET_RUNTIME_STATIC_VALIDATION=PASS` 与 `TARGET_RUNTIME_CONTAINER_VALIDATION=PASS`。
原有 Scope、required/future-required tests、拒绝 skip/xfail 和候选不变检查全部保留。
Completion 不接受手写 PASS 或未签名的外部 evidence。默认主动执行候选中固定位置的
`04_scripts/runtime/validate_target_runtime.py`。
入口尚未实现或获准 Linux builder 不可用时 `PROJECT_COMPLETION=BLOCKED`（退出码 3），
不得以 static-only 或 skip 替代完整 PASS。验证器失败、缺少机器证据、身份不符均 FAIL。
非 container target 不强制 Docker；Windows 无 Docker 不等于代码失败。

`target-runtime-evidence/1` 必须绑定完整 Commit/Tree、Runtime Manifest、Dockerfile、
dockerignore、依赖合同、全部 Compose 源和验证器源码的 SHA-256，以及 validator version、
实际 Image ID 和实际 rendered Compose SHA-256。必须提供 Linux 隔离 builder observation、
与 candidate 相符的 OCI/Tree/source/render identity，以及全部正反向 probes 的 PASS。
这些字段由后续 trusted host/CI engine实际采集；字段值本身不是 builder授权或签名。
源码哈希以 Git blob 的原始字节为准，
避免 Windows checkout CRLF 转换伪造身份变化；工作树输入必须仍与对应 Git blob 一致。
绑定对象变化使旧证据失效，不接受其他候选的结果。

跨环境验收可显式使用 `complete_project.py --project <project_id> --candidate-record <绝对路径>`。
此入口仍执行全部 required/future-required tests；仅将本机调用 Docker 引擎替换为验证
同一精确候选的 `candidate-validation-record/1`。记录只能由既有受保护 Linux
`pre_release_runtime.py` 自行执行真实引擎后，以 candidate-validation 域密钥签发；
Completion 不接受原始 `target-runtime-evidence/1`、调用方公钥或调用方 probe 声明。
解析器与 trust 必须先在当前 GitHub main 获批，候选对应 Git blob 必须与 main 相等；
从已批准 Git blob 加载解析器，禁止借候选修改公钥或解析器来自签验收。
origin 必须指向本系统正式 GitHub 仓库；main 必须仍与 origin/main 一致且为候选祖先。
记录签名、目的、域、撤销、有效期、
完整候选 binding 与全部 13 项观察必须通过现有校验。记录位于源码外普通非链接文件，
在全部测试和身份验证期间保持字节不变；验证前后重新核对批准来源、记录及候选。
该模式保留已验证的不可变 Image ID，不再次构建；输出记录其 SHA、record ID、
authority commit 和有效期。非 container 项目不能携带此参数；错误记录直接 FAIL，
不得自动改走本地引擎以掩盖失败。缺少记录时保留原有引擎 PASS/FAIL/BLOCKED 语义。
候选验证记录不等于 Production Approval 或 production write grant；正式发布仍须对实际
生产实例进行 same-image pre-release revalidation。
Registry/4 能力发布本身不表示容器验证器、Production Runtime v2 或业务 wiring 已闭包。

### 3.2 Runtime Mode 与写入保护

`runtime_target=none` 的 ordinary Business 不要求 runtime root、marker 或 production evidence，
无需创建占位 marker。只有实际使用 Runtime 的任务才适用相应 Runtime Mode/root/marker 检查；
高风险 lane 与生产 Runtime 合同不变。

当前 `03_src/agri_research_agent/shared/runtime_context.py` 实现五种 Runtime Mode：

| 模式 | 当前语义 |
|---|---|
| `fixture`（`RuntimeMode.FIXTURE`） | 测试夹具和系统临时目录内的临时 runtime root |
| `isolated-dev`（`RuntimeMode.ISOLATED_DEV`） | feature/worktree 自己的开发 Runtime，只能写自身 root |
| `formal-readonly`（`RuntimeMode.FORMAL_READONLY`） | 可读取经过批准且身份匹配的正式 Runtime，禁止写入 |
| `production-write`（`RuntimeMode.PRODUCTION_WRITE`） | 正式数据更新入口；要求 formal identity、预期 runtime ID、formal classification 和正式门禁 |
| `candidate-validation`（`RuntimeMode.CANDIDATE_VALIDATION`） | 独立临时容器验证；要求候选域执行授权与 candidate-validation marker，不能授权生产写入 |

生产写入须显式选择 Git 或 OCI execution request 并通过对应验证，不作类型探测后的
fallback。Git 路径保持真实检出与 Approved Commit/Tree 检查；OCI 路径需要受信任 host
签名及镜像内身份共同验证，不依赖镜像中的 `.git`。现有 FULL DAILY Wrapper 的独立
bootstrap/Approved 校验不因此被替换。能力进入 main 不表示信任公钥已配置或生产已部署。

Runtime root 使用 `.market-data-runtime.json` 标识。`RuntimeContext` 执行 fail closed：
marker 缺失、runtime identity/classification/module 不匹配、目标 resolve 后越界、
符号链接或 junction 穿越边界、formal-readonly 写入等情况均拒绝。linked Git Worktree
不得进入 production-write；生产正式写入必须来自经过批准的正式入口。该保护只说明
当前 RuntimeContext 已能执行的本地边界，不代表任何未来服务器写入流程已经实现。

### 3.3 Reference Data 与 legacy test-data compatibility

Feature Worktree 因 Git ignore 可能天然没有 `01_data/`、`06_outputs/`、`10_logs/` 等
本地运行内容。不得为了让测试通过而默认复制正式 Runtime、复制
current/previous/release index、创建指向正式可写 Runtime 的 junction/symlink，或让
多个 Worktree 共享 writable Runtime。

开发和测试所需数据按以下优先级选择：

1. fixture；
2. isolated-dev Runtime；
3. 经过批准的只读 reference snapshot；
4. 明确批准的 formal-readonly 数据。

对尚未完全解耦 Git 外历史测试数据的 legacy tests，可以在稳定、只读的参考数据环境
中运行测试，同时显式加载 Feature Worktree 源码。该兼容方式必须记录源码绝对路径、
参考数据来源和只读保证；测试不得更新正式数据，也不得因此获得 production-write。
此方式称为 **legacy test-data compatibility**，不是新业务数据架构的推荐模式。

### 3.4 Python 环境

多个 Worktree 不得同时对同一个 venv 执行安装、升级或卸载。任务不修改依赖且已有
验证过的解释器足以运行测试时，可以通过绝对路径调用该解释器，但必须记录解释器
绝对路径和 Python 版本，并保持依赖环境只读。若 feature 需要新增依赖、改变版本或
重新解析环境，必须使用独立环境，并把依赖变化列入明确开发范围。本文不要求每个
Worktree 机械复制完整 venv。

### 3.5 Scoped Tests 与 module_test_map

`02_configs/module_test_map.yaml` 是代码模块到 `direct_tests`、`impact_tests`、
`dependents` 和 `full_regression_when_changed` 的声明式映射。它提供影响范围事实，
不取代 `04_scripts/quality/run_scoped_tests.py` 测试入口，也不取代
`04_scripts/quality/audit_changed_scope.py` 范围审计入口。

- Direct Tests 验证被修改模块自身；
- Impact Tests 验证其直接依赖和相关业务；
- Full Regression 在公共或高风险模块声明要求、发布条件触发或任务明确要求时执行。

当前 `shared.runtime_context` 属于高风险共享基础，配置为
`full_regression_when_changed: true`。不得把当前某次实施的具体文件数或测试数量作为
长期规则。


禁止：

```text
git add .
git add -A
git commit -a
```

提交闸门：

1. `git status --short`
2. `git diff --check`
3. `git diff --stat`
4. `git diff --name-status`
5. 显式 `git add -- <允许文件>`
6. `git diff --cached --check`
7. `git diff --cached --stat`
8. `git diff --cached --name-status`
9. 普通 Business 按需运行开发反馈测试；高风险 lane 运行必需的提交前测试和语法检查

11. `git show --check --stat --oneline HEAD`
12. 确认提交只含允许文件

## 6. GitHub main-first 推送

本仓库采用 main-first：

1. 普通 Business 在独立 feature worktree 开发、提交并 push feature，取得真实 hosted `trusted-main-admission-v1` PASS 后在任务已有授权内接纳精确 Commit/Tree；不要求 Completion 或独立 integration。Shared lane 必须取得由可信 Scope、required/impact/必要 full tests 得出的 strict hosted PASS。Governance root 修改则在全部技术检查通过后返回 GOVERNANCE_ROOT_APPROVAL_REQUIRED，由 Maintainer/Admin 按治理合同精确接纳。不得把治理待接纳状态称作普通 PASS；不能把 shared 改名为 business。
2. 获取远程状态并确认没有意外变化，且 `origin/main` 是获批 HEAD 的祖先。
3. 从获批 branch 使用普通 fast-forward 更新 `origin/main`；不得先把 local main 变成开发 integration 场地。
4. 推送后核对获批 HEAD、`origin/main` 和 `ls-remote main` 指向同一完整 SHA。
5. 最后 fast-forward 同步本地 `main` checkout，并核验它 clean、ahead/behind 为 `0/0`。

普通 Business 在 main 写入前通过 GitHub API 只读核验以下现有证据，不新增 receipt 或审批系统：

- `GET /repos/{owner}/{repo}/commits/{candidate_sha}/check-runs`：核对当前 workflow run/attempt
  对应的 `trusted-main-admission-v1`，`head_sha` 等于获批 candidate，`status=completed`、
  `conclusion=success`、`app.slug=github-actions`、`app.id=15368`；不能用同名其他来源或旧 run 的 PASS 替代。
- 核对该 run 的现有 `main-admission/1` artifact：`final_result=PASS`、
  `business_scope=PASS`、无 failure codes，tests 非空且全部通过；candidate Commit/Tree
  与 GitHub commit 对象和拟推送对象相同，trusted main Commit/Tree 与 fresh 远端 main 相同。
- `GET /repos/{owner}/{repo}/git/ref/heads/main`、远端 feature ref、`git fetch` 与
  `git ls-remote` 重新确认 main/candidate 未漂移；`git merge-base --is-ancestor` 确认严格 fast-forward。
  main 变化须以新 main 重跑 Admission，candidate SHA 变化须重新获得 hosted 技术验证；Business/Shared 必须重获 required check PASS，治理升级须重新取得对应精确对象的 Maintainer/Admin 接纳。
  即使 Tree 未变，旧 SHA 的 successful check 也不可复用。
- 只推送已验证且在任务接纳授权内的完整 SHA：`git push origin <approved_candidate_sha>:refs/heads/main`，
  不用可能移动的 HEAD 替代。Business/Shared 保留 Active Ruleset、required check 和无 bypass；被拒绝时停止，
  不自行 Disabled Ruleset。推送后核对 GitHub main / origin/main / local main 的 Commit/Tree 一致。

以下 Git 核验在上述 lane 验收及适用授权核验后执行：

```bash
git status --branch --short
git remote -v
git branch -vv
git rev-parse HEAD
git fetch origin
git rev-parse origin/main
git log --oneline origin/main..HEAD
git diff --name-status origin/main...HEAD
git push origin <approved_candidate_sha>:refs/heads/main
git fetch origin
git rev-parse origin/main
git ls-remote origin refs/heads/main
# 在单独的 local main checkout 中执行：git merge --ff-only origin/main
# 然后核验：git status --branch --short
```

禁止 force push。GitHub main 更新不会自动改变生产。

## 8. 服务器可信检出

正式标准是服务器独立只读浅克隆，不使用 worktree。

固定要求：

1. 在全新、唯一的临时隔离目录开始。
2. 使用固定 SSH 包装脚本执行 `git ls-remote`，取得远程 `main` 完整 SHA。
3. 正式部署确认目标完整 SHA 等于本次明确批准的 SHA，且位于刚核验的远程 `main` 历史中；候选快照阶段则核对获批 candidate ref 的在线 SHA 与目标完全一致。
4. 使用只读 Deploy Key 建立独立浅克隆；正式部署取得可信 `main` 中的批准提交，候选快照取得上述获批 ref。浅历史不足以证明祖先关系时，必须补齐所需历史后验证，不得推断通过。
5. 检出目标完整 SHA，并保持 detached HEAD。
6. 核验本地完整 HEAD、Tree SHA、工作区 clean。
7. 执行必要的 `git fsck --connectivity-only`。
8. 记录检出命令、退出码、SHA、Tree 和验证结果。
9. 验证全部通过后，才允许把候选源目录原子发布为隔离的完整 SHA 目录。
10. 只有 `checkout_passed=true` 和 Manifest 通过才允许构建。

可信检出必须使用完整目标 Git SHA。首次检出失败后，必须冻结失败目录及日志，
在新的唯一 `attempt` 目录重新开始；不得在失败的 Git 对象库中继续 fetch、checkout、
reset、repair 或作为构建输入。第二次出现同类对象错误时停止盲目重试，转入文件系统、
并发清理、外层超时、I/O 或 OOM 专项调查。

绝对禁止在 `/home/ubuntu/market-data` 正式仓库中执行：

- 新版本 checkout 或分支切换；
- 依赖安装；
- 测试；
- 镜像构建；
- 作为候选构建上下文；
- 任何会改变正式仓库 HEAD 或工作区的准备操作。

## 9. 候选镜像

所有候选构建必须在隔离候选源目录完成。

候选镜像必须：

- 使用版本化、不可变、绑定 Git SHA 的镜像引用；
- 禁止使用 `latest`、`new`、无标签或 Compose 隐式镜像名作为身份；
- 记录完整 Image ID；
- `org.opencontainers.image.revision` 等于目标完整 Git SHA；
- 记录必要的 source、created、title 和 version；
- 保留原始构建命令、退出码、输出和 inspect；
- 不覆盖当前正式镜像标签或回滚对象；
- 通过目标应用所需的镜像和部署契约验证。

候选容器启动前必须执行 seal preflight，同时验证不可变标签、完整 Image ID、
OCI revision、Git Commit、Git Tree 和 Release 元数据。任一字段缺失或不一致立即
停止；不得修改既有候选结果或失败证据使其看似通过。

OCI revision 只承担完整 Git commit SHA 身份。Tree SHA 不要求写入 OCI
标签；它由可信 `tool_repo_root` 的 `HEAD^{tree}`、Release 产物、镜像内
`/app/RELEASE.json`、候选结果、部署计划、部署结果及各自 Manifest 传播和
验证。

候选验收与正式部署必须复用完全相同的 Image ID。该原则适用于三个正式应用，不因某个应用尚未完成自动化工具建设而降低。

## 10. 候选容器和验收

候选容器必须：

- 只绑定 `127.0.0.1` 测试端口；
- restart policy 为 `no`；
- 正式数据只读挂载；
- 日志、缓存和临时文件写入候选隔离目录；
- 核验容器 ID、Image ID、OCI revision、容器内 `RELEASE.json` 的 Git/Tree
  SHA，以及 Docker inspect 实测运行时 `MARKET_DATA_GIT_HEAD`；
- 检查根页面、健康接口、RestartCount、日志和受影响页面；
- 验证其他生产容器、正式 Git 和业务数据没有变化；
- 截图或浏览器证据必须来自候选容器。

验收结束后：

1. 只有实际候选容器的 Image ID、OCI revision、容器内 Git/Tree SHA 和
   inspect 实测运行时 Git SHA 全部匹配 Release 后，才生成不可覆盖的
   `candidate_result.json`；运行时 Git SHA 不得人工输入。
2. 生成并验证 `candidate_result.manifest.json`。
3. 保存必要日志、inspect、HTTP、页面和数据不变性证据。成功和失败候选均
   使用同一有限日志摘要：最多最后 200 行、最多 64 KiB，记录采集时间、
   原始采样字节数、脱敏尾部 SHA-256、截断状态和 warning/error 数量；不得
   保存无限完整日志、完整 inspect 环境变量或敏感值。日志读取失败只能记录
   受控 `unavailable` warning。
4. 成功候选和失败候选均删除候选容器。
5. 重新证明候选容器不存在。
6. 保留已验收候选镜像 Image ID、`candidate-data`、数据 Manifest、候选结果及
   Manifest、失败证据和可信源码身份。
7. 只有完成以上步骤，才允许生成 `deployment_plan.json` 和 `deployment_plan.manifest.json`。

候选容器、候选镜像、`candidate-data`、候选运行视图、候选结果和失败证据是不同
生命周期对象。候选容器不得长期保留；候选运行视图可以按证据和批准规则清理。
`candidate-data` 至少保留到 `deployment_result`、其 Manifest 和 bundle Manifest
密封、生产稳定性确认、复盘归档完成且另行获得明确清理授权；不得随候选容器自动
删除。

## 11. 当前强制发布产物

当前强制事实链产物是：

| 目标产物 | 对应 Manifest |
|---|---|
| `release.json` | `release.manifest.json` |
| `candidate_result.json` | `candidate_result.manifest.json` |
| `deployment_plan.json` | `deployment_plan.manifest.json` |
| `deployment_result.json` | `deployment_result.manifest.json` |
| 部署结果集合 | `deployment_result.bundle.manifest.json` |

要求：

- 四类 JSON、对应 Manifest 和部署结果 bundle Manifest 均采用排他创建实现；内容在内存完成序列化和
  校验、临时文件完整写入并 `flush`/`fsync` 后，以硬链接排他创建正式路径，
  不得通过 `os.replace` 覆盖已有目标；
- 每个 Manifest 至少密封目标文件名、SHA-256、字节大小、目标 Schema 版本、生成时间、Release Git SHA、Tree SHA 和 Image ID；候选结果与部署结果 Manifest 还密封容器 inspect 实测的运行时 Git SHA；
- 任何后续阶段读取 `release.json`、`candidate_result.json`、`deployment_plan.json` 或 `deployment_result.json` 前，必须先验证对应 Manifest；
- `release.env` 和 `checksums.sha256` 暂作为 Release 兼容产物继续生成；`checksums.sha256` 仍校验 `release.json` 与 `release.env`，但不能替代 `release.manifest.json`；
- `deployment_plan.json` 必须从已验证的 Release 和候选结果继承 Git SHA、Tree SHA
  与候选 Image ID，并显式记录 `tool_repo_root`、`production_compose_file`、
  `production_project_dir`、Compose 项目名、服务名和独立的
  `deployment_tool_revision`；业务 Release revision 与发布工具 revision
  可以不同，不得因工具升级要求重新构建已验收业务镜像；
- 计划生成前必须只读审计当前生产 Compose、env、容器、镜像、数据、端口和挂载，
  并同时锁定当前基线与目标身份，至少包括
  `production_baseline_compose_sha256`、`production_baseline_env_identity`、
  `production_baseline_image_id`、`target_compose_sha256`、`target_env_identity`、
  `target_image_id`、`target_git_commit`、`target_git_tree` 和目标数据 Manifest；
- 生成计划不得要求生产 Compose 或 env 已经等于目标 Release。Compose 与 env 必须
  一次性审计、一次性预演、一次性纳入计划，并在正式部署事务中联合原子同步；失败时
  按计划锁定的生产基线联合回滚；
- 正式执行 argv 必须直接进入 `deployment_plan` Schema 并由 Manifest 密封。核心
  安全参数变化时必须重新生成计划及 Manifest，不得在计划密封后用独立 execution
  amendment 补充或改变正式切换参数；
- 首次数据发布允许 `first_release=true` 且 `existing_file_count=0`，但必须生成空
  基线 Manifest。非首次发布若正式文件数意外为 0，必须与上一份
  `deployment_result` 对账并停止；
- `tool_repo_root` 是已批准发布工具的独立只读检出；`production_compose_file` 是正式切换实际使用的 Compose 文件；`production_project_dir` 是 Compose 相对路径、挂载源和 `env_file` 的正式解析基准；
- 计划中的生产 Compose 路径必须为经过校验的绝对路径。不得通过脚本目录、当前工作目录或 `/home/ubuntu/market-data` 的 HEAD 隐式推导；
- Release Git SHA、Tree SHA 和候选 Image ID 在候选结果、部署计划和部署结果任一级不一致时必须停止；
- `candidate_result.json` 必须保存候选容器 inspect 实测的运行时 Git SHA
  及有限脱敏日志摘要；其 Manifest 通过目标文件 SHA-256 密封该摘要身份；
  `deployment_result.json` 必须分别保存计划目标 Git SHA、正式容器 inspect
  实测运行时 Git SHA 和验证结果。缺失、空值、冲突值或不一致时不得生成成功结果；
- `deployment_result.json`、对应 Manifest 和 bundle Manifest 是正式部署的强制
  最后阶段；缺少任一产物不得宣称发布完整完成；
- 代码、镜像和运行数据必须形成三条分别密封的身份链：Git Commit/Tree、候选及
  正式 Image ID、逐文件数据 Manifest。代码已进入 Git 不代表数据已发布，镜像验收
  成功也不代表运行数据已发布；
- 缺失事实只能进入明确标记的追溯重建流程，不得伪造原始测量值。

以下暂列为待实现增强项，不是当前强制产物：

- `approval_record.json`
- 部署前 runtime JSON
- 部署后 runtime JSON
- 浏览器检查 JSON
- 自动化生成的部署前/后生产基线

只有对应脚本、Schema 和测试完成后，才可将增强项升级为强制要求。

上述产物、Tree SHA 传播、候选结果生成、计划生成、正式切换和部署结果记录的候选
实现位于 `09_deploy/spread_release/`，适用于 `spread-dashboard`。当前工具已实现
`current_production`/`target_release`、plan 内 argv、执行前基线防漂移、
执行阶段 env 原子切换与回滚恢复。候选数据生命周期仍按本规范的
独立契约处理。USDA 与 Oil World 必须遵守同一事实链和
同一 Image ID 原则，但一条式自动化工具仍待实现；不得把 spread 工具的存在描述成
另外两个应用已经自动化。

## 12. 正式部署

正式部署必须：

1. 获得用户对目标完整 SHA、同一 Image ID 和密封计划的明确批准。
2. 重新验证 Release、候选结果、部署计划及其 Manifest。
3. 从隔离只读检出中的发布脚本执行，并证明 `tool_repo_root`
   的 HEAD 和 Tree SHA 等于计划密封的 `deployment_tool_revision`；
   不得要求它等于业务 Release，也不得要求正式仓库 HEAD 等于新 SHA。
4. 从已验证计划读取 `production_compose_file`、`production_project_dir`、Compose 项目名、服务名和 `candidate_image_id`。
5. 证明候选容器已经删除。
6. 证明目标 Image ID 与候选验收 Image ID 完全相同。
7. 在任何写入前重新确认实际 env、Compose 和容器仍等于计划密封的
   `current_production`；随后由官方 helper 原子更新 env 为 `target_release`。
8. 从计划读取已经密封的执行 argv，只切换计划指定的目标服务，并同时包含
   `--no-build --pull never --no-deps --force-recreate`。
9. Compose 可以保留静态 `build:` 定义；安全门槛检查实际执行 argv，不得仅因
   YAML 存在 `build:` 就拒绝。正式事务禁止 `docker build`、`docker compose build`、
   `--build`、`latest`、`docker compose down` 和任何 prune。
10. 不无必要地重建或重启其他应用。
11. 核验正式容器实际 Image ID、OCI revision、容器内 Git/Tree SHA 和 Docker
    inspect 实测运行时 `MARKET_DATA_GIT_HEAD`；实测运行时 Git SHA 必须等于
    计划目标完整 SHA，实际 Image ID 必须等于候选结果和部署计划记录值。
12. 验证端口、挂载、环境、HTTP、页面、数据和其他应用不变。
12. 最后生成并密封 `deployment_result.json`、`deployment_result.manifest.json`
    和 `deployment_result.bundle.manifest.json`。

对尚未完成一条式自动化部署的应用，可以使用经过审核的受控步骤，但仍必须满足同一 Image ID、无正式阶段 build、明确回滚对象和强制部署结果要求。工具缺口必须如实记录。

#### 未启动容器授权的分步切换

要求对未启动容器签发 production grant 的 Runtime，可在已审核并密封的计划中使用
`compose create → pre-release → grant → docker start`。实际服务器的 `compose create`
没有 `--no-deps` 参数，因此创建 argv 必须包含 `--no-build --pull never --force-recreate`，
并先验证目标 Compose 仅有本次服务、没有依赖、profiles、links、extends 或 lifecycle hooks。
不得给 create 添加不存在的参数，也不得用 `compose up` 提前启动。
启动 argv 只允许 `docker start <created-container-id>`；该 ID 必须由本次 create 后的 inspect
获得，并与 pre-release 报告和 grant 一致。计划必须事先声明这个唯一实测绑定及完整命令模板，
不得允许操作者另填 ID、修改参数或补写 execution amendment。此命令本身不能构建、拉取镜像或启动依赖。
创建和启动前后均核验 Image ID、配置、挂载、容器清单和其他服务身份；grant 前启动、
额外服务变化或镜像变化立即失败。计划还必须预封旧容器停止与改名保留、失败恢复原名并启动
的精确步骤，并规定服务不可用窗口。此分步方式只替代直接 up 的四参数切换形式，其余事实链、
审批、数据保护、排他封存和回滚要求全部保留。
受控步骤可定义独立的 artifact schema 版本，但仍使用第 11 节的强制文件名及对应 Manifest，
逐阶段验证引用和实测值；不得冒用旧发布工具的 Schema 版本或绕过 Runtime 身份校验。

当宿主 policy 的 `actual_config_sha256` 只能在 create 后测量时，Release 和 Plan 必须在
create 前密封受保护的 `policy_template` 路径、字节 SHA-256、全部静态策略字段、唯一的
最终 policy 路径和派生命令模板。模板只允许缺少 `actual_config_sha256`；该字段必须按
宿主现有 observation 原语对本次 Docker Config、HostConfig、Path、Args 计算，写入
不可覆盖的 `created_instance_binding`。模板不是有效的宿主 policy，禁止将模板哈希、
占位值或预测值称为最终 policy 哈希。

create 后先封存实例 binding，再从已核验模板仅补入 binding 的 `actual_config_sha256`，
排他新建通过既有宿主 parser 的最终 policy。其余字段必须与模板逐字段一致；不得借此
改变角色、镜像、Commit/Tree、挂载、Compose、环境、candidate record 或信任域。随后
排他封存 `policy_binding`，记录 Release/Plan/template/created-instance-binding 和最终
policy 的 SHA-256；pre-release、grant、start 和 Result 均须复核这条派生链及同一实例。
最终 policy 的字节 SHA-256 与宿主报告中的规范化 policy digest 应分别记录和核验。
所有路径、派生字段、校验和 argv 都必须事先进入 Plan；这不是计划密封后追加参数的
execution amendment。旧计划没有该规则时必须重新生成并密封，不能事后补填或覆盖。

创建态与运行态配置摘要必须分别保留原始观测值。Docker Engine `26.1.3`、cgroup `2`
存在已复现的首次 start 转换：`HostConfig.OomKillDisable` 从严格布尔 `false` 变为 JSON
`null`。其依据是 [Moby 对默认值及不支持能力的处理](https://github.com/moby/moby/blob/v26.1.3/daemon/daemon_unix.go)。
只允许在新 Plan 的 `checks.start_config_transition` 中预封该版本、cgroup、字段、前后值
及唯一输出路径，并新增紧随 start、先于 health/consumer 的 `validate_start_transition`
argv。创建、pre-release、grant 前仍须按现有原语精确核对创建态原始摘要；不得改写
created binding、policy、grant，或把规范化值声称为 Docker 原始观察。

启动后先计算完整 Config、HostConfig、Path、Args 的真实原始摘要，再仅在比较副本中
将实际存在的该 `null` 还原为 `false`；副本完整摘要必须等于 created binding 摘要。
字段缺失、`true`、数值 `0`、其它配置变化、引擎或 cgroup 不符均失败。排他封存
`controlled-runtime-start-transition/1` 见证，记录 Plan/binding/实例/镜像身份、版本、
字段和实测前后值、创建态/运行态/比较副本摘要及观察时间。Result 原有
`actual_config_sha256` 保存真实运行态摘要，原有 `binding_sha256` 继续引用创建态；
不增加 Result 顶层字段。Bundle 必须增加唯一 `start_transition` role，并交叉核对
见证路径、Plan、binding、policy/grant/pre-release 的创建态摘要、Result 运行态摘要，
以及唯一成功的见证步骤。后续运行态观察必须精确等于首次运行态摘要，不能反复容忍
转换或反向漂移。见证包含 `failure_reason`：PASS 时为 null；转换校验失败时必须封存
FAILED 见证、固定失败原因和所有已实测摘要，只有无法取得的观测摘要允许为 null。
失败见证须绑定失败步骤及 FAILED/ROLLED_BACK Result，不能转为成功。仅在 start 未成功
且见证步骤尚未执行时可使用原有未执行占位；禁止把已执行但失败的见证伪装成未执行。
这仅是上述已测部署启动转换的规则，不改变 Runtime 验签、权限、时效或通用身份算法。

受控执行须读取最新已明确批准的治理说明，并在 Release/Plan 中单独固定其完整
`governance_revision` Commit/Tree 和文档 SHA-256；运行时不得自动跟随 main。该治理
身份与发布工具 revision、目标业务 Commit/Tree 和已验收 Image ID 分别绑定。治理说明
更新不会自动升级目标生产镜像，也不修改 Runtime 的验签、grant 有效期或续签能力。

## 13. 生产身份

本章镜像身份针对代码部署；FULL DAILY 数据更新不以开发 caller 的 main/clean 身份为门禁。
其正式身份是 Approved Production Commit/Tree、clean detached control-plane 与 tool-repo，
实际业务入口/import/cwd 来自 tool-repo。运行说明统一见 [Windows Wrapper](../04_scripts/automation/说明.md)。
NO_CHANGE 与有合法源缺失证据的 MISSING 不默认阻断；真正数据丢失、mapping/schema/corruption
和摘要不一致仍 fail closed。本文件不重定义 Async/Missing 或 Domestic Basis 业务政策。
Prewarm 不参与 DATA_READY 核心判定；Prewarm Separation 仍为未闭包 candidate，不得宣称已生产启用。

不得使用以下单一信息证明生产版本：

- 目录修改时间；
- 容器名称；
- 镜像标签字符串；
- GitHub main；
- 旧容器 `Config.Image`；
- `latest` 或 `new`。

生产身份至少核验：

- `deployment_result.json` 和 Manifest；
- 正式容器实际 Image ID；
- OCI revision；
- 容器内 `RELEASE.json` 的完整 Git SHA 和 Tree SHA；
- Docker inspect 从 `Config.Env` 实测的 `MARKET_DATA_GIT_HEAD`，以及它与计划
  目标完整 SHA 的验证结果；
- 当前生产 Git/基线记录；
- HTTP、页面和数据挂载状态。

## 14. 回滚

回滚对象必须在部署计划中明确并经过预校验：

- 上一完整 Git SHA；
- 上一可用 Image ID；
- 生产基线 Compose、env、数据 Manifest、正式容器配置、端口、挂载和环境；
- 回滚脚本或受控步骤；
- 健康检查和数据不变性验证。

回滚禁止重新构建镜像、使用 `latest` 猜测旧版本或删除失败证据。

`spread-dashboard` 使用仓库当前密封 Release 契约指定的部署和回滚脚本。USDA、Oil World 在自动化完善前必须保留明确的上一 Image ID 和受控回滚记录。

## 15. 清理

清理是独立任务。默认禁止：

```text
docker system prune
docker image prune
docker image prune -a
docker volume prune
docker compose down
```

清理前必须盘点容器、镜像、构建源、`candidate-data`、Release、候选结果、计划、
部署结果、Manifest、回滚对象、失败证据和磁盘使用。

任何删除对象必须同时满足：

1. 不是当前正式对象；
2. 不被任何容器引用；
3. 不被发布事实链或 Manifest 作为必需实体引用；
4. 不是唯一回滚对象；
5. 不是事故复盘的唯一证据；
6. 有明确对象名、完整 ID 或经核验的绝对路径；
7. 已获得单独批准。

候选容器不进入长期清理评估，因为它必须在部署计划前删除；候选镜像、
`candidate-data` 和候选证据仍按上述规则保留和评估。结果链未全部密封、生产尚未
稳定、复盘未归档或没有独立清理授权时，不得清理 `candidate-data`。

## 16. 停止条件

以下任一情况必须停止：

- baseline HEAD/Tree 不一致；
- Feature Worktree 不在预期 branch，或存在无法解释的工作区修改；
- 输入数据或 Reference Data 身份无法确认；
- 实际使用 Runtime 的任务，其 Runtime Mode、marker、module 或 resolved root 无法确认；
- 正式 Runtime 被错误赋予写权限，或 linked worktree 试图进入 production-write；
- 修改超出 Change Boundary；
- Shared Dependencies 的修改扩大了影响面，但测试范围未重新计划；
- required Direct/Impact/Full Tests 或本地页面/业务验收失败；
- Git root、common dir、branch、Commit 或 Tree 身份不一致；
- 正式部署目标 SHA 未进入已在线核验的远程 main 历史，或不等于明确批准的生产 SHA；
- 独立候选获取的 SHA 不等于获批 candidate ref 的在线实测 SHA；
- 只读身份、主机身份或包装脚本无法核验；
- 检出不是 detached HEAD、工作区不干净或 fsck 失败；
- 候选源位于正式仓库；
- 候选或正式 Image ID 不一致；
- 候选容器未在计划前删除；
- 计划要求生产 Compose/env 预先等于目标，或没有同时锁定当前基线和目标身份；
- 正式执行 argv 缺少四个安全参数，或包含实际 build、`latest`、`down`、prune；
- 计划密封后试图通过独立 amendment 改变核心执行参数；
- 数据、挂载或其他应用出现非预期变化；
- 回滚对象不明确；
- 强制产物或 Manifest 缺失；
- 用户已有修改、生产事实或文件身份无法解释。

触发停止条件后，不得通过复制未知数据、修改正式 Runtime、扩大权限、跳过测试或
直接去服务器验证来绕过停止点。


已授权普通 Business 开发包括范围内 commit/push feature，不重复要求阶段许可；main 按任务既有授权和精确对象执行。START / RESUME 会 fetch 并写 local Git metadata，不是纯 read-only。
治理实现首次升级时，当前 trusted main 的旧裁判仍有权拒绝 candidate。feature CI 中新裁判的 regression PASS 只证明提案测试通过，不是当前 main 的 admission PASS；不得让 candidate 自选 trusted base、把自身声明为 trusted，或关闭 Ruleset。升级如被旧策略阻塞，报告精确身份和证据，等待用户决定，不伪造已闭包。


Governance Root of Trust：Repository Maintainer/Admin 是治理信任根。Business 正常 branch/worktree → tests → trusted admission PASS → main；Shared/high-risk 使用 strict/impact/consumer tests，未修改治理根时不增加人工治理批准。

Governance root change 完成可信身份、Scope、ownership、required/owned tests、减测和 mutation 检查后，技术失败返回 FAIL；全部通过返回 `TECHNICAL_VALIDATION=PASS`、`MAIN_ENTRY=GOVERNANCE_ROOT_APPROVAL_REQUIRED`。这是正常的待治理根接纳状态，不是普通 PASS。没有 candidate-side approval API、token、文件或 workflow 可把它升级为 PASS。最终接纳由 Repository Maintainer/Admin 在自动化之外批准精确 base/Commit/Tree。

`CANDIDATE_CONTROLLED_SELF_APPROVAL = NO`；`MAINTAINER_GOVERNANCE_ROOT_OVERRIDE = YES_BY_DESIGN`；`PROJECT_EXISTENCE_APPROVAL_REQUIRED = NO`；`ORDINARY_BUSINESS_NEEDS_HUMAN_APPROVAL = NO`。前者约束可信 validator 的权限授予，不能把候选同名绿色 check 当成可信来源证明；Maintainer 需审查执行来源及精确证据。不声称平台能防止 Admin 覆盖自己管理的规则。

Admin 权限只用于 Governance trusted-root transition 或灾难恢复，不得绕过普通 Business check、普通测试失败、scope violation、production release 或数据质量 gate。治理根接纳不能把技术失败改成 PASS。日常保持 Ruleset Active、bypass_actors=[]；极少数治理接纳按 [Governance Transition 合同](templates/GovernanceTransition.md) 的短时 Admin 操作完成并立即恢复，不能长期放宽普通开发。

Production 独立 release：Approved identity、Commit/Tree/Image、Manifest、release gate、rollback、candidate 不写 production、生产单独授权全部保留。已授权普通业务不重复申请 commit/push 或项目存在许可；任何任务明确的 main/生产禁止仍优先遵守。
