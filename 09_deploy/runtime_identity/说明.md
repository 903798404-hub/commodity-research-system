# 主机执行授权工具

`host_authorization.py` 是生产执行身份合同的主机侧工具。它从 Docker
读取实际容器、镜像、配置、挂载和 RELEASE 数据，校验这些观测是否符合受保护
的主机策略，之后才签发短时效 Ed25519 grant。签发入口不接受调用方提供的
`observed` 字典。

生产 grant 与 candidate validation grant 使用不同的 trust domain。v1 候选验证只
允许 `/tmp` 容器路径；v2 候选验证使用宿主临时 scope 证据，容器路径与生产使用同一
Runtime Manifest 合同。grant 以 `O_EXCL` 独占创建，已有 grant
绝不覆盖；私钥保持 root-owned、0600。Docker socket、host namespace、特权容器、
设备、额外 capability、可写 rootfs 和 root 用户都会被拒绝。

本工具不启动或部署业务容器；部署编排器只能在 grant 密封并以只读方式注入后，
启动已经完成实际检查的新容器。

本阶段只完成主机观测、纯校验和签发接口，尚未完成真实 Linux Docker candidate
验证。公开 trust 配置已登记两个独立 v2 域；这不代表已签发 grant 或具备生产可用授权。
程序读取 Docker 和受保护策略，写入一次性 grant；人工不得直接修改已签发 grant。
正式生产数据、secret、私钥和持久业务 volume 不得放入本目录；candidate 临时
文件只在候选生命周期内存在。

本源码目录不是临时目录。人工可通过项目治理维护代码和 Schema；程序不在本目录生成运行产物。

## 调用与兼容

[RuntimeContext](../../03_src/agri_research_agent/shared/runtime_context.py) 显式接受
[GitExecutionRequest 或 OCIExecutionRequest](../../03_src/agri_research_agent/shared/production_identity.py)，
不探测后自动切换类型。Git 路径必须属于当前实际执行源码、正常 checkout、clean、完整 Approved
Commit/Tree 一致；空 `.git`、linked worktree、其他 checkout、隐藏索引变更或 Git 身份重定向均拒绝。
Approved 输入由可信调用链提供，不能从 runtime marker 推导。

`FORMAL_READONLY` 保持只读。`PRODUCTION_WRITE` 和新的 `CANDIDATE_VALIDATION` 每次写入前
都重新验证材料；候选使用 `candidate-validation` 标记及独立签名域。module、runtime ID、marker SHA、
resolved path 和签名 writable roots 共同限制写入。返回的验证对象不能作为长期授权缓存。
FULL DAILY trusted checkout/Wrapper 保持原有更强校验，不要求立即迁移到本库。

`artifact_origin=candidate` 与 `role=production` 可以同时成立；正式批准后可以提升同一个 Image ID。
artifact 来源、实际部署角色和写权限不是同一个字段，历史镜像 deployment label 不能授予权限。

## 宿主策略与执行顺序

宿主策略显式分派严格的 `host-runtime-policy/1` 与 `/2`。两者的共同字段由 `validate_policy` 限定：身份字段及
Approved Commit/Tree、Image ID、artifact service/RELEASE application、source/runtime 根、manifest
路径与 SHA、marker/RELEASE/实际配置 SHA、实际 mounts、按序 Compose `[{path, sha256}]`、真实
project directory、受保护 env 文件、rendered Compose SHA、grant 容器目录与 candidate host root。
这些是实例数据，不写入业务源码 runtime manifest；生产角色的 candidate host root 必须为空。
v2 额外要求 `candidate_scope`：production 必须为 `null`；candidate validation 必须精确绑定
受保护 descriptor 的路径、SHA-256 和 32-hex scope ID。

v2 的 `runtime_root` 必须等于 hash-bound `runtime-manifest/2` 中 `identity_root_role` 指向的只读
容器根。production 与 candidate validation 因此使用相同的逻辑容器路径。候选的临时性来自宿主证据：
scope 根由 root 在固定的 `/tmp/market-data-candidate-scopes` mode `0700` authority root 下新建，
descriptor 记录根及每个 bind source 的 resolved
path、device、inode、目标和只读属性。签发器拒绝 symlink、socket/device、regular-file hardlink、scope
外来源、嵌套 host mount、未声明 mount 和发生变化的 inode。descriptor 在第一次签发尝试开始时以
`O_EXCL` 写入并同步消费凭据及父目录；即使后续检查失败或宿主重启，同一 scope 也不能重放。

宿主签发器及其 grant/manifest parser、公开 trust 配置必须从 root-owned、祖先不可被非 root 改写的
authority source checkout 执行；v2 Compose source 与 project directory 也必须来自同类受保护快照。
控制面先创建未启动的容器，设置随机 32 位 hex hostname nonce，再以受保护审批策略绑定完整实例。
签发器只处理 `created` 状态，内部实际 inspect、读取容器文件并验证：

1. OCI revision/tree/service/release label、不可变 Image ID、原始 RELEASE 字节和 Approved 身份；
2. 数字非 root UID、只读 rootfs、cap_drop ALL、no-new-privileges、命名空间和设备边界；
3. 真实 Compose 来源标签、按序 source SHA，重新渲染后逐项比较实际 image/entrypoint/Cmd/env/mount；
4. 容器内 manifest、marker 和公开信任锚原始字节，以及 manifest roots/mount 权限；v2 使用项目内
   Python 3.10 兼容的 source parser，并要求签名 writable roots 精确等于 manifest 的 `rw` roots；
5. 真实 host mount source；拒绝控制 socket/device、代码覆盖或候选目录外的挂载；
6. 私钥的公钥必须在当前镜像信任配置中属于请求角色且未撤销；
7. 签名前重新检查实例、Compose、manifest、marker、信任锚、mount source 和 candidate descriptor，
   必须仍是同一个未启动容器和同一组宿主文件身份。

当前授权版本仅接受显式 bind mount；其他类型保持拒绝，不静默近似。grant 目录为 root `0755`，
只读注入容器，grant 文件为 `0444`；private key 和审批策略为 root `0600`。祖先不可被其他用户
改写；候选临时根可经过 root sticky `/tmp` 祖先，但临时根本身必须由 root 控制。
私钥不得进入镜像或任何业务挂载。容器密封 grant 后的启动、失败清理和恢复由部署控制面负责。
授权最长一小时；过期、证据缺失或身份变化立即拒绝后续写入，不自动续期。

## 信任与测试边界

[公开信任配置](../../02_configs/production_runtime_trust.json) 登记
`production-runtime-v2-production-20260905` 与 `production-runtime-v2-candidate-20260905` 两个独立域。
公钥作为受审查的源码变更进入候选镜像；对应私钥只保存在获准宿主的 root-owned `0600`
`/etc/market-data/runtime-identity` 目录。候选与生产密钥不可复用，也不能通过环境变量
替换信任锚。[机器 grant Schema](production_authorization.schema.json) 同时精确描述
`production-execution-grant/1` 与 `/2`。宿主和容器共用不依赖 `jsonschema` 的标准库 shape parser；
JSON Schema 保留为本地/CI 一致性 oracle。
Ed25519 签名覆盖排序 key、无额外空白、UTF-8 的 payload，固定版本及算法必须精确匹配。

签名绑定 Approved/RELEASE Commit/Tree、Image ID、RELEASE/manifest/marker SHA、实际配置、
rendered Compose、mount identity、container ID、nonce、角色、roots、grant ID 和时效。
v2 另绑定 runtime manifest schema、identity root role，以及候选角色的 scope ID/descriptor SHA；
production 的两个 scope 字段必须显式为 `null`。不同版本的 policy、manifest 或 grant 不允许混配。
容器库不能独立向 Docker 查询 Image ID；这一事实来自宿主真实观测与签名，容器内再验证不可变材料。
单元测试模拟 OS/Docker transport，但真正执行哈希、签名、Schema 和拒绝条件，不能代替真实容器门禁。
本工具不捕获业务数据、不通知、不调度、不提升 Approved Production。

## Release planning 与 execution authorization

### Candidate validation claim 与 secret declaration

`candidate-validation-record/1` 的唯一解析/验签合同仍是
`candidate_validation_record.py`。`evidence.spread_runtime_packaging` 是显式可选的
**signed claim**（不是被忽略的扩展，也没有第二套外部 evidence-only 权威）。旧记录
可以缺少它；当前 spread validator 必须输出完整对象。字段被 evidence SHA256 和
envelope 签名覆盖，任何顶层或嵌套未知字段、缺少必需字段或类型错误均拒绝。

对象必需字段及规则：Commit/Tree/Image/OCI/role 与核心 binding 相等；`grant_binding`
含精确 Commit/Tree/Image、64位 container ID 和 runtime ID；`import_closure` 含正整数
required/manifest/Dockerfile counts 与三个空 missing lists；四个 `lifecycle_imports`
全部 PASS；`probe_stages` 必须逐项等于核心13 probes。`readonly_initialization` 是完整
`spread-runtime-preflight/1` 对象，其身份匹配、exit_code 为整数0、AppTest/strict page
为 PASS、capture/Tankan secret/network 均未执行。spread 项目不得缺少初始化；其他项目
未执行时只能使用 null 和 NOT_EXECUTED，不能自报 PASS。

`workflow_run_id` 为数字字符串或 null；`timestamp` 为带时区 RFC3339；固定候选信任
不带 ephemeral fingerprint/persistence 声明，已有 Hosted ephemeral 候选信任必须声明
私钥未持久化、未进入容器，生产 key 未使用。可选 `service_credential_mounts` 必须含
declared_readonly、undeclared_rejected、wrong_target_rejected、writable_rejected 四项 PASS。
完整精确字段集合与类型/交叉规则只由上述 parser 定义；不接受 allow-extra。

Candidate file secret 必须由 Runtime Manifest 的精确 `secret_references` 和绑定源
Compose 的精确 source→target 声明共同解析。实际候选 Compose 可以只选择声明的
secret，但不得改 target、增加未知 secret、重复声明、引入非 file secret 或 RW mount。
每个 file secret 都在新的候选 scope 内分配 root-owned RO 文件，Service Credential
仍由既有 issuer 在 fresh created container 校验后填入，随后签发原有 candidate grant。
无 namespace wildcard、额外 path allowlist 或跳过 mount validation。

Hosted Admission 同时保存真实 engine evidence 和由正式 parser 验证的 signed record
**测试夹具**；测试 record 使用 host 内存中的一次性候选 fixture key，不是生产 trust
anchor，也不能交给 production release 使用。生产 `pre_release_runtime.py` 的固定主机
candidate signer、trust、撤销、有效期、source 和同一镜像检查保持不变。

历史 grant 到期是正常行为，不用于否定已经 running 的 production 身份或回滚镜像资产。
发布风险与资产评估见正式发布规范14.1–14.3和 `pre_release_runtime.py --release-request`。
本工具只向 fresh created instance 签发；新启动、restart 或 rollback 应创建新实例并签发
新 grant，不能给旧 running/stopped 实例续期补签。长期运行不代表 grant 成为永久授权：
后续受保护操作仍按现有 verifier 校验，写入前校验不变。风险评估不调用本工具签发、
不延长 TTL、不修改签名域、不放宽 Compose/mount/nonce/Commit/Tree/Image 绑定。


### Stateful reversibility calibration

Stateful does not automatically mean full rollback rehearsal. Validation depth
follows reversibility and destructive-state risk. `pre_release_runtime.py`
保留两个顶层风险，另输出 STATE_CHANGE_CLASS、FULL_ROLLBACK_REHEARSAL_REQUIRED 和
TARGETED_RECOVERY_VALIDATION_REQUIRED。`release_reversibility.py` 只读取 exact Git trees，
不执行 candidate 代码，不接受 low-risk override。独立新增 bind + 有界直接文件 I/O
可证明 additive；没有明确 destructive evidence 的自定义业务/config 覆盖缺口输出 NEEDS_MAINTAINER_RISK_REVIEW。
Additive 的正式发布不要求真实 targeted recovery PASS；该方法保留为可选诊断和独立
Recovery Runtime Lifecycle Hardening 技术债。若实际调用，旧 exact image/config、fresh grant、
基础 health/HTTP、历史和新增 state 保留仍由现有验证器严格核验，不得伪报 PASS。
Destructive/irreversible 保留 full recovery 和独立迁移授权，人工不能降级。
Maintainer 可按 diff/tests/存储及兼容性审计在普通 JSON review 记录 ADDITIVE_REVERSIBLE 或 HIGH_RISK。
记录绑定 exact base/target/main Commit/Tree 和机器 findings；消费时实时核对 main，任何身份漂移使其失效。
review 不是 execution grant，不自动通过候选 Gate；不新增签名、approval server 或 workflow。Routine 无需 review。
字段及 raw observation 内容以本文下方 Release assessment parser 小节和实际 parser 为准。


## Release assessment 与 rollback 实现参考

本节记录发布控制面的字段与恢复实现，不增加顶层发布 Gate。何时必须运行恢复演练以[标准规范](../../07_docs/03_标准开发与生产发布规范.md#141-发布风险与回滚资产)和当前评估器为准。

### Release assessment parser 与受保护输入

`ROUTINE_STATELESS` 的执行入口改为正式 Routine 发布入口；本节 signed candidate record、recovery
observation 和多级 Manifest 流程继续适用于 `STATEFUL_OR_INFRA`。普通发布不因历史
grant 到期、缺少复杂 Evidence Bundle 或未做 rollback rehearsal 而回到高风险密封流程。

只读分类入口（不表示 release PASS 或生产授权）：
`python -B 04_scripts/runtime/pre_release_runtime.py --classify-release <base完整SHA> <target完整SHA> <project>`。
可加 `--maintainer-risk-review <review.json>` 验证并合并普通 Maintainer 记录；只输出非授权 assessment，不签发 grant、不启动实例。

正式评估从受保护的已批准 governance clean detached 源码执行；target_source_root
另指精确 target 的受保护 clean detached 源码，两者分别核验，不要求旧 target 内已有新版评估器：
`python -I -B 04_scripts/runtime/pre_release_runtime.py --release-request <root-owned请求JSON> --report-output <全新受保护报告路径>`。
请求必须 root-owned 0600，引用文件的祖先均受保护；JSON 重复键按现有 host parser 拒绝。
现有 candidate/production 参数不能混用，入口不签发 grant、不操作实例、不修改数据。
原 `--production-policy` 仍是 fresh instance pre-release Gate，不能用风险报告替代。

机器结构由同一入口的严格字段 parser 定义（未知字段、类型或缺失均拒绝）：

- `production-release-request/1`：schema_version、project_id、current、previous、target_commit、target_source_root、
  candidate_record、state_plan、acceptance_plan、recovery_evidence（Routine 或 Additive 可为 null）。
  可选 maintainer_risk_review 为上述普通 JSON 对象，嵌入同一受保护 release request，不新增审批协议。
- current/previous：commit、tree、image_id、image_location、registry_digest、release、runtime_config、
  data_schema、procedure。文件引用仅有绝对 path 和字节 sha256；分别对应当前及上一正式部署；相同 artifact 的重复部署可共用已核验资产。
- runtime_config：artifact（commit/tree/image_id）、namespace（compose_project/container_name/host_ports）、
  compose/env 文件引用（键为 compose/environment）。data_schema：schema_identity、assets 引用列表，
  空列表仅适用于已确认没有持久业务数据的服务。procedure：artifact、fresh_instance_required=true、
  fresh_grant_required=true、非空 steps。操作负责人必须在密封前审查其实际可恢复性。
- state_plan：base/target（commit/tree）、data_schema_sha256、irreversible（YES/NO/UNKNOWN）、
  compatible、database_migration、production_data_mutation、storage_format_change（严格 bool）。
  这属于可信控制面的审计事实，业务 caller 不得自行创建为减险声明；明确的 migration/mutation/format change 不得由 risk review 覆盖。
- acceptance_plan：target、image_id、非空 checks；candidate_record 必须通过现有签名、期限、
  完整 target source binding 与 probe 验证，不能提交人工 PASS 代替。
- `production-recovery-observation/1`：schema_version、base、target、old_image_id、runtime_config_sha256、
  data_schema_sha256、method（fresh-recovery/blue-green/canary/targeted-recovery）、observed_at、result、evidence。
  evidence 必须逐一引用 instance/grant/preflight/health/consumer/data_unchanged 原始证据。
  instance 包含 container_id/image_id/hostname/created_at/started_at；grant 是现有完整签名 envelope。
  四项 probe envelope 必须包含 container_id/commit/tree/image_id/exit_code/status/raw 文件引用；
  退出码必须是整数0且 status=PASS，逐一匹配同一实例。验证 production 域签名、撤销、精确
  old identity 与 nonce，并核对 created ≤ issued ≤ started < expires、acceptance < expires。
  历史演练 grant 现在可过期，但不得在当时启动或验收时已过期。
  targeted-recovery 复用同一 observation、签名 grant 与原始 probe 引用，不新增审批协议。
  consumer raw 为 localhost HTTP 的 url/status_code=200；data_unchanged raw 包含
  historical_before/after（绝对文件路径→SHA256）、operational_before/after（container_path、
  source、device、inode、相对文件→SHA256 的 files）、old_mounts（source/target/read_only）。
  完整列举所有新增 roots；前后目录/文件身份必须一致，旧 RW mount 不得覆盖新目录。
  原始枚举由受保护 host collector 观察，不接受业务调用者自报 PASS；本分类器不连接服务器。
  fresh-recovery/blue-green/canary 仍为完整恢复证据，targeted-only 不能满足 full 要求。
  它由受保护发布控制面根据真实观测密封，不是 candidate 提供的授权文件；有效期最多24小时，
  实例/grant/消费者和数据不变性仍须在实际切换前复核。HTTP 200 不能单独支持 PASS。
- `production-release-risk/1` 输出精确 base/target、build contract digest、逐文件分类理由和风险；
  正式评估额外输出资产、candidate image、请求 digest、全部失败 predicate 及 production_authorized=false。

旧 grant 不作为请求字段、不读取、不续期；新 grant 只由现有 issuer 在 fresh created 状态签发。
评估 PASS 只是独立生产审批前的准备证据；生产审批、同一验证 Image、数据 Manifest、正式
acceptance 和失败后的恢复步骤全部保留。输入漂移须重做，不得复用旧报告。

### Rollback assets 与 recovery namespace

至少保留当前及上一正式 production 的镜像、Commit/Tree、Manifest、配置和必要数据/schema
材料；清理前证明没有删除这些恢复引用。`LOCAL_IMAGE_ONLY` 明确输出
`HOST_LOSS_NOT_COVERED`，只能在保留该 Image ID 的宿主恢复，不能声称跨主机灾备。
`REGISTRY_IMMUTABLE_IMAGE` 必须是该镜像实际 RepoDigests 中的 repository@sha256 引用；
恢复前还须核验 registry 可访问性，不能只保留可变 tag。未来迁移 registry 时需要单独验证
推送、平台/架构、digest 拉取与保留策略；本合同不自动开通 registry 或迁移镜像。

`ARTIFACT_IDENTITY` 包含 Commit/Tree/Image、业务配置、data/schema identity；
`RUNTIME_NAMESPACE_IDENTITY` 包含 Compose project、container name、host port。
两者分别记录，namespace 不是业务内容身份。正式 production Compose 精确约束保持；
受保护 host policy/3、/5 可为 recovery-validation 声明有限 namespace 投影，见
下文 Recovery Runtime Namespace Projection。
复用现有 production 签名域与旧镜像 grant schema，不增加容器 role、公钥或审批服务；
recovery 是 host policy 的用途限制，不是 deployment 授权或普通 caller override。

仅允许独立 Compose project、container name、127.0.0.1 的非8501宿主端口和独立普通
bridge（internal=false）。容器内仍使用旧8501端口。除 fresh grant 的独立只读注入目录
和既有随机 hostname nonce 外，业务 env/command、Commit/Tree/Image、历史数据源及
RO/RW 语义逐项等于受保护旧 policy 与实际仍运行 production；额外差异拒绝。
恢复仅认可已在运行的精确旧 artifact，不能借 recovery 启动未接纳业务 candidate；
旧 candidate record 作为历史绑定保留，不用历史 record/grant 到期阻止新实例签发。

顺序保持 fresh create → inspect/pre-release → fresh grant → start → runtime preflight /
health / localhost HTTP / targeted preservation → 清理明确 recovery instance/network。
签名前后复核实际 production ID/Image/started_at/config/network/ports，新的 operational
来源不得出现在旧恢复实例的任何挂载（含RO）中，目录/文件身份前后保留。签名仍绑定
actual instance、nonce、配置/rendered Compose/mount hash及期限；不得复用旧 grant。
不得 stop/restart/rename production，不做 traffic switch，不做CNF save，不做完整业务回放。
普通 deployment、Routine Release 及无 recovery 字段的 policy 行为不变。

## Recovery Runtime Namespace Projection

### Docker config 的有界默认值兼容

`actual_config_sha256` 始终保留原算法：对完整 Config/HostConfig/Path/Args 作 canonical JSON
SHA-256，不把 semantic hash 冒充历史 raw hash，不重写旧 policy、created binding 或 deployment result。
Raw equal 直接通过。Raw mismatch 时仅重建 `host_config.OomKillDisable` 的 false/null 对侧，
重建 payload 必须精确重现 sealed raw SHA，实际 payload 也必须重现 observed raw SHA。
所有其他字段保持原字节身份；缺字段、数字0、true、其他HostConfig/env/mount变化不适用。

命名规则 `OOM_KILL_DISABLE_FALSE_NULL_EQUIVALENCE` 仅在宿主实际 `docker info`
证明 ServerVersion=26.1.3、CgroupVersion=2 时启用，记录 Docker version/cgroup mode/driver。
其他平台 raw equal 不受影响；raw mismatch 保持失败，扩展平台需独立证据和测试。
`compare_config_payloads` 是纯比较；正式入口从实际 Docker 观察读取平台，不接受 policy 提交
平台豁免。结果保留 policy_raw_sha256、actual_raw_sha256、raw_hash_match、semantic_config_match、
compatibility_rule、platform。Recovery pre-release 在 recovery_config_comparison 中保留旧实例比较。
原始实例指纹、fresh create/grant/start 时序、grant raw config hash 和 namespace projection 均不改变。

真实脱敏 fixture `08_tests/fixtures/runtime_config/production-e42-running.json` 来自只读审计。
测试仅将 OomKillDisable 改为 false 重建旧 payload，并分别断言两个完整历史 SHA；该重建不是
新 policy 或历史 inspect 原件。回放只证明本默认值兼容，不代表真实 targeted recovery PASS。

当前 recovery-validation 复用 production 域，旧 image 的 production-execution-grant/2 或 /3
无需修改。只有从获批、root-owned clean detached tooling 执行的 host issuer 消费这项用途；
不增加签名类型、审批层或新 Evidence Bundle。普通 production/candidate policy 不获得投影能力。

host-runtime-policy/3、/5 的可选 `recovery` 对象必须只有以下字段：

- `purpose`: `recovery-validation`。
- `baseline_policy`: 原 root-owned production policy 的绝对 `path` 与 `sha256`；禁止递归recovery。
- `production_container_id`: 仍在运行的旧production精确64位ID。
- `production_observation_sha256`: `recovery_namespace.production_identity` 从实际Docker观察生成；
  包括ID/Image/Created/RestartCount/Config/HostConfig/NetworkSettings/Path/Args/started_at。
- `nonce`: fresh随机32位hex；`project=spread-recovery-<nonce>`、
  `container=<service_id>-recovery-<nonce>`、`network=<project>-net`。
- `host_port`: 1024–65535内未占用且非8501的端口，强制只绑定127.0.0.1。
- `preserved_store_sources`: 此次target新增operational目录的完整resolved来源列表；
  必须已经存在，不能alias或互相重叠。旧实例不得挂载它们，包含RO祖先覆盖。
- `expected_network_id`: create 后从实际 recovery Docker network object 读取的完整 ID；
  准备 Compose 投影时尚无该对象，可暂缺；pre-release 与 fresh grant 前必须写入
  root-owned policy 并与重新读取的 network object 精确相等。

该对象只记录命名空间和旧实例绑定，不接受safe/PASS/业务override声明。policy外层既有
artifact/runtime字段、历史mounts与baseline一致；source_root/approved_source_root仍指旧artifact，
宿主工具从当前批准main独立检出执行。恢复只观察已运行且与旧policy精确相符的artifact；
不使用旧candidate record的有效期作为fresh recovery grant许可，也不跳过旧source/Manifest核验。
旧record引用仍必须与baseline一致。历史execution grant既不读取也不续期。

唯一技术挂载来源变化为fresh grant目录：在既有protected storage allocation内单独创建，
只读注入同一grant destination；不得与旧grant目录/任何业务来源重叠。该变化服务于fresh
instance-bound grant，不允许替换history/data/log/output/snapshot来源或修改其RO/RW。
实际production端口/名称保持占用；新network独占、bridge/internal=false、无IPv6/额外options，
实际Docker network ID不得等于production network ID，不能有其他container endpoint。
比较旧 Compose network 与恢复投影时，仅将空的 `network.ipam: {}` 视为未声明 custom IPAM；
非空 IPAM 和其他网络字段仍严格核验，之后才投影 network name。此规则不适用于其他空对象。
恢复配置再经 Compose 解析后，network 子树由同一恢复语义校验器验证有效 driver、
internal、custom IPAM、独立网络及投影名称；只有校验明确通过，最终 Compose 结构比较才
移除该子树。服务端口、网络成员关系和所有非 network 字段继续严格比较。

执行使用现有步骤：操作者先准备root-owned policy与rendered Compose，普通
`docker compose up --no-deps --no-start --no-build --pull never <service>` 创建新slot，
inspect 实际容器与独立 network object，并将后者 ID 写入受保护 recovery policy；然后现有
`pre_release_runtime.py --production-policy ... --container-id ... --report-output ...`
和 `host_authorization.py` production issuer 核验并签发，最后才 `docker start <exact ID>`。
pre-start 只接受 `State=created`、唯一批准的 network attachment、network object 精确 ID、
隔离 bridge 语义与 localhost port。created inspect 中尚未 materialize 的空 `NetworkID`
记录 `RUNTIME_NETWORK_IDENTITY_ASSERTION=DEFERRED_UNTIL_POST_START`；非空错误 ID 立即失败。
旧镜像继续使用既有 grant/2 payload；仅 recovery grant 的签名 `grant_id` 对受保护 network
object ID、容器 ID、随机 nonce、端口、镜像和 Approved Commit/Tree 作承诺，不增加容器协议字段。
start 后、任何 runtime preflight/health/HTTP 前必须调用 host
`validate_recovery_post_start(exact_id, expected_policy_path=..., grant_path=..., key_path=...)`：
核验原签名、grant ID 承诺、实际 `NetworkID`、非空 `EndpointID`、唯一 endpoint、网络对象与
Production 隔离。失败立即停止并只清理精确恢复实例/网络，撤销或过期其 grant，不继续探测。
命令行入口为 `host_authorization.py --validate-recovery-post-start --role production`
并传入同一 `--container-id`、`--policy`、`--key`、`--grant-directory`、`--grant`；
该模式只验证现有 grant，绝不重新签发。只有输出 `POST_START_NETWORK_IDENTITY_VALIDATION=PASS`
才能继续 runtime preflight。失败由操作者执行上述精确清理与 grant 撤销，不得继续运行健康检查。
创建前保存旧production指纹与targeted history/operational枚举；issuer在签名前后重读旧policy、
actual production和operational目录/文件。签名内existing rendered_compose_sha256、
actual_config_sha256、mount_contract_sha256、container_id与nonce绑定实际recovery slot。

上述 post-start 网络 PASS 后，collector 才继续真实 runtime preflight/health/localhost HTTP
及原有 targeted preservation observation。原有 pre-start issuer 仍只接受 created，不能向
running 容器补 grant。
结束时核验history内容、operational目录inode/files和production指纹均未变化，保存证据，
仅清理精确recovery ID及其无其他endpoint的network，保留image和所有数据源。
本能力的模拟/CI PASS不是实际targeted recovery PASS；真实执行仍需独立任务授权。
