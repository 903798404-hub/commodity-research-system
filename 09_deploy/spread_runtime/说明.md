# Spread Production Runtime Wiring

本目录是 `spread-production-runtime-wiring` 的部署源码，服务仍为完整 `spread-dashboard`。Runtime Manifest 是 `02_configs/runtime_contracts/spread-production-runtime.json`。登记和源码实现不等于容器验收或生产批准。

## 候选与生产身份

从精确 Commit/Tree 的干净 Git 源码构建 digest-pinned Python 镜像；`RELEASE.json` 的 application 是项目 ID，OCI service 是 `spread-dashboard`。镜像不包含 `.git`、候选 fixture、私钥或生产数据。使用数值非 root 用户和只读 root filesystem。业务容器不挂 Docker socket，不签发授权。

执行身份必须显式选择。容器使用受保护宿主注入的只读 grant，同时验证 RELEASE、manifest、实际镜像和实例配置。Git CLI 要求显式 Git identity 和 Approved Commit/Tree，不接受 repository_root 或 runtime marker 单独授权。任何身份失败均退出，不自动回退到开发模式。

镜像构建把已核验的 `MARKET_DATA_GIT_HEAD` 和 `MARKET_DATA_GIT_TREE` build arguments 固化为镜像默认环境。Compose 不动态提供或覆盖这两个值。只读 preflight 在完成 OCI grant 验证后，必须确认实际环境、`/app/RELEASE.json` 和已验证 OCI identity 的 Commit/Tree 三者完全相同，并且只输出 Commit、Tree、Image ID 和身份角色这些非敏感身份字段。任何缺失或不匹配都使 preflight 失败。这些镜像默认环境会被宿主的实际配置摘要和 Compose 默认环境比较所覆盖，不扩展 Runtime Manifest 的 deployment 环境合同。

## 部署来源和存储

所有 Compose 命令以精确候选源码根作为 `--project-directory`，使用本目录 `compose.yml`；不能因为路径名相同就把另一份 Compose 当作实际部署源。生产 release 记录 source/rendered Compose SHA、实际 mounts、环境、Image ID 和宿主授权。通过候选验收的 Image ID 直接提升，正式切换禁止 build。

`SPREAD_IDENTITY_ROOT` 是受保护正式 identity 根。数据、Weather、历史 runtime、snapshot consumer、result 和 CNF 根为只读；outputs/logs 为独立可写目录。各来源必须来自批准的 production allocation，不能指向开发 worktree、旧 PM worktree、Preview 或候选临时数据。

`SPREAD_SNAPSHOT_ROOT` 同时以只读 consumer `/runtime/import-profit/snapshots` 和可写 capture alias `/runtime/capture-snapshots` 挂载。生产预检及显式 capture 必须确认二者实际为同一目录；CLI 只能写入 grant 授权的 alias。候选使用独立只读合成 snapshot 和独立空的临时可写 alias，不能把 fixture 挂成可写来模拟生产。

页面固定 `STRICT_RUNTIME` / `FORMAL`，不启用 CNF save，不传历史 business_date 或页面写入授权变量。Tankan 仍使用 `TANKAN_SECRET_FILE` 所指文件，通过 Compose secret 注入 `/run/secrets/tankan.env`，不创造包含秘密的新环境变量。初始化不读取该秘密、不访问网络、不 capture。

## 验收

13 个明确登记的合成输入仅用于候选验证：其 Git blob SHA 和目标只读路径绑定在 manifest 中，由通用引擎放入受保护的临时 mount。不得复制为生产 runtime，也不得把这些 synthetic snapshot 当作真实 AM/PM temporal acceptance。

只读 preflight 初始化真实 CLI identity、Domestic Spread reader、Soybean STRICT_RUNTIME 页面和 immutable snapshot consumer。生产预检只读取已有 SEALED；正式 AM 不是部署前置条件，只有 PM 时验证 PM，合法空 Snapshot store 报告 `NOT_YET_AVAILABLE`，不要求补采。已有 release 不完整、环境不符、身份或内容校验失败仍然失败，不能作为空 store 忽略。候选读取明确的 synthetic SEALED。缺少实际 runtime、身份或依赖必须失败。有效的投产前空 AM/PM 状态不等于已验证真实 AM/PM capture 或结果批次展示。

代码 closure 前必须取得实际隔离 Linux image 的全部正反向 Deployability probe 和签名 candidate record，再按项目 Completion 和独立 integration 验收。Windows 上的解析或 Python tests 不能替代容器 PASS。当前目录不能自我签发 Production Approval。

## 激活边界

不新增 cron、Scheduled Task、自动 AM/PM capture、FULL DAILY/Wrapper/Provider Preflight/Daily Summary 接入或 Notification activation。只读部署 smoke 不执行 capture，也不修改旧 SEALED。未来显式执行 capture 时必须指定日期/session、request/calendar、正式 identity 和 capture alias，并通过现有 secret-file 与数据合同。

`AM_PM_AUTO_EXECUTION=NO`；`INTRADAY_FULL_DAILY_DEPENDENCY=NONE`；`NOTIFICATION_AUTO_EXECUTION=NO`。`REAL_AM_TEMPORAL_ACCEPTANCE=DEFERRED`；`REAL_PM_TEMPORAL_ACCEPTANCE=DEFERRED`；temporal acceptance 不阻塞部署。

## 受控 Runtime Release

本节是在已获得本次完整范围授权、且项目 Completion、main 集成、同一候选 Image ID 的
13 项 Deployability probe 与签名 candidate record 均已完成后使用的审核受控步骤。它不
替代宿主 `host_authorization` 的身份规则，不创建授权策略、密钥或生产数据，也不把
`09_deploy/spread_release/` 的候选工具或旧 schema 当作正式控制面。实际本次审批引用由
发布负责人填入密封 Release；不得重复要求或臆造审批。

本步骤使用规范要求的文件名，但使用独立 schema，不冒充旧工具版本：

| 文件 | schema_version | 作用 |
| --- | --- | --- |
| `release.json` | `controlled-runtime-release/1` | 目标身份、已验证候选和回滚对象 |
| `release.manifest.json` | `controlled-runtime-artifact-manifest/1` | 密封 Release |
| `candidate_result.json` | `controlled-runtime-candidate-result/1` | 引用现有签名候选 record 与实际 probe 身份 |
| `candidate_result.manifest.json` | `controlled-runtime-artifact-manifest/1` | 密封候选结果 |
| `deployment_plan.json` | `controlled-runtime-plan/1` | 唯一允许的切换模板和实测绑定规则 |
| `deployment_plan.manifest.json` | `controlled-runtime-artifact-manifest/1` | 密封计划 |
| `deployment_result.json` | `controlled-runtime-result/1` | 实测切换或回滚结果 |
| `deployment_result.manifest.json` | `controlled-runtime-artifact-manifest/1` | 密封部署结果 |
| `deployment_result.bundle.manifest.json` | `controlled-runtime-result-bundle/1` | 密封结果及所有必需成员 |

每个 artifact 在内存中完成独立 schema 校验后，使用已批准源码中的排他 JSON 发布原语写入；
目标和 Manifest 都必须新建、fsync 并拒绝覆盖。每个 artifact Manifest 至少包含
`artifact_type`、`target_file`、`target_sha256`、`target_size_bytes`、
`target_schema_version`、`generated_at`、`release_id`、`git_commit`、`git_tree` 和
`image_id`。候选和部署结果 Manifest 还必须包含实测的 `runtime_git_commit`。Bundle
逐项列出 Release、Candidate、Plan、Result、各 Manifest、pre-release report 和 grant
evidence 的文件名、SHA-256、大小及 schema；它不是旧 Release bundle。

### 闭合 artifact 字段

`controlled-runtime-release/1` 必须包含：`release_id`、`generated_at`、
`approval_reference`、`project_id`、`service_id`、`runtime_id`、`approved_commit`、
`approved_tree`、`image_ref`、`image_id`、`oci_revision`、镜像内 `RELEASE.json` 的
SHA-256 与 Commit/Tree、Runtime Manifest 和 runtime marker 的路径及 SHA-256、
protected policy 的路径标识及 SHA-256、candidate record 的 record ID/SHA-256/
evidence SHA-256、目标 Compose/项目目录/环境的路径标识和 SHA-256、allocation mount
contract digest、正式数据资产 release/manifest SHA-256，及完整 `rollback_object`。
`rollback_object` 至少有旧容器 ID、Image ID、OCI revision、Config SHA-256、Compose
SHA-256、环境 SHA-256、端口/挂载 digest 和唯一 rollback 临时名称。

`controlled-runtime-candidate-result/1` 必须包含 Release SHA-256、现有签名 candidate
record 的路径标识、record ID、签名 key ID、record SHA-256、evidence SHA-256、13 项
probe 的名称和 PASS 状态、候选 Image ID、OCI revision、镜像内 Release Commit/Tree 与
实测 runtime Git Commit。它只引用已验证 record，不接受调用方提供的 probe 内容。

`controlled-runtime-plan/1` 必须包含 Release 与 Candidate artifact SHA-256、开始前
baseline snapshot SHA-256、目标 Compose 的严格单服务投影、目标环境 allowlist 的键名和
SHA-256、旧实例冻结身份、rollback template、timeouts、健康与 consumer 数据检查、
失败触发条件和全部 argv 模板。Plan 在 create 前不含未知容器 ID；唯一的
`created_instance_binding` 规则要求把 create 后实测的 64 位 container ID、Image ID、
Config SHA-256、mount contract SHA-256、actual Compose SHA-256 和 `Running=false` 写入
新的不可覆盖 binding artifact，并以其 SHA-256 作为 pre-release、grant、start 和 Result
唯一可接受的实例引用。外部输入不得填写或替换该 ID、binding 或 argv。

`controlled-runtime-result/1` 必须包含 Release/Plan/Binding SHA-256、每一步 argv 的
实测退出状态和 UTC 时间、旧/新容器 ID、实际 Image ID、OCI revision、镜像内 Release
Commit/Tree、实测 runtime Git Commit、实际 Config/Compose/mount/data-asset digest、
pre-release report SHA-256 与 PASS、grant ID/SHA-256/expiry、start、health 和 consumer
检查结果，以及 `status`、`rollback_performed` 和 rollback 后实际身份。失败结果同样
排他封存，绝不写为成功。

### 分步切换

1. 在任何写入前重新只读核验已密封 Release、Candidate、Plan、正式旧实例、目标镜像、
   policy、allocation、Compose、环境和数据资产；任一漂移即停止。
2. 固定容器名需要短暂服务窗口：停止旧 `spread-dashboard`，改名为 Release 密封的唯一
   rollback 名称，保留其容器和镜像，不删除、不 build。若 create 前失败，立即改回名称并
   启动旧实例。
   新 Release 必须使用已密封、与旧实例 Compose project label 不同的唯一项目名；目标
   Compose 的顶层 name、计划 argv 和宿主重渲染结果必须一致。仅改旧容器名称不会改变其
   Compose labels；沿用旧项目名会让 `--force-recreate` 选中并删除回滚实例，因此禁止。
3. 只可执行 Plan 密封的 create argv：

   ```text
   docker compose --env-file <target-env> --project-name <project> \
     --project-directory <directory> -f <compose> \
     create --no-build --pull never --force-recreate spread-dashboard
   ```

   当前 Docker Compose `create` 支持 `--no-build`、`--pull never` 和
   `--force-recreate`，但不支持 `--no-deps`；不得伪造该参数。目标 Compose 严格投影必须
   只有 `spread-dashboard`，其 `depends_on` 缺失或为空，且没有 profiles、scale、extends、
   links 或 lifecycle hooks。create 后实测只创建一个未启动的目标容器，任何额外容器的
   创建、启动、停止或删除，或任何 build/pull，均失败并回滚。
4. 使用 create 后唯一 binding 的 container ID 执行既有只读原语
   `pre_release_runtime.py --production-policy ... --container-id ... --report-output ...`；
   报告必须为 PASS，且 `container_started=false`、`production_write_granted=false`。随后仅以
   同一 ID 调用既有 `host_authorization.py --role production` 签发受保护、只读、排他的
   grant。任何 grant 前启动、policy/record/实例漂移或 grant 写入失败均失败。
5. 仅在 grant 后执行 Plan 密封的 `docker start <exact-container-id>`。该命令只能启动已
   创建的单一 stopped 实例，不能 build、pull、recreate 或解析依赖；不得使用
   `docker compose up` 代替。start 前后重测绑定 ID、镜像、Release、grant、Config、mount
   与端口，并完成有界 health 和 consumer 数据检查。
6. 成功后封存 Result、Result Manifest 和 Bundle。失败时停止并移除新实例，改回旧实例的
   正式名称并启动，重测其密封的旧 Image/Config/mount/health；保留失败证据和已签发 grant，
   不复用 grant、不删除 rollback 对象，且 Result 标为 rollback 或失败。
